# 설계 결정 기록

왜 이렇게 만들었는지를 남긴다. **무엇을 만들었는지는 각 플러그인 README에 있다.**
여기 있는 건 나중에 "이거 왜 이렇게 했지?" 싶을 때 보는 문서다.

결정을 바꾸려면 이 문서의 해당 항목부터 고치고 구현을 따라오게 한다.

---

## 마켓플레이스

### plugins/ 하위 모노레포로 간다

플러그인마다 레포를 파면 버전 관리가 흩어지고, 사용자는 마켓플레이스를 여러 개 등록해야 한다.
루트에 `.claude-plugin/marketplace.json` 하나를 두고 `source`를 `"./plugins/<이름>"`으로 건다.
플러그인이 늘어도 사용자는 마켓플레이스 하나만 최신화하면 된다.

### 버전은 두 곳을 함께 올린다

`plugin.json`과 `marketplace.json`의 `version`이 어긋나면 사용자가 업데이트를 못 받는다.
한쪽만 올리는 실수가 가장 흔하므로, 배포 전 두 값이 같은지 확인한다.

### 플러그인 이름에 내부 구조 용어를 쓰지 않는다

`work-cases`는 "10개 case로 나눠놨다"는 **제작자의 구조**를 이름에 노출한 것이었다.
쓰는 사람은 case가 뭔지 모른다. 이름은 **무엇을 해주는지**를 말해야 한다.
`work-cases → work-toolkit`, `dashboard-maker → report-maker`, `ne-knowledge → knowledge-notes`.

같은 이유로 스킬 이름도 기능 용어를 피한다. 비데이터 인력이 쓰는 플러그인이다.

## work-toolkit

### 스킬은 영역으로 묶고, 상황은 참조 문서로 세분화한다 (v0.2.0)

v0.1.0은 상황 하나당 스킬 하나(case-01~10)였다. 두 가지 문제가 있었다.

1. **과적합** — case-01이 "요구사항 변경 + 일정 고정"으로 못박혀 있어,
   "요구사항은 그대론데 인력이 빠졌다"는 갈 곳이 없었다. 판별표를 벗어나면
   플러그인 밖으로 빠져나가 일반 답변이 됐고, 그러면 플러그인을 쓸 이유가 없다.
2. **description 충돌** — case-01/03/07이 서로 겹쳐 보였다. 상황을 52개로 늘리면
   스킬 52개가 되고, description이 뒤엉켜 자동 라우팅이 오히려 망가진다.

그래서 계층을 하나 올렸다.

```
영역 스킬 7개 (description이 서로 명확히 구분됨)
  └ 상황 판별표
      └ references/situations/<영역>/<id>.md  (52개)
```

**상황이 늘어도 스킬 수는 안 늘어난다.** 과적합은 각 영역 스킬에
"판별표에 없으면 그 영역의 공통 원칙으로 처리" 경로를 둬서 해소했다.
이제 안 맞는 상황도 플러그인 밖이 아니라 영역 안에서 받는다.

### 출력 규격을 references로 분리한다

같은 상황을 두 번 돌렸을 때 결과 모양이 달라지면 신뢰가 무너진다.
`references/output-rules.md`에 공통 규칙(확인 필요 표기, 사실·추정 구분, 번호 매긴 출력 섹션,
분량, 톤)을 두고 52개 문서가 참조만 한다. 규칙이 바뀌면 한 곳만 고친다.

52개 SKILL.md에 같은 규칙을 복사했다면 규칙 변경 때마다 52곳을 고쳐야 하고,
실제로는 몇 곳이 누락되어 서로 다른 규칙이 공존하게 된다.

### 참고 자료는 구조만 차용한다

에이블런 프롬프트 팩과 퍼블리 AI 프롬프트 45를 참고했다. 둘 다 인용 시 출처 명기를 요구한다.
프롬프트 문장을 그대로 옮기지 않고 구성(먼저 확인할 것 · 출력 섹션 구조)만 차용해
사내 실무에 맞게 다시 썼다. 출처는 work-toolkit README에 명기한다. **사내 용도로만 사용한다.**

## report-maker

### 포맷 중립 스펙 레이어를 반드시 거친다

```
브리프 → 데이터 → [리포트 스펙] → HTML 또는 문서
```

"무엇을 어떤 차트로 어떤 메시지로 보여줄지"를 포맷과 무관하게 먼저 확정한다.
렌더러가 각자 레이아웃을 판단하면 **같은 데이터로 만든 HTML과 슬라이드의 결론이 달라진다.**
전사 배포에서 이건 신뢰 문제가 된다.

exhibit이 하나뿐이어도 스펙 단계를 건너뛰지 않는다.

### 기준은 규칙이 아니라 파라미터다

순출고를 봐야 할 때도, 총출고를 봐야 할 때도 있다. 특정 기준을 강제하지 않는다.
강제하는 것은 **기준을 명시했다는 사실**이다.

- 스펙의 `basis` 필드 필수, exhibit별 override 가능
- 화면 상단과 각주에 항상 노출
- 기준이 바뀌면 결론문도 바뀌므로, `action_title`을 다시 계산해서 다시 쓴다

### 데이터 소스는 어댑터 구조

Metabase 전용으로 만들지 않는다. 엑셀·CSV·붙여넣은 표·Metabase가 대등한 입력이다.
**Metabase는 사내망 전용**이라 접근 불가한 사용자가 반드시 있다.
어떤 경로든 `load-data`를 통과하면 정규화 데이터셋 + 데이터셋 카드가 나온다.

### 참조 문서에는 조회로 알 수 없는 것만 쓴다

- 테이블 목록, 컬럼명, 시트 구성, 헤더 위치 → **런타임 조회.** 문서화하지 않는다
- "YES24는 BNK가 아닌 SCM 기준", "이 테이블은 일 스냅샷이라 합산하면 중복" → 문서화

조회하면 아는 것을 문서에 박으면 실제와 어긋나는 순간 해롭고,
전사 배포에서는 갱신할 때마다 재배포해야 한다.

### quick과 report는 형식이 다를 뿐 품질 기준은 같다

애드혹이라고 파이차트가 나오거나 기준 표기가 빠지면 안 된다.
두 모드가 `design-rules` / `chart-rules` / `metrics`를 동일하게 적용한다.

### HTML은 외부 의존이 없어야 한다

차트 라이브러리를 CDN에서 불러오면 사내망 밖이나 오프라인에서 안 열린다.
인라인 SVG로 직접 그린다. 단일 파일이라 링크 공유와 사외 반출이 쉽다
(그래서 보호 옵션 안내가 필요하다).

## knowledge-notes

### 공용 vault가 아니라 개인 vault + 규칙 통일

공용 vault는 누가 관리하느냐에서 막히고, 결국 아무도 안 쓴다.
각자 개인 vault를 쓰되 **노트 타입 5종 · frontmatter 스키마 · 관계 어휘 6개 · 원자성 판정**
네 가지만 고정한다. 이게 통일되지 않으면 나중에 노트를 합칠 수 없다.

이 넷은 설정으로 빼지 않는다. vault 경로·폴더 번호 체계·개인 태그만 설정 대상이다.

### 폴더는 타입으로만 나눈다

주제별 폴더(영업/데이터/S&OP)를 만들면 **한 노트가 두 곳에 속하는 문제가 반드시 생긴다.**
주제는 링크와 `domain` 필드로 처리한다.

### aliases가 가장 중요한 필드다

국문·영문·약어를 섞어 쓰는 환경에서 alias가 없으면
"재고회전율", "재고 회전율", "inventory turnover", "ITR"이 전부 별개 노트로 자란다.
`kb-atomize`의 3단계(기존 vault 검색 + alias 대조)가 이 플러그인의 존재 이유다.
이게 없으면 템플릿과 다를 게 없다.

### schema 번호를 반드시 넣는다

나중에 규칙이 바뀔 때 마이그레이션 대상을 찾는 유일한 단서다.

### 정의의 단일 출처는 사내 문서다

개인 vault는 **해석과 적용**을 담는다. 지표 정의를 노트에 복사하면
원본이 개정된 순간 복사본은 거짓이 되고, 그 복사본을 근거로 만든 보고서가 계속 나간다.
사내 문서를 참조만 한다.

### 매 턴 "지식화할까요?"를 띄우지 않는다

`Stop` 훅으로 매번 제안하면 **사흘 안에 전원이 무시하게 된다.**
사내 배포 실패의 가장 흔한 원인이다.
주력은 주 1회 `/kb-review`다. 한 주를 모아 보면 반복 등장한 것이 보이고,
그게 진짜 지식화할 가치가 있는 것이다.

### 시드 노트를 동봉한다

빈 플러그인은 아무도 안 쓴다. 규칙보다 이게 채택률을 좌우한다.
48개를 넣었고, 사내 정의가 확인되지 않은 항목은 **일반 정의만 채우고 사내 정의는 TODO로 비워뒀다.**
추정으로 채우지 않았다.

## 세 플러그인 공통

### 확인되지 않은 값은 추정으로 채우지 않는다

지표 정의, 임계값, 사내 기준처럼 확인이 필요한 값은 **빈칸 + TODO**로 남긴다.
추정값을 넣고 조용히 돌리면 틀린 보고서가 나가고, 틀렸다는 사실 자체를 아무도 모른다.
미확정 항목은 `docs/open-issues.md`에 모아 관리한다.

### 플러그인 간 경계

| 단계 | 담당 |
|---|---|
| 무엇을 볼지, 어떻게 해석할지, 어떻게 설명할지 | work-toolkit (`data-insight`, `make-visual`) |
| 차트·대시보드·보고서를 실제로 만들기 | report-maker |
| 알게 된 것을 노트로 남기기 | knowledge-notes |

`data-insight`와 `make-visual`은 렌더링 단계에서 report-maker로 인계한다.
report-maker가 설치되어 있지 않으면 표와 해석 문장까지만 내고 사용자에게 알린다.

### 스킬 description은 실제로 칠 법한 문장을 넓게 넣는다

진입 스킬(`work-helper`, `report-helper`)은 넓고 다소 밀어붙이는 톤으로 쓴다.
"차트로 보여줘", "이 엑셀 보고용으로 정리" 무엇이든 들어오게 한다.
나머지 스킬은 좁게 쓰되, 숙련 사용자가 직접 부르는 건 막지 않는다.
