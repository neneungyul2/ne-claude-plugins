# 설계 결정 기록

왜 이렇게 만들었는지를 남긴다. **무엇을 만들었는지는 각 플러그인 README에 있다.**
여기 있는 건 나중에 "이거 왜 이렇게 했지?" 싶을 때 보는 문서다.

결정을 바꾸려면 이 문서의 해당 항목부터 고치고 구현을 따라오게 한다.

---

## 마켓플레이스

### plugins/ 하위 모노레포로 간다

플러그인마다 레포를 파면 버전 관리가 흩어지고, 사용자는 마켓플레이스를 여러 개 등록해야 한다.
루트에 `.claude-plugin/marketplace.json` 하나를 두고 `source`를 `"./plugins/<이름>"`으로 건다.
플러그인이 늘어도 사용자는 마켓플레이스 하나만 최신화하면 된다.

### 버전은 두 곳을 함께 올린다

`plugin.json`과 `marketplace.json`의 `version`이 어긋나면 사용자가 업데이트를 못 받는다.
한쪽만 올리는 실수가 가장 흔하므로, 배포 전 두 값이 같은지 확인한다.

### 플러그인 이름에 내부 구조 용어를 쓰지 않는다

`work-cases`는 "10개 case로 나눠놨다"는 **제작자의 구조**를 이름에 노출한 것이었다.
쓰는 사람은 case가 뭔지 모른다. 이름은 **무엇을 해주는지**를 말해야 한다.
`work-cases → work-toolkit`, `dashboard-maker → report-maker`, `ne-knowledge → knowledge-notes`.

같은 이유로 스킬 이름도 기능 용어를 피한다. 비데이터 인력이 쓰는 플러그인이다.

## work-toolkit

### 스킬은 영역으로 묶고, 상황은 참조 문서로 세분화한다 (v0.2.0)

v0.1.0은 상황 하나당 스킬 하나(case-01~10)였다. 두 가지 문제가 있었다.

1. **과적합** — case-01이 "요구사항 변경 + 일정 고정"으로 못박혀 있어,
   "요구사항은 그대론데 인력이 빠졌다"는 갈 곳이 없었다. 판별표를 벗어나면
   플러그인 밖으로 빠져나가 일반 답변이 됐고, 그러면 플러그인을 쓸 이유가 없다.
2. **description 충돌** — case-01/03/07이 서로 겹쳐 보였다. 상황을 52개로 늘리면
   스킬 52개가 되고, description이 뒤엉켜 자동 라우팅이 오히려 망가진다.

그래서 계층을 하나 올렸다.

```
영역 스킬 7개 (description이 서로 명확히 구분됨)
  └ 상황 판별표
      └ references/situations/<영역>/<id>.md  (52개)
```

**상황이 늘어도 스킬 수는 안 늘어난다.** 과적합은 각 영역 스킬에
"판별표에 없으면 그 영역의 공통 원칙으로 처리" 경로를 둬서 해소했다.
이제 안 맞는 상황도 플러그인 밖이 아니라 영역 안에서 받는다.

### 출력 규격을 references로 분리한다

같은 상황을 두 번 돌렸을 때 결과 모양이 달라지면 신뢰가 무너진다.
`references/output-rules.md`에 공통 규칙(확인 필요 표기, 사실·추정 구분, 번호 매긴 출력 섹션,
분량, 톤)을 두고 52개 문서가 참조만 한다. 규칙이 바뀌면 한 곳만 고친다.

52개 SKILL.md에 같은 규칙을 복사했다면 규칙 변경 때마다 52곳을 고쳐야 하고,
실제로는 몇 곳이 누락되어 서로 다른 규칙이 공존하게 된다.

### 참고 자료는 구조만 차용한다

에이블런 프롬프트 팩과 퍼블리 AI 프롬프트 45를 참고했다. 둘 다 인용 시 출처 명기를 요구한다.
프롬프트 문장을 그대로 옮기지 않고 구성(먼저 확인할 것 · 출력 섹션 구조)만 차용해
사내 실무에 맞게 다시 썼다. 출처는 work-toolkit README에 명기한다. **사내 용도로만 사용한다.**

## report-maker

### 포맷 중립 스펙 레이어를 반드시 거친다

```
브리프 → 데이터 → [리포트 스펙] → HTML 또는 문서
```

"무엇을 어떤 차트로 어떤 메시지로 보여줄지"를 포맷과 무관하게 먼저 확정한다.
렌더러가 각자 레이아웃을 판단하면 **같은 데이터로 만든 HTML과 슬라이드의 결론이 달라진다.**
전사 배포에서 이건 신뢰 문제가 된다.

exhibit이 하나뿐이어도 스펙 단계를 건너뛰지 않는다.

### 기준은 규칙이 아니라 파라미터다

순출고를 봐야 할 때도, 총출고를 봐야 할 때도 있다. 특정 기준을 강제하지 않는다.
강제하는 것은 **기준을 명시했다는 사실**이다.

- 스펙의 `basis` 필드 필수, exhibit별 override 가능
- 화면 상단과 각주에 항상 노출
- 기준이 바뀌면 결론문도 바뀌므로, `action_title`을 다시 계산해서 다시 쓴다

### 데이터 소스는 어댑터 구조

Metabase 전용으로 만들지 않는다. 엑셀·CSV·붙여넣은 표·Metabase가 대등한 입력이다.
**Metabase는 사내망 전용**이라 접근 불가한 사용자가 반드시 있다.
어떤 경로든 `load-data`를 통과하면 정규화 데이터셋 + 데이터셋 카드가 나온다.

### 참조 문서에는 조회로 알 수 없는 것만 쓴다

- 테이블 목록, 컬럼명, 시트 구성, 헤더 위치 → **런타임 조회.** 문서화하지 않는다
- "YES24는 BNK가 아닌 SCM 기준", "이 테이블은 일 스냅샷이라 합산하면 중복" → 문서화

조회하면 아는 것을 문서에 박으면 실제와 어긋나는 순간 해롭고,
전사 배포에서는 갱신할 때마다 재배포해야 한다.

### quick과 report는 형식이 다를 뿐 품질 기준은 같다

애드혹이라고 파이차트가 나오거나 기준 표기가 빠지면 안 된다.
두 모드가 `design-rules` / `chart-rules` / `metrics`를 동일하게 적용한다.

### HTML은 외부 의존이 없어야 한다

차트 라이브러리를 CDN에서 불러오면 사내망 밖이나 오프라인에서 안 열린다.
인라인 SVG로 직접 그린다. 단일 파일이라 링크 공유와 사외 반출이 쉽다
(그래서 보호 옵션 안내가 필요하다).

### 결론은 판단 + 요청이다 (v0.4.0)

`key_takeaway`가 발견에서 끝나면 독자는 요청을 문서 맨 아래 액션 표에서야 만난다.
위에서 아래로 읽는 사람에게는 그게 마지막이다.

Knaflic의 Big Idea는 "고유한 관점 + 무엇이 걸려 있는지 + 완전한 한 문장"이고,
그 문장은 요청까지 포함한다. 그래서 `key_takeaway.ask`를 report 필수로 올리고
히어로 안에 렌더링한다. 액션 표는 그 전개일 뿐이다.

**대안으로 검토했다가 버린 것** — 액션 표를 문서 위로 올리는 것.
근거를 보기 전에 액션이 나오면 "왜?"가 해소되지 않는다. 요청 한 줄과 액션 표는 역할이 다르다.

### 히어로 요약을 따로 쓰지 않는다 (v0.4.0)

이전에는 `summary` 3줄을 별도로 썼다. 그러면 요약과 본문 제목이 따로 놀고,
요약이 세부 수치로 채워져 비교 틀이 서기 전에 숫자가 먼저 나온다.

지금은 **각 exhibit의 `action_title`을 순서대로 그대로** 나열한다. 부수 효과 셋:

1. 수평 논리 검사가 자동으로 된다 — 제목만 읽어서 이야기가 되면 통과
2. Bing-Bang-Bongo의 Bing이 공짜로 생긴다 (무엇을 말할지 먼저 말한다)
3. `action_title`이 서술형이 아니면 히어로가 무너지므로, 규칙이 강제된다

### views와 emphasis_steps를 분리한다 (v0.4.0)

같은 데이터로 여러 이야기를 할 때, 이야기마다 정렬을 최적화하고 싶어진다.
Knaflic 9장 사례연구 3의 결론은 명확하다 — **독자를 데이터에 익숙해지게 만들어 놓고
재배열하는 것은 불필요한 인지 세금이다.**

그래서 두 기능을 언어 수준에서 갈랐다.

| | 바뀌는 것 | 정렬 |
|---|---|---|
| `views` | 축·단위 | 바뀌어도 된다 (다른 축이므로) |
| `emphasis_steps` | 강조만 | **고정. 바뀌면 검사에서 걸린다** |

축을 바꾸면 결론이 뒤집히는 경우는 둘 다 아니다. 별도 exhibit이다.

### 스토리 검사를 체크박스가 아니라 절차로 둔다 (v0.4.0)

수평 논리·수직 논리·cascading·역스토리보딩은 "예/아니오"로 답할 수 없다.
**읽어 봐야** 한다. 그래서 `plan-report` 자체검사에서 체크리스트와 분리해
"실제로 돌리는 검사"로 따로 두고, 결과(읽은 문장)를 사용자에게 그대로 보여주게 했다.

같은 이유로 `build-html` 검수의 **"눈이 먼저 가는 곳" 테스트**도 체크박스가 아니다.
렌더링한 그림을 보고 시선이 어디로 가는지 확인하는 것이지, 코드로 판정할 수 없다.

### 정량 기준은 출처가 있는 것만 쓴다 (v0.4.0)

"계열은 몇 개까지", "강조는 얼마나"는 취향 논쟁이 되기 쉽다. 근거가 있는 것만 규칙으로 올렸다.

| 기준 | 값 | 출처 |
|---|---|---|
| 계열 수 상한 | 4~5개 | 단기기억 용량 약 4덩어리 |
| 강조 면적 상한 | 10% | Lidwell, *Universal Principles of Design* |
| 대각선 텍스트 금지 | 45° 52%↓ / 90° 205%↓ | Wigdor & Balakrishnan (2005) |
| 색맹 대응 | 남 8% / 여 0.5% | 일반 역학 수치 |
| 판단 시간 | 3~8초 | Knaflic 4장 |

숫자를 붙이면 "이건 왜 안 되나"에 답할 수 있다.

### 참조 문서에 완성된 예시를 두지 않는다 (v0.4.1)

예시는 텍스트만 오염시키는 게 아니라 **형태와 흐름을 고정한다.**
스펙 예시에 exhibit이 둘 있으면 둘을 만들고, 템플릿 body에 섹션이 셋 있으면 셋을 만든다.
브리프 예시에 질문이 셋 있으면 셋으로 맞춘다. 지침이 "질문 개수는 decision이 정한다"고
말해도, 눈앞의 완성품이 이긴다.

그래서 참조 문서의 코드 조각은 **키 스켈레톤**으로만 둔다 — 값 없이, 중첩 위치와 자료형만.
완결된 스펙 한 벌은 `references/examples/`로 빼고, README에
"가져올 수 있는 것은 중첩 위치와 자료형뿐"이라고 못박았다.
`html-template.html`의 `<body>`는 "부품 목록이지 레이아웃이 아니다"를 파일 안에 적었다.

**남겨둔 예외는 판단 예시다.** 반려/수정 쌍처럼 무엇이 왜 틀렸는지 보여야 하는 것은
추상적으로 쓰면 전달되지 않는다. 대신 자리표시자(A·B·X)로 도메인을 걷어냈다.

### 도메인 사례를 참조 문서에 남기지 않는다 (v0.4.1)

v0.4.0까지 참조 문서 곳곳에 특정 프로젝트의 사례가 박혀 있었다.
그중 일부는 **우리가 검증 끝에 폐기한 분류**였다 — 결과 변수(고등 비중)로 그룹을 나눈 뒤
그 그룹이 결과에서 다르다고 보고하는 순환논증. 예시로 남아 있으면 다음 리포트가 그걸 따라 한다.

사례를 걷어내고, 대신 **왜 그게 틀렸는지의 규칙**을 `frame-question`과 `spec-schema` 양쪽에 넣었다
(동어반복 / 선택 편향 / 교란 3행 표 + "분류 근거는 결과 변수와 독립이어야 한다").
플랫폼 기준 지표를 당사 매출로 읽는 문제도 용어 이름이 아니라
"기준이 다르면 다른 숫자다 / 합산하지 않는다"는 규칙으로 바꿨다.

실제 사례는 플러그인이 아니라 프로젝트 문서에 남긴다.

### 검수는 만든 사람이 하지 않는다 (v0.5.0)

v0.4.x까지 검수는 `build-html`의 체크리스트였다. **만든 에이전트가 자기 산출물을 자기 목록으로
채점하는 구조**였고, 이건 검수가 아니다. 무엇을 말하려 했는지 이미 알기 때문에
화면에 안 적힌 것도 읽힌다고 착각한다.

5단계로 `verify-report`를 신설하고, 실제 검수는 `agents/report-verifier`가 한다.
**넘기는 것은 파일 경로뿐이다** — 왜 이렇게 만들었는지, 어디를 봐 달라는지, "○○는 의도한 것"이라는
해명은 넘기지 않는다. 맥락을 주는 순간 서브에이전트로 돌리는 의미가 없어진다.
검수자가 찾는 것은 "만든 사람이 설명해야 알 수 있는 것"이고, 그건 곧 독자도 모른다는 뜻이다.

발견과 수정도 분리했다. 검수자는 파일을 쓰지 않는다 — 고치기 시작하면 눈이 흐려진다.

### 판단이 필요 없는 검사는 모델이 하지 않는다 (v0.5.0)

`scripts/check_html.py`. 의존성 없는 표준 라이브러리 스크립트다.
외부 리소스·자리표시자 잔존·각주 4요소·히어로 목록 개수·본문 표 행 수·숫자 중복·용어 등록,
그리고 `--spec`을 주면 `encoding.claim`과 `weight: primary` 개수까지 본다.

이걸 만들자마자 **우리 템플릿이 폰트 크기 20종, 모서리 라운드 12종을 쓰고 있었다는 게 드러났다.**
아티클이 지적한 바로 그 문제(11종 / 8종)를 우리 참조 문서가 저지르고 있었고,
1년 가까이 아무도 몰랐다. 규칙으로 "토큰만 쓴다"고 적어둔 것으로는 안 잡힌다 —
**세어봐야 잡힌다.** 타입 8단계(`--t1`~`--t8`)와 라운드 5단계(`--r`~`--rp`)로 정리했다.

### 인코딩 서열 — 차트를 골랐다고 끝이 아니다 (v0.5.0)

`question_type → chart` 매핑은 있었지만 **그 차트 안에서 어느 값이 어느 채널에 실리는지**는
아무도 정하지 않았다. 막대 길이는 건수인데 제목은 건당 효율을 말하는 실패가 여기서 나온다.

Cleveland & McGill 서열(위치 > 길이 > 각도 > 면적 > 농담 > 색상 > 텍스트)을 넣고,
스펙에 `encoding.claim`을 추가했다 — `action_title`의 주장을 만드는 필드 이름 하나.
판정은 기계적이다: `claim`이 `x`나 `y`가 아니면 반려.

### 자리 크기는 서열의 선언이다 (v0.5.0)

스펙은 "무엇을 말할지"를 정했지만 "화면에서 어떤 비중으로"를 정하지 않았고,
그래서 렌더러가 전부 같은 크기로 깔았다. `exhibit.weight`(primary/supporting/appendix)를
추가하고 `plan-report`에 배치 설계 절을 신설했다 — 서열 / 숫자의 소유권 / 강조 예산 / 흐름.

**별도 스킬로 빼지 않은 이유**: 스펙이 유일한 원본이어야 하고(HTML과 슬라이드의 결론이 갈리면 안 된다),
배치 판단은 결론 판단과 분리되지 않는다. `weight`는 포맷 중립이고, 픽셀은 각 렌더러가 번역한다.

### 서브에이전트는 격리가 목적일 때만 쓴다 (v0.5.0)

모델 차등으로 토큰을 아끼려면 각 단계를 서브에이전트로 돌려야 하지만,
스킬 frontmatter의 `context: fork` + `agent:`는 Claude Code 2.1.112 이하에서 무시된다.
그래서 파이프라인 전체를 선언적 fork로 바꾸지 않고, **격리 자체가 목적인 곳에만** 넣었다.

| 에이전트 | 모델 | 왜 |
|---|---|---|
| `report-verifier` | `inherit` | 맥락 격리가 목적이다. 스크린샷 판단에는 판단력이 필요하다 |
| `report-data-prep` | `sonnet` | 파싱·정제는 기계적이다. 파싱 로그로 본 대화 맥락을 채우지 않는 효과도 있다 |

`build-html`을 sonnet으로 내리는 것이 절감이 가장 크지만,
SVG 라벨 충돌·클리핑을 기계로 잡을 수 있다는 것이 확인되기 전에는 내리지 않는다 (open-issues E-6).

### 4px 그리드 — 치수가 제각각인 것이 "AI가 만든 느낌"이다 (v0.5.0)

diagram-design(cathrynlavery)이 "모든 치수는 4px의 배수"를 규칙으로 두고 그 근거를
**"AI가 만든 미감을 막는다"**로 적어둔 것을 보고 채택했다.

우리 템플릿에는 22px 패딩, 30px 여백, 11.5px·13px 글자가 섞여 있었다.
독자는 어디가 어긋났는지 못 짚지만 "뭔가 만들다 만 것 같다"는 인상은 받는다.

정리하면서 **타입 8단계 → 6단계, 라운드 5단계 → 4단계로 줄었고 전부 4의 배수가 됐다.**
줄어든 것이 손해가 아니라 이득이다 — 11.5px와 13px는 붙어 있어서 독자에게 아무 차이도
전달하지 못하면서 값만 늘리고 있었다. 예외는 1px 테두리, 2px 미세선, 999px 알약 셋뿐이고,
`check_html.py`의 `c_grid`가 배수 아닌 값을 전부 잡는다.

**폰트 크기까지 4배수로 밀어붙인 것은 의도한 선택이다.** 한국어 본문 14px는 유지되고
(4의 배수다), 붙어 있던 중간 단계만 흡수됐다. 본문을 16px로 올리거나 12px로 내리는
식이었다면 채택하지 않았을 것이다.

### 형태를 목적에서 도출한다 — 네 유형 (v0.5.0)

**템플릿을 부품 목록으로 바꿔도 형태는 여전히 하나였다.** 헤더 → 히어로 → KPI →
exhibit 세로 나열. 영업일보도 신간 판단도 추적 대시보드도 전부 진단 리포트 모양으로 나왔다.
샘플을 지운 것과 같은 문제가 한 층 위에 남아 있었던 것이다.

유형을 **산출물 사례에서 거꾸로 뽑지 않았다.** 그건 분류지 유형화가 아니고 새 상황에서 또 안 맞는다.
목적에서 내려왔다 — 이런 산출물이 존재하는 이유는 *누군가 무엇을 해야 하는데 그 판단에
필요한 것이 머릿속에 없기 때문*이다. 그래서 형태를 정하는 근본 변수는 주제가 아니라
**독자가 무엇을 모르는가**다. "모른다"에는 네 종류가 있다.

| 모르는 것 | 유형 | 주인공 |
|---|---|---|
| 무슨 일이 일어나는지 | `diagnostic` | 근거 exhibit 하나 |
| 어느 쪽이 나은지 | `choice` | 옵션 × 판단기준 표 |
| 지금 괜찮은지 | `watch` | 지표 행과 임계값 |
| 계획대로 가는지 | `track` | 시간축과 기준선 |

여기서 더 큰 갈래가 드러났다 — **한 번 읽는 것(진단·선택)과 다시 여는 것(감시·추적)은
다른 물건이다.** "특이사항 없음"이 전자에서는 실패고 후자에서는 정상 출력이다.

### 유형화는 규칙을 늘리는 일이 아니라 전제를 드러내는 일이었다 (v0.5.0)

유형표를 만들자 **기존 규칙 여럿이 진단형 전용이었다는 게 드러났다.**
`key_takeaway.ask` 필수, `brief.tension` 필수, `actions` 3~5개 필수, `weight: primary`가
exhibit 하나, 히어로 요약 = action_title 목록 — 전부 감시형에서 성립하지 않는다.
감시형은 열 때마다 결론이 달라지고, 정상이면 액션이 0개인 게 정답이고, 주인공이
exhibit이 아니라 KPI 행이다.

`report-types.md` §3에 유형 × 요소 표를 두고 `report_type`을 스펙(2.4)에 넣었다.
`check_html.py`도 유형을 읽어, watch에서 빈 `actions`를 실패로 보지 않고
오히려 억지로 만든 `tension`을 경고한다.

### 유형은 묻지 않고 읽어낸다 (v0.5.0)

"진단·선택·감시·추적 중 무엇인가요"라고 물으면 안 된다 — 사용자가 우리 분류를 배울 이유가 없고,
넷 중 고르라고 하면 대부분 애매해한다. 사용자가 이미 한 말, 특히 **"왜 지금 만드나"**에
답이 들어 있다. 신호표로 추정하고, 신호가 없거나 섞였을 때만 **가르는 질문 하나**를 던진다
("이 화면, 다음 달에도 같은 걸 또 여시나요?"). 두 번이면 끝난다.

### 확인은 두 번, 둘 다 글자로 (v0.5.0)

`frame-question`에서 **형태**(데이터 전), `plan-report`에서 **배치**(데이터 후).
데이터 전에 유형을 정하는 이유는, 데이터를 먼저 보면 *있는 데이터로 만들 수 있는 모양*이
형태를 정해버리기 때문이다. 배치는 실제 숫자를 봐야 정해지므로 데이터 후다.

**둘 다 글자 와이어프레임으로 보여준다. HTML을 그려서 확인받지 않는다.**
화면을 만들면 사용자는 구조가 아니라 색과 폰트에 반응하고, 만든 쪽은 만든 것에 애착이 생겨
틀렸어도 못 버린다. 되돌리는 비용이 글자 몇 줄이어야 되돌릴 수 있다.

### 사람의 눈은 판단에만 쓴다 — 렌더 검사 (v0.6.0)

`verify-report`를 만들 때 서브에이전트가 스크린샷을 보고 "잘린 글자가 있는가"를 판정하게 했다.
그런데 쿠팡 리포트에서 손으로 고쳤던 것들 — 라벨 클리핑, 라벨 충돌, 축 눈금과 값 라벨 겹침 —
**전부 기계가 잴 수 있는 것들이었다.** 사람의 눈을 글자 잘림 찾는 데 쓰면
정작 "강조가 옳은 곳에 걸렸나"를 볼 여력이 없어진다.

`scripts/lint_render.py`가 Playwright로 실제로 칠한 뒤 픽셀을 잰다 —
`scrollWidth > clientWidth`(잘림), SVG `getBBox` 대 `viewBox`(밖으로 나간 라벨),
텍스트 bbox 교차(겹침), 문서 대 뷰포트 폭(가로 스크롤), JS 에러, 요청 실패,
9px 미만 글자, 잉크 비율(빈 공간이 너무 많은 차트).

**폰트 폴백 검사가 특히 우리 문제였다.** 우리는 폰트를 임베드하지 않고 Pretendard를
가정해 SVG 좌표를 계산한다. 만든 PC에서는 멀쩡하고 받는 PC에서 넘친다.
폴백 스택만으로 다시 렌더해 같은 검사를 돌리고 WARN으로 낸다.

검수자 에이전트에서는 손으로 짠 playwright 조각을 지우고 이 스크립트를 부르게 했다.
에이전트가 보는 것은 이제 **기계가 못 보는 것뿐**이다 — 눈이 먼저 가는 곳, 위계,
어려운 말, 차트 종류가 질문에 맞는지.

### 같은 사실이 두 곳에 있으면 검사로 묶는다 (v0.6.0)

참조 문서 곳곳에 "이 표는 저기와 동일하다, 한쪽만 고치지 않는다"가 적혀 있었다.
**그건 규칙일 뿐 검사가 아니었고**, 오늘만 스펙을 2.2→2.3→2.4로 세 번 올리면서
아무도 대조하지 않았다.

`scripts/verify_docs_sync.py`(개발용)가 8가지를 본다 —
`${CLAUDE_PLUGIN_ROOT}` 경로 실존, SKILL/agent `name`과 폴더명 일치,
`spec_version`(머리말·필드표·예시 JSON·변경 이력), question_type 매핑표 줄 단위 대조,
유형 슬러그 3곳, 스크립트 임계값 대 문서 숫자, plugin.json 대 marketplace.json 버전,
스킬·에이전트 참조 실존.

만들자마자 **chart-rules가 "spec-schema 4장과 동일한 표"라고 가리키는데 실제로는 8장**인 것을
찾았다. 고치면서 장 번호 참조 자체를 지웠다 — 번호는 바뀌고, 바뀐 것을 아무도 모른다.
**깨지기 쉬운 참조는 검사하는 것보다 없애는 쪽이 낫다.**

여섯 가지를 일부러 어긋뜨린 사본으로 검사가 실제로 잡는지 확인했다.

## knowledge-notes

### 공용 vault가 아니라 개인 vault + 규칙 통일

공용 vault는 누가 관리하느냐에서 막히고, 결국 아무도 안 쓴다.
각자 개인 vault를 쓰되 **노트 타입 5종 · frontmatter 스키마 · 관계 어휘 6개 · 원자성 판정**
네 가지만 고정한다. 이게 통일되지 않으면 나중에 노트를 합칠 수 없다.

이 넷은 설정으로 빼지 않는다. vault 경로·폴더 번호 체계·개인 태그만 설정 대상이다.

### 폴더는 타입으로만 나눈다

주제별 폴더(영업/데이터/S&OP)를 만들면 **한 노트가 두 곳에 속하는 문제가 반드시 생긴다.**
주제는 링크와 `domain` 필드로 처리한다.

### aliases가 가장 중요한 필드다

국문·영문·약어를 섞어 쓰는 환경에서 alias가 없으면
"재고회전율", "재고 회전율", "inventory turnover", "ITR"이 전부 별개 노트로 자란다.
`kb-atomize`의 3단계(기존 vault 검색 + alias 대조)가 이 플러그인의 존재 이유다.
이게 없으면 템플릿과 다를 게 없다.

### schema 번호를 반드시 넣는다

나중에 규칙이 바뀔 때 마이그레이션 대상을 찾는 유일한 단서다.

### 정의의 단일 출처는 사내 문서다

개인 vault는 **해석과 적용**을 담는다. 지표 정의를 노트에 복사하면
원본이 개정된 순간 복사본은 거짓이 되고, 그 복사본을 근거로 만든 보고서가 계속 나간다.
사내 문서를 참조만 한다.

### 매 턴 "지식화할까요?"를 띄우지 않는다

`Stop` 훅으로 매번 제안하면 **사흘 안에 전원이 무시하게 된다.**
사내 배포 실패의 가장 흔한 원인이다.
주력은 주 1회 `/kb-review`다. 한 주를 모아 보면 반복 등장한 것이 보이고,
그게 진짜 지식화할 가치가 있는 것이다.

### 시드 노트를 동봉한다

빈 플러그인은 아무도 안 쓴다. 규칙보다 이게 채택률을 좌우한다.
48개를 넣었고, 사내 정의가 확인되지 않은 항목은 **일반 정의만 채우고 사내 정의는 TODO로 비워뒀다.**
추정으로 채우지 않았다.

## 세 플러그인 공통

### 버전은 푸시할 때 한 번만 올린다

한 세션에서 0.4.1 → 0.5.0 → 0.6.0을 만들었는데 **뒤의 둘은 푸시된 적이 없었다.**
아무도 설치할 수 없는 번호를 두 개 만든 셈이고, 번호가 무엇을 뜻하는지 알 수 없게 된다.

**버전은 편집 배치가 아니라 설치 가능한 상태를 가리킨다.**

| | 언제 | 예 |
|---|---|---|
| `0.x.0` minor | 설치자가 **다르게 써야 하는** 변화 | 단계 추가, 스펙 필드 추가, 필수 요건 변경, 에이전트·스크립트 신설 |
| `0.0.x` patch | 하던 대로 써도 되는 변화 | 문구 다듬기, 오탈자, 임계값 미세조정 |

같은 세션에서 열 번을 고쳐도 **푸시 전까지는 같은 번호**다. 푸시 직전에 한 번 정한다.
미푸시 번호가 이미 여러 개 쌓였으면 되돌려 하나로 합친다 — 건너뛴 번호를 남기지 않는다.

### 확인되지 않은 값은 추정으로 채우지 않는다

지표 정의, 임계값, 사내 기준처럼 확인이 필요한 값은 **빈칸 + TODO**로 남긴다.
추정값을 넣고 조용히 돌리면 틀린 보고서가 나가고, 틀렸다는 사실 자체를 아무도 모른다.
미확정 항목은 `docs/open-issues.md`에 모아 관리한다.

### 플러그인 간 경계

| 단계 | 담당 |
|---|---|
| 무엇을 볼지, 어떻게 해석할지, 어떻게 설명할지 | work-toolkit (`data-insight`, `make-visual`) |
| 차트·대시보드·보고서를 실제로 만들기 | report-maker |
| 알게 된 것을 노트로 남기기 | knowledge-notes |

`data-insight`와 `make-visual`은 렌더링 단계에서 report-maker로 인계한다.
report-maker가 설치되어 있지 않으면 표와 해석 문장까지만 내고 사용자에게 알린다.

### 스킬 description은 실제로 칠 법한 문장을 넓게 넣는다

진입 스킬(`work-helper`, `report-helper`)은 넓고 다소 밀어붙이는 톤으로 쓴다.
"차트로 보여줘", "이 엑셀 보고용으로 정리" 무엇이든 들어오게 한다.
나머지 스킬은 좁게 쓰되, 숙련 사용자가 직접 부르는 건 막지 않는다.
