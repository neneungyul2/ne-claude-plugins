# 정리하고 전달할 때

work-toolkit에서 가장 자주 쓰이는 영역이다.

## 0. 먼저 읽을 것

${CLAUDE_PLUGIN_ROOT}/references/output-rules.md — 공통 출력 규칙. 건너뛰지 않는다.

## 1. 상황 판별

| id | 이럴 때 |
|---|---|
| o-01 | 받은 지시·요청이 애매해서 뭘 만들어야 하는지부터 확인해야 한다 |
| o-02 | 긴 이메일에서 답할 내용과 확인할 부분을 구분하기 어렵다 |
| o-03 | 회의는 끝났는데 무엇이 결정됐고 누가 할 일인지 모르겠다 |
| o-04 | 보고서를 썼는데 "그래서 결론이 뭔데?"라는 말을 들었다 |
| o-05 | 보고서는 완성했는데 구두 보고가 막막하다 |
| o-06 | 실수나 일정 지연이 생겨 어떻게 보고할지 난감하다 |
| o-07 | 피드백을 받았는데 무엇부터 고쳐야 할지 모르겠다 |
| o-08 | 버그·장애·이슈가 터져 재현·원인·대응을 정리해 공유해야 한다 |
| o-09 | 상사·타 부서에 진행 상황이나 지원 필요 사항을 보고해야 한다 |
| o-10 | 핸드오프가 계속 반려되어 완료 기준(DoD)과 리뷰 규칙을 맞춰야 한다 |
| o-11 | 내가 한 일의 성과를 근거와 함께 정리해 공유해야 한다 |

헷갈리기 쉬운 구분

- o-04는 **문서 자체를 고치는 것**, o-09는 **상황을 전달하는 것**이다.
- o-06(실수·지연)은 신뢰가 걸린 자기 보고, o-08(장애)은 시스템 이슈 공유다. 톤이 다르다.

## 2. 절차

1. 위 표에서 맞는 id를 고른다. 겹치면 짧게 되물어 확정한다.
2. `${CLAUDE_PLUGIN_ROOT}/references/situations/organize-deliver/<id>.md` 를 Read 도구로 읽는다.
3. 그 문서의 지침을 그대로 따른다.
4. **표에 없으면** 억지로 끼우지 말고 아래 3장의 공통 원칙으로 처리한다.

## 3. 이 영역의 공통 원칙

- **결론이 맨 위다.** 배경부터 시작하지 않는다.
- **확정과 미확정을 구분한다.** 아직 정해지지 않은 것을 정해진 것처럼 쓰지 않는다.
- **읽는 사람이 바로 답할 수 있게 쓴다.** 질문은 선택형으로, 요청은 무엇을 언제까지인지 명시해서.
- **책임을 사람에게 돌리는 표현을 쓰지 않는다.** 무슨 일이 있었는지를 쓴다.
- 원문에 없는 사실·수치를 추가하지 않는다. 빠진 건 `확인 필요`로 남긴다.
- 메신저용과 메일용이 모두 필요하면 둘 다 만든다. 메일에는 제목을 붙인다.
