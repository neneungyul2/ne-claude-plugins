# CASE 1. 요구 사항 변경 → 우선순위 재정렬

## 상황
일정은 고정된 채 요구 사항이 추가·삭제·수정되어, 무엇을 먼저 처리할지 기준을 다시 세워야 한다.

## 먼저 확인할 정보 (대화에서 이미 아는 항목은 재질문하지 말 것)
1. 과제/기능 정의 — 지금 다루는 과제를 한 줄로
2. 현재 요구 사항(기준선) — 변경 전 상태
3. 변경 내용 — 추가/삭제/수정으로 구분
4. 변경 이유·배경
5. 요청자와 승인 라인
6. 최종 일정과 중간 마일스톤
7. 영향 범위 — 일정/품질/리소스/의존성
8. 우선순위 판단 기준
9. 수용 가능한 대안(MVP/단계적 반영/범위 축소/기한 조정 등)
10. 산출물 형태와 톤(표/요약/결정요청, 명확/중립/실행중심 등)

빠진 항목 중 우선순위 판단에 꼭 필요한 것(변경 이유, 일정, 우선순위 기준)만 골라 확인한다.

## 만들 수 있는 산출물 (사용자가 원하는 것에 맞춰 하나 선택 — 애매하면 물어본다)

### A. 변경 영향 분석 + 우선순위 재정렬
- 변경 사항 요약(추가/삭제/수정) 표 1개
- 영향 분석(일정/리소스/리스크/의존성) 5~8줄
- 우선순위 재정렬 리스트(TOP 5~10) + 근거
- "보류/제외/다음 단계"로 분류한 범위 제안
- 결정을 위해 확인이 필요한 질문 TOP 5

### B. 범위·일정 재합의 요청 메시지 (메신저/메일)
- 현 상황 요약 3줄(변경→영향→필요 결정)
- 옵션 2~3개(각: 장점/리스크/일정 영향)
- 추천 옵션 1개 + 이유(기준과 연결)
- 상대가 바로 답할 수 있는 선택형 질문 2개
- 메신저 버전 1개 + 메일 버전 1개(제목 포함)

### C. 변경 관리 운영체계 (변경 로그 + 결정 로그 + DoD)
- 변경 로그 템플릿(요청일/변경 내용/이유/영향/승인/상태)
- 결정 로그 템플릿(결정/근거/대안/오너/재검토 시점)
- 완료 기준(DoD) 체크리스트 10개(기능/문서/검수/공유 포함)
- 변경 수용 규칙 5개(즉시 반영 vs 다음 버전 이월 기준)
- 주간 체크인 메시지 템플릿 1개(변경/영향/요청/다음)
