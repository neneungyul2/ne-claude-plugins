# 기획하고 결정할 때

## 0. 먼저 읽을 것

${CLAUDE_PLUGIN_ROOT}/references/output-rules.md — 공통 출력 규칙. 건너뛰지 않는다.

## 1. 상황 판별

| id | 이럴 때 |
|---|---|
| p-01 | 아이디어는 있는데 무엇부터 실행해야 할지 모르겠다 |
| p-02 | 시장·경쟁 자료는 많은데 전략 기획서로 연결되지 않는다 |
| p-03 | 기능 아이디어는 있는데 PRD 첫 줄부터 막힌다 |
| p-04 | 개발자에게 요청했더니 확인 질문만 계속 돌아온다 |
| p-05 | 신사업 아이디어가 정말 돈이 될지 검토해야 한다 |
| p-06 | 여러 선택지 중 무엇을 고를지 판단 기준이 없다 |
| p-07 | 요구사항은 계속 늘어나는데 일정은 그대로다 (MVP 범위 정하기) |
| p-08 | 요구사항이 바뀌어 우선순위를 다시 정렬해야 한다 |
| p-09 | 일정이 밀리고 있어 작업을 다시 쪼개고 계획을 새로 짜야 한다 |

p-07과 p-08은 헷갈리기 쉽다. **무엇을 뺄지**가 문제면 p-07, **무엇을 먼저 할지**가 문제면 p-08이다.

## 2. 절차

1. 위 표에서 맞는 id를 고른다. 겹치면 짧게 되물어 확정한다.
2. `${CLAUDE_PLUGIN_ROOT}/references/situations/plan-decide/<id>.md` 를 Read 도구로 읽는다.
3. 그 문서의 지침을 그대로 따른다.
4. **표에 없으면** 억지로 끼우지 말고 아래 3장의 공통 원칙으로 처리한다.

## 3. 이 영역의 공통 원칙

- **가설과 확정을 구분한다.** 아직 검증되지 않은 것은 가설로 표시하고, 무엇을 확인하면 판별되는지 함께 쓴다.
- **정보가 부족하면 임의로 채우지 않는다.** 빠진 자리를 `확인 필요`로 두고 그게 왜 필요한지 적는다.
- **제약을 먼저 확정한다.** 일정·예산·인력·기술 제약을 모르면 계획이 아니라 희망이다.
- 계획에는 항상 **첫 행동**이 있어야 한다. "이번 주에 시작할 일 3개" 수준까지 내려간다.
- 결정을 다룰 때는 **추천안 하나와 그 근거**로 끝낸다. 선택지만 나열하고 끝내지 않는다.
- 되돌릴 수 있는 결정과 되돌릴 수 없는 결정을 구분해 검토 깊이를 달리한다.
