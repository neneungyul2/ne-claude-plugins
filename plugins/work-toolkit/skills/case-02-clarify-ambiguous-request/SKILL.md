# CASE 2. 애매한 요청 → 확인/정의

## 상황
요청이 "기존 자료 참고해서 ASAP" 수준으로만 전달돼, 자의로 해석해서 움직이면 나중에 다시 갈아엎을 위험이 크다. 먼저 확인부터 해야 한다.

## 먼저 확인할 정보
1. 요청 원문(또는 요약) 그대로
2. 요청 목적 — 왜 필요한지
3. 기대 산출물 — 형태·분량
4. 포함/제외 범위(가설이라도)
5. 성공 기준·품질 기준
6. 일정(확정/추정) + 중간 공유 시점
7. 필요한 자료·권한·제약
8. 요청자/실사용자/최종 승인자 구분
9. 현재 가장 불명확한 지점·리스크
10. 전달 채널(메신저/메일)과 톤

## 만들 수 있는 산출물

### A. 결정 질문 세트 (상사/요청자에게 확인)
- '결정이 필요한 질문' 5~7개(우선순위 포함, 선택지 A/B나 예시를 붙여 답하기 쉽게)
- '선호 확인 질문' 2~3개(톤/형식/깊이)
- "제가 이해한 요약" 2~3줄(Yes/No로 확인 가능하게)

### B. 요구 사항 정의서 (1페이지)
- 목표/비목표 각 5개 이내
- 요구 사항(필수/선택) 리스트 + 우선순위
- 수용 기준(DoD) 8~12개
- 일정(마감/중간 공유) + 의존성/리스크
- 확인 필요 항목(질문 형태) + 담당자/승인자 표기

### C. 확인 메시지 + 15분 미팅 아젠다
- 메신저 메시지 1개(요약→질문→결정 요청)
- 메일 버전 1개(제목 포함, 조금 더 공식)
- 15분 미팅 아젠다 3개(결정할 것 중심) + 준비 요청(자료 2개 이내)
- 일정 리스크를 압박처럼 보이지 않게 알리는 문장 1개
