# CASE 6. 이슈 재현·원인·대응 공유

## 상황
문제는 이미 터졌고 보고는 빨리 해야 하는데, 원인은 아직 특정되지 않았다. 발생 조건부터 사실 중심으로 정리해야 한다.

## 먼저 확인할 정보
1. 이슈 요약(핵심 증상 한 줄)
2. 발생 시점·환경·버전
3. 재현 절차와 빈도(재현 가능 여부)
4. 기대 결과 vs 실제 결과
5. 영향 범위(사용자/데이터/서비스)
6. 로그·증거(확인 경로)
7. 초기 원인 가설 — 추정과 확인된 사실 구분
8. 현재 임시 대응과 상태
9. 다음 액션과 담당자·기한(ETA)
10. 출력 형태(문서/메신저/메일)와 톤(사실 중심, 과장 금지)

과장하거나 근거 없이 원인을 확정 짓지 말 것 — 추정(가설)과 확인된 사실을 항상 구분해서 표현한다.

## 만들 수 있는 산출물

### A. 표준 버그/이슈 리포트
- 요약 3줄 + 심각도/우선순위 표기
- 재현 절차(번호 리스트) + 재현율
- 영향 범위(사용자/데이터/서비스) + 즉시 위험 요약
- 다음 액션 표(오너/기한/의존성) + 필요한 지원 요청

### B. 원인 분석 + 대응 방안(가설-검증-대응)
- 원인 가설 3~5개(확률/근거/검증 방법)
- 바로 할 검증 순서(최소 노력 → 최대 정보)
- 대응 플랜 A(근본 해결) / 플랜 B(완화) + 발동 트리거
- 재발 방지 항목(테스트/모니터링/체크리스트) 5~8개

### C. 상태 공지(메신저/메일)
- 메신저 공지 1개(상태/영향/조치/다음 업데이트)
- 메일 버전 1개(조금 더 공식, 제목 포함)
- "확정/미확정" 문장 템플릿 3개(불확실성 처리)
- 다음 업데이트 시점 문장 1개
