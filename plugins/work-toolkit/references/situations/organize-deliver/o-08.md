# o-08. 버그·장애·이슈가 터져 재현·원인·대응을 정리해 공유해야 할 때

## 이럴 때
문제는 이미 터졌고 보고는 빨리 해야 하는데 원인은 아직 특정되지 않았다.
발생 조건부터 **사실 중심**으로 정리한다.

## 먼저 확인할 것
- 이슈 요약 (핵심 증상 한 줄)
- 발생 시점·환경·버전
- 재현 절차와 빈도 (재현 가능 여부)
- 기대 결과 vs 실제 결과
- 영향 범위 (사용자·데이터·서비스)
- 로그·증거 확인 경로
- 초기 원인 가설
- 현재 임시 대응과 상태
- 다음 액션과 담당자·기한

## 진행
**과장하거나 근거 없이 원인을 확정하지 않는다.** 추정(가설)과 확인된 사실을 항상 구분한다.

## 출력 (아래 셋 중 하나)

### A. 표준 이슈 리포트
1. **요약** — 3줄 + 심각도·우선순위.
2. **재현 절차** — 번호 리스트 + 재현율.
3. **영향 범위** — 사용자·데이터·서비스 + 즉시 위험 요약.
4. **다음 액션** — 표(오너·기한·의존성) + 필요한 지원 요청.

### B. 원인 분석 + 대응 방안
1. **원인 가설** — 3~5개. 각각 확률·근거·검증 방법.
2. **검증 순서** — 최소 노력으로 최대 정보를 얻는 순서.
3. **대응 플랜** — A(근본 해결) / B(완화)와 발동 트리거.
4. **재발 방지** — 테스트·모니터링·체크리스트 5~8개.

### C. 상태 공지
1. **메신저 공지** — 상태·영향·조치·다음 업데이트.
2. **메일 버전** — 제목 포함, 조금 더 공식.
3. **불확실성 문장 템플릿** — 확정/미확정 표현 3개.
4. **다음 업데이트 시점** 한 문장.

## 주의
- 원인을 모를 때 "조사 중"이라고 쓰는 것은 정직한 보고다. 추측을 원인으로 적지 않는다.
- 다음 업데이트 시점을 반드시 명시한다. 그게 없으면 문의가 계속 온다.
