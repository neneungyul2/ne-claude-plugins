# p-03. 기능 아이디어는 있는데 PRD 첫 줄부터 막힐 때

## 이럴 때
말로는 설명되는데 문서로 쓰면 범위와 예외가 빠진다.
개발팀과 공유할 수 있는 **목적과 범위가 명확한 PRD**로 만든다.

## 먼저 확인할 것
- 기능 아이디어 (예: 교사용 일괄 주문)
- 해결할 문제·주요 사용자 (예: 반복 주문 이탈·단체 구매 담당 교사)
- 기대효과·지표 (예: 주문 완료율 상승)
- 제약·참고 자료 (예: 기존 API·출시 일정)

## 진행
세부 개발 방법부터 정하지 말고, **왜 필요한 기능인지와 무엇을 어디까지 만들 것인지**를 중심으로.
정보가 부족한 부분은 임의로 정하지 말고 '확인 질문'으로 분리한다.

## 출력
1. **PRD 요약** — 문제 정의, 목표, 사용자, 기대효과를 각각 한 문장으로.
2. **사용자 스토리** — '[사용자]는 [목적]을 위해 [행동]하고 싶다' 형식으로 핵심 스토리.
3. **기능 범위** — 이번 버전에 포함할 기능과 제외할 기능, 그렇게 판단한 이유.
4. **핵심 사용자 흐름** — 사용자가 기능에 진입해 목표를 달성하기까지를 단계별로. **세부 오류 처리보다 주요 분기**를 먼저.
5. **핵심 기능과 우선순위** — 사용자 가치와 목표 기여도 기준으로 필수·선택·추후 검토로 구분.
6. **성공 기준** — 이 기능이 문제를 해결했는지 판단할 사용자 행동과 성과 지표.
7. **확인 질문** — 개발·디자인을 시작하기 전에 결정해야 할 미확정 사항을 중요도순으로.

## 주의
- "나중에 정하자"는 항목이 확인 질문에 들어가야 한다. 문서에서 조용히 빠지면 개발 중에 터진다.
- 제외 기능을 쓰는 것이 포함 기능을 쓰는 것보다 중요하다.
