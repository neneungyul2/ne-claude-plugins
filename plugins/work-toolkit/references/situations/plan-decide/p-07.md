# p-07. 요구사항은 계속 늘어나는데 일정은 그대로일 때

## 이럴 때
전부 중요해 보이는 요구사항 앞에서 일정만 밀린다.
정해진 일정 안에 **핵심 가치를 검증할 최소 범위**를 정한다.

## 먼저 확인할 것
- 핵심 목표·가치 (이번에 반드시 검증할 것)
- 전체 요구사항 (들어온 것 전부)
- 일정·자원 (예: 2주·담당 2명)
- 대체 수단·제약 (수작업·기존 도구 활용 가능 여부)

## 진행
요구사항을 모두 넣으려 하지 말고, **정해진 일정 안에 핵심 가치를 검증하는 데 필요한 최소 범위**를 정한다.
이해관계자의 요청과 사용자 가치가 충돌하면 판단 기준을 명확히 설명한다.

## 출력
1. **목표 재정의** — 이번 일정 안에 반드시 검증해야 할 핵심 가설과 성공 기준을 한 문장씩.
2. **요구사항 분류** — 각 요구사항을 사용자 가치, 목표 기여도, 긴급성, 작업량, 의존성, 위험 기준으로 평가.
3. **최소 범위** — 반드시 포함 / 가능하면 포함 / 다음 단계로 연기 / 제외 네 그룹으로 나누고 이유를 표로.
4. **대체 방안** — 새로 만들지 않고 수작업, 기존 도구, 운영 정책으로 대체할 수 있는 기능과 방법.
5. **일정 제안** — 선행 작업과 의존성을 고려해 정해진 기간 안의 작업 순서, 담당 역할, 중간 확인 시점, 출시 기준.
6. **변경 대응 기준** — 새 요구사항이 추가될 때 넣을지 미룰지 판단할 질문 5개와,
   추가하려면 기존 범위에서 무엇을 빼야 하는지 결정하는 규칙.
7. **공유 문안** — 이해관계자에게 포함·제외 범위와 이유를 설명하는 짧은 안내문.

## 주의
- 6번(변경 대응 기준)이 이 문서의 핵심이다. 이게 없으면 다음 주에 같은 상황이 반복된다.
- "다 넣되 품질을 낮춘다"는 선택지는 대부분 최악이다. 범위를 줄인다.
