# p-04. 개발자에게 요청했더니 확인 질문만 계속 돌아올 때

## 이럴 때
"팝업 하나 띄워주세요" 수준의 요청이 오가며 말이 바뀐다.
바로 작업 가능한 **개발 티켓**으로 바꾼다.

## 먼저 확인할 것
- 요청 배경·목적 (예: 결제 이탈 감소)
- 사용자·작업 내용 (예: 미결제 고객 안내 팝업)
- 정상·예외 상황 (예: 노출 조건·미노출 조건)
- 일정·참고 자료 (예: 기존 화면·배포 일정)

## 진행
개발자가 다시 물어봐야 할 **모호한 표현을 찾아 구체화**한다.
정보가 부족한 항목은 임의로 채우지 말고 질문으로 남긴다.

## 출력
1. **티켓 제목** — 무엇을 왜 변경하는지 한눈에.
2. **배경과 목적** — 현재 문제, 변경 이유, 기대효과를 짧게.
3. **사용자 스토리** — '[사용자]는 [목적]을 위해 [행동]하고 싶다' 형식.
4. **상세 요구사항** — 노출 조건, 작동 방식, 입력·출력, 상태 변화, 권한, 데이터 연동 항목.
5. **정상·예외 케이스** — 정상 흐름과 함께 오류, 빈 값, 중복 행동, 취소, 권한 없음, 네트워크 실패 등을 표로.
6. **인수 조건** — 개발 완료 판단 기준을 '어떤 상황에서(Given) 무엇을 하면(When) 어떻게 된다(Then)' 형식으로.
7. **범위와 일정** — 포함·제외 범위, 선행 작업, 의존성, 희망 일정과 우선순위.
8. **확인 질문** — 작업 시작 전 기획자·개발자·디자이너가 합의해야 할 질문을 담당자별로.

## 주의
- 예외 케이스를 안 쓰면 개발자가 임의로 정한다. 그게 나중에 버그로 돌아온다.
- 인수 조건이 없으면 "완료"의 기준이 사람마다 다르다.
