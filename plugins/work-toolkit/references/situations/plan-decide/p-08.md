# p-08. 요구사항이 바뀌어 우선순위를 다시 정렬해야 할 때

## 이럴 때
일정은 고정인데 요구사항이 추가·삭제·수정되어 무엇을 먼저 할지 기준이 흔들린다.

## 먼저 확인할 것
- 과제 정의 (한 줄)
- 변경 전 기준선 — 원래 요구사항
- 변경 내용 — 추가·삭제·수정으로 구분
- 변경 이유와 요청자·승인 라인
- 최종 일정과 중간 마일스톤
- 영향 범위 — 일정·품질·리소스·의존성
- 우선순위 판단 기준
- 수용 가능한 대안 (단계적 반영·범위 축소·기한 조정)

빠진 항목 중 **변경 이유·일정·우선순위 기준**은 없으면 반드시 묻는다. 나머지는 추론해도 된다.

## 출력 (아래 셋 중 사용자가 원하는 것 하나. 불명확하면 한 줄씩 요약해 고르게 한다)

### A. 변경 영향 분석 + 우선순위 재정렬
1. **변경 사항 요약** — 추가·삭제·수정 표.
2. **영향 분석** — 일정·리소스·리스크·의존성을 5~8줄로.
3. **우선순위 재정렬** — 상위 5~10개와 각각의 근거.
4. **범위 제안** — 보류 / 제외 / 다음 단계로 분류.
5. **확인 질문** — 결정을 위해 필요한 질문 5개.

### B. 범위·일정 재합의 요청 메시지
1. **현 상황 요약** — 변경 → 영향 → 필요한 결정, 3줄.
2. **옵션** — 2~3개. 각각 장점·리스크·일정 영향.
3. **추천안** — 1개와 이유(우선순위 기준과 연결).
4. **선택형 질문** — 상대가 바로 답할 수 있는 것 2개.
5. **메신저 버전 / 메일 버전** — 메일에는 제목 포함.

### C. 변경 관리 운영체계
1. **변경 로그 템플릿** — 요청일·변경 내용·이유·영향·승인·상태.
2. **결정 로그 템플릿** — 결정·근거·대안·오너·재검토 시점.
3. **완료 기준 체크리스트** — 10개. 기능·문서·검수·공유 포함.
4. **변경 수용 규칙** — 5개. 즉시 반영 vs 다음 버전 이월 기준.
5. **주간 체크인 템플릿** — 변경·영향·요청·다음.

## 주의
- "무엇을 뺄지"가 문제라면 p-07(최소 범위 정하기)이 맞다.
- 우선순위 근거를 쓰지 않으면 다음 변경 때 또 처음부터 논쟁한다.
