# 지식 노트 규칙 (kb-conventions)

**이 문서가 규칙 원본이다.** 규칙이 바뀌면 여기부터 고치고 나머지 스킬이 참조하게 한다.
같은 규칙을 여러 SKILL.md에 복사하지 않는다.

아래 1~5는 **고정 규칙**이다. 사용자가 바꿀 수 없다. 이게 통일되지 않으면 나중에 노트를 합칠 수 없다.

---

## 1. 노트 타입 5종

| type | 역할 | 원자성 기준 |
|---|---|---|
| `term` | 용어 1개의 정의. 짧고, 인용당하는 쪽 | 제목 = 용어명 하나 |
| `concept` | 원리·메커니즘·인과. "왜/어떻게" | 제목 = 주장 한 문장 |
| `insight` | 우리 상황에 적용한 판단·경험 | 제목 = 결론 한 문장 |
| `source` | 문서·대화·아티클 출처 요약 | 원문 1개 = 노트 1개 |
| `moc` | 특정 영역의 진입점 지도 | 영역 1개 |

- `term`은 **정의만**, `concept`은 **설명만**, `insight`는 **내 판단만** 담는다.
- 경계가 섞이면 atomic이 깨진다. "재고회전율이 뭐고 우리는 왜 이걸 잘못 쓰고 있는가"는
  `term` 하나 + `insight` 하나다.

---

## 2. frontmatter 스키마

```yaml
---
type: term            # term | concept | insight | source | moc
aliases: [영문명, 약어]
domain: [S&OP, 재고]
status: seed          # seed → growing → stable
created: YYYY-MM-DD
schema: 1
---
```

- **`aliases`가 실질적으로 가장 중요하다.** 국·영문·약어를 섞어 쓰는 환경에서 alias가 없으면
  같은 개념이 별개 노트로 자란다. 떠오르는 표기를 모두 넣는다.
- **`schema: 1`은 반드시 넣는다.** 나중에 규칙이 바뀔 때 마이그레이션 대상을 찾는 유일한 단서다.
- `status`: `seed`(만들어만 둠) → `growing`(내용 붙는 중) → `stable`(안정)
- `domain`은 주제 태그다. 폴더가 아니라 이 필드로 주제를 처리한다.

---

## 3. 관계 어휘 6개 (추가·변경 금지)

Dataview 인라인 필드로 쓴다.

```markdown
상위:: [[재고관리]]
구성:: [[평균재고]], [[매출원가]]
선행:: [[안전재고]]        # 이걸 모르면 이해 안 되는 것
대조:: [[재고일수]]        # 혼동 주의
근거:: [[240612_S&OP 프레임워크 문서]]
적용:: [[품절 예측은 회전율만으로 판단하면 틀린다]]
```

| 어휘 | 뜻 |
|---|---|
| `상위::` | 이 노트가 속한 더 큰 개념 |
| `구성::` | 이 개념을 이루는 요소 |
| `선행::` | 이걸 모르면 이 노트가 이해되지 않는 것 |
| `대조::` | 비슷해서 혼동되는 것 |
| `근거::` | 출처 노트 |
| `적용::` | 이 지식을 적용한 판단(insight) |

**새 어휘를 만들지 않는다.** 6개로 표현이 안 되면 본문 문장으로 쓴다.

**본문 안에서 링크할 때는 왜 연결했는지 한 문장을 같이 쓴다.** 맥락 없는 링크는 반년 뒤 쓸모가 없다.

---

## 4. 원자성 판정

- 제목에 "그리고"가 들어가면 쪼갠다.
- 제목만 보고 내용이 예측되지 않으면 **제목이 잘못된 것이다.**
- 다른 노트에서 통째로 인용될 수 있는 최소 단위가 노트 1개다.
- `concept`·`insight`의 제목은 **문장**이다. 명사구면 아직 쪼개거나 다듬을 여지가 있다.

---

## 5. 용어 노트 표준 구조

```markdown
# 재고회전율

> 일정 기간 재고가 몇 번 팔려나갔는지 나타내는 비율.

## 산식
매출원가 ÷ 평균재고

## 사내 정의
- 우리 기준: (정의 · 산출 쿼리 위치 · 기준 수립 주체)
- 일반 정의와 다른 점:

## 혼동 주의
- [[재고일수]] — 역수 관계, 보고서에서 자주 뒤섞임

상위:: [[재고관리]]
```

`사내 정의` 섹션은 **필수**다. 지표 정의가 조직마다 다른 게 사내 지식화의 핵심 난점이다.

단, 개인 vault는 **해석과 적용**을 담는다. **정의의 단일 출처는 사내 문서**이므로
사내 문서를 참조만 하고 내용을 통째로 복사하지 않는다. 사내 문서가 바뀌면 복사본은 거짓이 된다.

아직 사내 정의를 모르면 **빈칸으로 두고 `TODO`를 남긴다.** 일반 정의로 채우지 않는다.

## 6. 폴더 체계 (기본값. 변경 가능)

```
000_inbox/        원문 투입, 미분해
100_terms/
200_concepts/
300_insights/
400_sources/
900_maps/
```

- 폴더는 **타입으로만** 나눈다.
- **주제별 폴더(영업/데이터/S&OP)를 만들지 않는다.** 한 노트가 두 곳에 속하는 문제가 반드시 생긴다.
  주제는 링크와 `domain` 필드로 처리한다.
- 사용자가 다른 번호 체계를 쓰면 그대로 따른다. 타입 분리 원칙만 유지한다.

---

## 7. 파일명

- `term` / `concept` / `insight`: 제목 그대로. 특수문자(`/ \ : * ? " < > |`)만 제거
- `source`: `YYMMDD_원문제목` (예: `260612_S&OP 프레임워크 문서`)
- `moc`: 영역명 (예: `재고관리 MOC`)

---

## 8. vault 경로 설정

사람마다 다르므로 스킬 본문에 경로를 박지 않는다.

1. `~/.knowledge-notes/config.json`을 읽는다.
2. 없으면 사용자에게 **한 번** 묻고 만든다.

```json
{
  "vault_path": "",
  "folders": {
    "inbox": "000_inbox",
    "term": "100_terms",
    "concept": "200_concepts",
    "insight": "300_insights",
    "source": "400_sources",
    "moc": "900_maps"
  },
  "language": "ko",
  "personal_tags": []
}
```

경로를 모른 채 노트를 만들지 않는다. 엉뚱한 곳에 쌓이면 되돌리기 어렵다.

---

## 9. 규칙을 바꿀 때

- 이 파일을 먼저 고친다.
- `schema` 번호를 올려야 하는 변경(frontmatter 구조 변경, 관계 어휘 변경)이면
  기존 노트 마이그레이션 계획을 함께 적는다.
- 플러그인 버전을 올리고 배포한다.
