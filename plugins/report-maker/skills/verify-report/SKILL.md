# 검수 (verify-report)

**만든 사람은 자기 산출물을 객관적으로 못 본다.** 무엇을 말하려 했는지 이미 알기 때문에,
화면에 안 적힌 것도 읽힌다고 착각한다. 그래서 검수는 만든 맥락이 없는 쪽이 한다.

report 모드에서는 건너뛸 수 없다. quick 모드는 1·2단계(스크립트)만 돌린다.

## 0. 순서

```
1) 소스 검사  check_html.py    ← 항상. 파일을 읽어서 판정
2) 렌더 검사  lint_render.py   ← 항상. 브라우저로 칠해보고 픽셀을 잼
3) 서브에이전트 검수             ← report 모드 필수. 판단이 필요한 것만
4) 고칠 것을 고친다              ← 여기서만 파일을 쓴다
5) 다시 1)~2)                  ← FAIL 0이 될 때까지
```

**1·2를 통과하기 전에 3으로 넘어가지 않는다.** 사람(서브에이전트)의 시간을
기계가 잡을 수 있는 것에 쓰지 않는다. 잘린 글자를 찾느라 눈을 쓰면
정작 "강조가 옳은 곳에 걸렸나"를 볼 여력이 없어진다.

## 1. 소스 검사 — 파일을 읽는다

```bash
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/check_html.py <산출물.html> --spec <report-spec.json>
```

의존성이 없다. 종료 코드 0이면 FAIL 없음, 1이면 있음.
`--json`은 기계용 출력, `--template`은 템플릿 자체를 볼 때의 모드다.

보는 것 — 외부 리소스, 자리표시자 잔존, 한국어 줄바꿈, 다크모드 분기,
**폰트 크기·라운드 종류 수**, **4px 그리드**, 토큰 밖 색, 기울어진 텍스트, 중앙정렬,
각주 4요소, **히어로 목록 개수 = exhibit 개수**, action_title 주장 수,
**본문 표 행 수**, 계열 수, **같은 숫자 반복**, 용어 등록.
`--spec`을 주면 스펙 대조 — action_title 일치, **`encoding.claim`이 위치·길이에 있는지**,
emphasis 부분 문자열, **`weight: primary` 개수**, **종류별 필수·해당없음**, 배경 모름이면 질문→그림→답 순서, 계산 방법 창의 실제 숫자.

## 2. 렌더 검사 — 실제로 칠해본다

```bash
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/lint_render.py <산출물.html>
```

소스로는 안 보이는 것을 잡는다. **잘린 글자·겹친 라벨·넘치는 폭은 그려봐야 안다.**

| | 본다 |
|---|---|
| 데스크톱 1280px | 글자 잘림, 가로 스크롤, viewBox 밖 라벨, 라벨 겹침 |
| 모바일 400px | 같은 항목 — 여기서 무너지는 리포트가 많다 |
| **폰트 폴백** | Pretendard가 없는 PC에서 라벨이 넘치는가 (WARN) |
| 차트 | 9px 미만 글자, **잉크 비율** (빈 공간이 너무 많은 차트) |
| 페이지 | JS 에러, 요청 실패 |

`--shot out.png`를 붙이면 전체 스크린샷을 남긴다. 3단계에서 그 그림을 쓴다.

**폰트 폴백이 WARN인 이유** — 우리는 폰트를 임베드하지 않는다. 만든 PC에서는 멀쩡하고
받는 PC에서 넘친다. 사내 배포라면 고치는 쪽이 맞다.

playwright가 없으면 종료 코드 2와 설치 안내가 나온다. **조용히 통과하지 않는다.**
설치할 수 없는 환경이면 3단계의 눈 검사를 반드시 돈다.

## 3. 서브에이전트 검수

Agent 도구로 `report-verifier`를 호출한다.

**넘기는 것은 파일 경로뿐이다.**

```
산출물:  <절대경로>.html
브리프:  <절대경로>/report-brief.json
스펙:    <절대경로>/report-spec.json
```

**넘기지 않는 것 — 이게 핵심이다.**

- 왜 이 차트를 골랐는지
- 어떤 것을 고민하다 이렇게 했는지
- 어디를 특히 봐 달라는 요청
- "○○는 의도한 것이다"라는 해명

전부 검수자의 눈을 흐린다. **맥락을 주는 순간 서브에이전트로 돌리는 의미가 없어진다.**
검수자는 "만든 사람이 설명해야 알 수 있는 것"을 찾는 사람이고,
그건 곧 독자도 모른다는 뜻이다.

`report-verifier`가 하는 것 — 스크린샷을 직접 보고 ①눈이 먼저 가는 곳 ②위계
③읽힘 ④차트를 확인한 뒤, 산출물만 보고 각 섹션 요점을 적어 `brief.questions`와 대조한다.

## 3-1a. 탐색형이면 검수 자체가 다르다

`references/report-types.md`에서 탐색형으로 판정된 산출물(`build-explore`의 결과물)은
**결론을 검사하지 않는다.** `key_takeaway`·`action_title`·`weight: primary`가 없으니
1~3장의 스펙 대조 항목(수평 논리, emphasis, primary 개수) 대부분이 해당 없음이다.

대신 확인하는 것 — **축 조합을 바꿔도 화면이 안 깨지는가.**

- `check_html.py`·`lint_render.py`는 구조 검사(외부 리소스·자리표시자·한국어 줄바꿈·
  4px 그리드·토큰 밖 색·기울어진 텍스트)에는 그대로 쓴다. **`--spec`으로 결론 대조는
  하지 않는다** — explore-spec.json에는 그 필드들이 없다
- 최소 3개 축 조합(기본값, 데이터가 가장 많은 극단값, 데이터가 적거나 없는 값)으로
  각각 스크린샷을 찍어 본다. 값이 안 나오는 조합에서 **"볼 수 없음"이 표시되는지,
  빈 화면이나 NaN·undefined가 새어나오는지**를 확인한다
- 기타 드릴다운이 축을 바꿔도 다시 계산되는지 — 열어서 값을 보고, 축을 하나 바꾼 뒤
  다시 열어 값이 달라졌는지 확인한다
- 위계·이동: `sections`가 있으면 목차를 접어도 현재 섹션이 강조되고 조건 바에 현재 위치가
  보이는지, 계층 드릴다운을 끝까지 내려갔다 올라와도 값이 맞는지 본다
- 읽는 양: 패널 위에 줄글이 남아 있지 않은지, ⓘ를 누르면 사용법·기준이 열리는지,
  첫 비교가 금액·부수 같은 원래 단위이고 비교군이 보이는지 본다
- 서브에이전트 검수는 report와 같은 방식으로 부르되, 넘기는 프롬프트만 다르게 한다 —
  "역스토리보딩으로 questions와 대조"가 아니라 **"각 축을 하나씩 바꿔보고 패널이
  갱신되는지, 조합을 섞어도 화면이 깨지지 않는지"**를 확인해 달라고 요청한다

> `check_html.py`는 explore-spec을 인식하지 못한다. `--spec` 없이 구조 검사만 돌린다.
> 이때 나오는 결정·진단형 전용 WARN(히어로 요약·`action_title` 서술형)은 탐색형에 해당 없다.

## 3-1. 종류에 맞는 검수인가 (결정·진단·점검·조망)

`report-types.md` §3의 표가 **무엇이 필수인지**를 바꾼다. 검수도 그 표를 따른다.

- 점검형에 액션이 없다고 지적하지 않는다. **정상이면 0개가 정답이다**
- 점검형·조망형에 긴장이나 3분 스토리가 없다고 지적하지 않는다. 해당 없음이다
- 반대로 **점검형인데 데이터 시점이 화면 상단에 없으면 그건 고장이다.**
  다시 여는 화면에서 먼저 확인할 것은 값이 아니라 신선도다
- 결정형에 "왜 나머지가 아닌가"가 없으면 반드시 고칠 것으로 올린다.
  검증할 수 없는 권고는 승인되지 않는다
- **조망형에 판단 문장("~해야 한다", "대응이 필요하다")이 있으면 고칠 것으로 올린다.**
  조망형은 관찰로 쓴다. 단계마다 경로와 전체 대비 비중이 보이는지도 본다
- **독자 배경이 `new`인데** 맨 위에 답이 먼저 오거나 전체 그림이 없으면 고칠 것으로 올린다.
  처음 보는 사람이 첫 화면만 보고 전체 규모를 알 수 있는지 본다

## 3-2. 계산을 따라 할 수 있는가 — 모든 종류

계산 방법 창(ⓘ)을 하나씩 열어 본다. **처음 보는 사람이 창 안의 계산을 계산기로 그대로
따라 해서 화면의 숫자를 얻을 수 있는가.**

- `check_html.py`는 창에 숫자와 `=`가 있는지만 본다 (`c_calc_worked`). 따라 할 만큼 쉬운지는 여기서 본다
- 계수·지수가 이름으로만 나오면("계절지수 1.3") 뜻으로 바꾸라고 올린다("평소 달보다 1.3배")
- 단계가 셋을 넘거나 예외 조건이 여럿이면 **계산을 줄이라고** 올린다. 설명을 늘리라고 하지 않는다
- 첫 화면의 숫자가 지수·비율로 시작하면 원래 단위(부수·금액·%)로 바꾸라고 올린다

## 3-3. 단락·배치·편집이 동작하는가 — HTML

- 목차(사이드바·메뉴)의 라벨이 짧고, 눌렀을 때 그 단락으로 가는가
- 편집을 켜서 글 하나를 고치고, 단락 하나를 옮기고, 저장 → 다시 열었을 때 그대로인가
  (로컬 파일이면 내려받은 파일로 확인한다)
- 화면에 늘 보이는 글이 결론·숫자·출처 한 줄뿐인가. 용어 뜻·가정·계산 설명이 본문에
  줄글로 쌓여 있으면 툴팁·창으로 빼라고 올린다

## 4. 받은 것을 처리한다

| 검수 결과 | 한다 |
|---|---|
| 스크립트 FAIL | 전부 고친다. 예외 없다 |
| 폰트 폴백 WARN | 사내 배포면 고친다. 라벨을 줄이거나 마진을 넓힌다 |
| "반드시 고칠 것" | 고친다. 안 고칠 거면 **왜 안 고치는지 사용자에게 말한다** |
| "판단이 필요한 것" | 판단해서 고치거나, `open_questions`로 올린다 |

**결론이 바뀌어야 하는 지적이면 `plan-report`로 되돌아간다.** 화면만 고쳐서 덮지 않는다.
축 선택이나 인코딩이 틀렸다는 지적은 대개 여기에 해당한다.

검수자의 지적에 동의하지 않을 수 있다. 그럴 때 **"의도한 것"이라고 넘기지 말고,
그 의도가 화면에 글자로 있는지 본다.** 없으면 검수자가 맞다.

## 5. 다시 돌린다

고친 뒤 **본문을 다시 조립하고** 1·2단계를 다시 돌린다.

```bash
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/assemble.py <이름>.content.html -o <이름>.html
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/check_html.py <이름>.html --spec <스펙>
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/lint_render.py <이름>.html --quick
```

**표현만 고쳤으면 `--quick`을 쓴다** — 데스크톱 1회만 돈다. 모바일·폰트 폴백은
레이아웃이 바뀌었을 때만 의미가 있다.

3단계는 **구조나 결론이 바뀌었을 때만** 다시 부른다.
라벨 위치를 옮긴 정도면 부르지 않는다 — 검수자가 볼 것이 바뀌지 않았다.

**전달 직전에는 `--quick` 없이 한 번 전부 돌린다.**

## 6. 전달

- 소스 검사·렌더 검사 FAIL 0
- "반드시 고칠 것" 0건 또는 **안 고친 이유를 사용자에게 밝힘**

둘 다 만족하면 전달한다. 사용자에게는 **무엇을 검수했고 무엇이 남았는지** 한두 줄로 전한다.
검수 과정을 늘어놓지 않는다.

## 7. 이 단계에서 하지 않는 것

- 검수자에게 맥락 주기
- 검수자가 직접 고치게 하기 — **발견과 수정은 분리한다.** 고치기 시작하면 눈이 흐려진다
- 지적을 다 올리기 — 심각도 순으로 자르는 것이 검수자의 일이다
- 통과했다고 좋은 점 나열하기
