# 검수 (verify-report)

**만든 사람은 자기 산출물을 객관적으로 못 본다.** 무엇을 말하려 했는지 이미 알기 때문에,
화면에 안 적힌 것도 읽힌다고 착각한다. 그래서 검수는 만든 맥락이 없는 쪽이 한다.

report 모드에서는 건너뛸 수 없다. quick 모드는 1·2단계(스크립트)만 돌린다.

## 0. 순서

```
1) 소스 검사  check_html.py    ← 항상. 파일을 읽어서 판정
2) 렌더 검사  lint_render.py   ← 항상. 브라우저로 칠해보고 픽셀을 잼
3) 서브에이전트 검수             ← report 모드 필수. 판단이 필요한 것만
4) 고칠 것을 고친다              ← 여기서만 파일을 쓴다
5) 다시 1)~2)                  ← FAIL 0이 될 때까지
```

**1·2를 통과하기 전에 3으로 넘어가지 않는다.** 사람(서브에이전트)의 시간을
기계가 잡을 수 있는 것에 쓰지 않는다. 잘린 글자를 찾느라 눈을 쓰면
정작 "강조가 옳은 곳에 걸렸나"를 볼 여력이 없어진다.

---

## 1. 소스 검사 — 파일을 읽는다

```bash
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/check_html.py <산출물.html> --spec <report-spec.json>
```

의존성이 없다. 종료 코드 0이면 FAIL 없음, 1이면 있음.
`--json`은 기계용 출력, `--template`은 템플릿 자체를 볼 때의 모드다.

보는 것 — 외부 리소스, 자리표시자 잔존, 한국어 줄바꿈, 다크모드 분기,
**폰트 크기·라운드 종류 수**, **4px 그리드**, 토큰 밖 색, 기울어진 텍스트, 중앙정렬,
각주 4요소, **히어로 목록 개수 = exhibit 개수**, action_title 주장 수,
**본문 표 행 수**, 계열 수, **같은 숫자 반복**, 용어 등록.
`--spec`을 주면 스펙 대조 — action_title 일치, **`encoding.claim`이 위치·길이에 있는지**,
emphasis 부분 문자열, **`weight: primary` 개수**, **유형별 필수·해당없음**.

## 2. 렌더 검사 — 실제로 칠해본다

```bash
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/lint_render.py <산출물.html>
```

소스로는 안 보이는 것을 잡는다. **잘린 글자·겹친 라벨·넘치는 폭은 그려봐야 안다.**

| | 본다 |
|---|---|
| 데스크톱 1280px | 글자 잘림, 가로 스크롤, viewBox 밖 라벨, 라벨 겹침 |
| 모바일 400px | 같은 항목 — 여기서 무너지는 리포트가 많다 |
| **폰트 폴백** | Pretendard가 없는 PC에서 라벨이 넘치는가 (WARN) |
| 차트 | 9px 미만 글자, **잉크 비율** (빈 공간이 너무 많은 차트) |
| 페이지 | JS 에러, 요청 실패 |

`--shot out.png`를 붙이면 전체 스크린샷을 남긴다. 3단계에서 그 그림을 쓴다.

**폰트 폴백이 WARN인 이유** — 우리는 폰트를 임베드하지 않는다. 만든 PC에서는 멀쩡하고
받는 PC에서 넘친다. 사내 배포라면 고치는 쪽이 맞다.

playwright가 없으면 종료 코드 2와 설치 안내가 나온다. **조용히 통과하지 않는다.**
설치할 수 없는 환경이면 3단계의 눈 검사를 반드시 돈다.

## 3. 서브에이전트 검수

Agent 도구로 `report-verifier`를 호출한다.

**넘기는 것은 파일 경로뿐이다.**

```
산출물:  <절대경로>.html
브리프:  <절대경로>/report-brief.json
스펙:    <절대경로>/report-spec.json
```

**넘기지 않는 것 — 이게 핵심이다.**

- 왜 이 차트를 골랐는지
- 어떤 것을 고민하다 이렇게 했는지
- 어디를 특히 봐 달라는 요청
- "○○는 의도한 것이다"라는 해명

전부 검수자의 눈을 흐린다. **맥락을 주는 순간 서브에이전트로 돌리는 의미가 없어진다.**
검수자는 "만든 사람이 설명해야 알 수 있는 것"을 찾는 사람이고,
그건 곧 독자도 모른다는 뜻이다.

`report-verifier`가 하는 것 — 스크린샷을 직접 보고 ①눈이 먼저 가는 곳 ②위계
③읽힘 ④차트를 확인한 뒤, 산출물만 보고 각 섹션 요점을 적어 `brief.questions`와 대조한다.

## 3-1. 유형에 맞는 검수인가

`report-types.md` §3의 표가 **무엇이 필수인지**를 바꾼다. 검수도 그 표를 따른다.

- 감시형에 액션이 없다고 지적하지 않는다. **정상이면 0개가 정답이다**
- 감시형에 긴장이나 3분 스토리가 없다고 지적하지 않는다. 해당 없음이다
- 반대로 **감시·추적형인데 데이터 시점이 화면 상단에 없으면 그건 고장이다.**
  다시 여는 화면에서 먼저 확인할 것은 값이 아니라 신선도다
- 선택형에 "왜 나머지가 아닌가"가 없으면 반드시 고칠 것으로 올린다.
  검증할 수 없는 추천은 승인되지 않는다

## 4. 받은 것을 처리한다

| 검수 결과 | 한다 |
|---|---|
| 스크립트 FAIL | 전부 고친다. 예외 없다 |
| 폰트 폴백 WARN | 사내 배포면 고친다. 라벨을 줄이거나 마진을 넓힌다 |
| "반드시 고칠 것" | 고친다. 안 고칠 거면 **왜 안 고치는지 사용자에게 말한다** |
| "판단이 필요한 것" | 판단해서 고치거나, `open_questions`로 올린다 |

**결론이 바뀌어야 하는 지적이면 `plan-report`로 되돌아간다.** 화면만 고쳐서 덮지 않는다.
축 선택이나 인코딩이 틀렸다는 지적은 대개 여기에 해당한다.

검수자의 지적에 동의하지 않을 수 있다. 그럴 때 **"의도한 것"이라고 넘기지 말고,
그 의도가 화면에 글자로 있는지 본다.** 없으면 검수자가 맞다.

## 5. 다시 돌린다

고친 뒤 1·2단계를 다시 돌린다 — 둘 다 빠르다.
3단계는 **구조나 결론이 바뀌었을 때만** 다시 부른다
(라벨 위치를 옮긴 정도면 다시 부르지 않는다).

## 6. 전달

- 소스 검사·렌더 검사 FAIL 0
- "반드시 고칠 것" 0건 또는 **안 고친 이유를 사용자에게 밝힘**

둘 다 만족하면 전달한다. 사용자에게는 **무엇을 검수했고 무엇이 남았는지** 한두 줄로 전한다.
검수 과정을 늘어놓지 않는다.

## 7. 이 단계에서 하지 않는 것

- 검수자에게 맥락 주기
- 검수자가 직접 고치게 하기 — **발견과 수정은 분리한다.** 고치기 시작하면 눈이 흐려진다
- 지적을 다 올리기 — 심각도 순으로 자르는 것이 검수자의 일이다
- 통과했다고 좋은 점 나열하기
