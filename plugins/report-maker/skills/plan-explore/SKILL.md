# 탐색 구성 확정 (plan-explore)

`plan-report`와 같은 자리지만 확정하는 것이 다르다. **결론을 확정하지 않는다.**
축·패널·그레인·기본값을 확정한다 — 독자가 무엇을 볼지는 화면을 여는 사람이 그때 정한다.

## 0. 먼저 읽을 것

작업 폴더의 `explore-brief.json`을 먼저 읽는다. **여기서 축을 바꾸지 않는다.**
바뀌어야 하면 `frame-explore`로 되돌아간다.

- `${CLAUDE_PLUGIN_ROOT}/references/explore-model.md` — **필수.** 그레인·축·패널 카탈로그
- `${CLAUDE_PLUGIN_ROOT}/skills/plan-explore/references/explore-spec-schema.md` — 스펙 규격
- `${CLAUDE_PLUGIN_ROOT}/references/chart-rules.md` — 패널 안 차트 선택·금칙은 그대로 적용
- `${CLAUDE_PLUGIN_ROOT}/references/design-rules.md` — 배치·타이포·색 원칙은 그대로 적용
- `${CLAUDE_PLUGIN_ROOT}/references/metrics.md` — glossary 원본

## 1. 순서

0. **계열을 재확인한다.** 데이터를 보고도 여전히 탐색형인가. 축을 실제로 다 못 쓰게
   되는 데이터라면(그레인 부족) `frame-explore`로 되돌아가 축을 줄인다.
1. **그레인을 실제로 확인한다.** `explore-brief.grain`대로 원자료가 쪼개져 있는지
   실측한다. 부족하면 되돌아간다 — `plan-report`에서 "데이터에서 답을 찾는다"와 같다.
2. **축마다 기본값을 확정한다.** 처음 여는 화면이 가장 무거운 조합이 되지 않게 한다.
3. **패널을 확정한다.** `explore-brief.panels` 후보를 실제 데이터로 채울 수 있는지
   본다. 채울 수 없는 패널은 빼거나 축을 다시 조정한다.
4. **패널 배치를 설계한다.** 아래 2장. 패널이 여러 주제로 갈리면 `sections`로 묶는다. 탐색형에도 서열은 있다 — KPI가 항상 위,
   상세 표는 항상 아래. 다만 `weight: primary`처럼 결론을 만드는 자리는 없다.
5. **차트를 고른다.** 패널 유형별로 `chart-rules.md` 매핑표를 그대로 따른다.
   금칙 차트(파이·3D·이중Y축·잘린축·무지개팔레트)도 동일하게 적용된다.
6. **드릴다운 방식을 정한다.** 분류에 위계가 있으면 `hierarchy`(계층 드릴다운·트리 표),
   없으면 기타(etc) 드릴다운. 3장 참고.
6-1. **비교군과 단위를 정한다.** `compare` 축의 `groups`(여럿이면 전부 함께 그린다), 패널의 `units`. 원래 단위가 먼저다.
6-2. **글을 나눈다.** 사용법은 `guide`, 기준·비고는 `notes`로 빼서 ⓘ 뒤에 둔다. 패널 위에는
   이름·숫자 칩만 남긴다 (`explore-model.md` §7).
7. **용어와 산식을 훑는다.** 4장.
8. **스펙 JSON을 쓴다.**
9. **자체 검사를 돌린다.**

## 2. 패널 배치

`plan-report` 2-1장과 같은 이유로 필요하다 — 설계하지 않으면 렌더러가 패널을
전부 같은 크기로 깐다. 다만 판정 기준이 다르다.

| | plan-report (보고형) | plan-explore (탐색형) |
|---|---|---|
| 가장 큰 자리 | `weight: primary` 결론 exhibit | KPI 카드 행. 항상 최상단 |
| 서열의 근거 | 어느 것이 결론을 만드는가 | 어느 것을 가장 먼저 확인해야 하는가 |
| 강조 예산 10% | 그대로 적용 — 단, 강조 대상은 "이번 조합에서 임계값을 넘은 값" 같은
  **화면이 계산해서 정하는 것**이다. 저자가 미리 어떤 값을 강조할지 정하지 않는다 |

패널 순서는 개요(KPI) → 추이(trend) → 구성(mix) → 위치(map) → 상세(table) 순이
기본이다. `sections`를 쓰면 섹션 순서가 이 흐름을 따르고, 섹션 안에서는 원래 단위 비교 →
증감률·지수 순으로 둔다. 독자가 큰 그림을 먼저 보고 세부로 내려가게 한다 — cascading은 탐색형에도
적용된다. 다만 "제일 큰 얘기가 먼저 나오나"(자체검사 ②)는 **결론의 순서**를 묻는
질문이라 탐색형에는 해당 없음이다. 이건 **화면 배치의 순서**일 뿐이다.

## 3. 드릴다운

### 계층 드릴다운 (분류에 위계가 있을 때)

대분류 > 중분류 > 소분류처럼 위계가 있으면 한 목록에 펼치지 않는다. `hierarchy`에
상위→하위 차원을 적고, 구성 패널은 행을 눌러 한 단계씩 내려가게, 표는 `tree_table`로
▸를 펴게 한다. 이때는 "기타"로 묶지 않는다 — 각 단계의 모든 항목을 상위 분류 안의
비중으로 보여준다. 아주 작은 항목(세 대상 모두 1% 미만 등)만 줄이고, 줄였다는 사실을 표시한다.

### 기타(etc) 드릴다운 (위계가 없을 때)

`plan-report`의 `group_detail`과 같은 역할을 한다 — 묶은 건 반드시 열어볼 수 있어야
한다. 다른 점은 탐색형에서는 **드릴다운도 필터에 반응해야** 한다는 것이다. 부문을
바꾸면 "기타"에 묶인 항목의 구성도 다시 계산돼야 한다 — 렌더 시점에 고정한 목록을
그대로 두면 필터를 바꿔도 기타의 내용이 안 바뀌는 버그가 된다.

상위 N을 정하는 기준(`explore-model.md` §3)을 스펙에 명시한다. "5개만" 같은 임의
숫자를 쓰려면 왜 5인지 — 누적 비중 몇 %인지 — 를 같이 적는다.

## 4. 용어와 산식

`plan-report` 4장과 규칙이 같다. `glossary`는 `metrics.md`에서 가져오고,
**쉬운 말이 먼저 온다** — desc는 쉬운 말 한 줄로 시작하고 정확한 산식은 그 뒤에 붙인다.
한 문장을 넘는 산식은 `calcs` 모달로 뺀다. 모달 소개문(`calcs.scope`)도 "얘기 하나만"
규칙을 통과해야 한다 — `plan-report` 2장, `chart-rules.md` §7과 동일하다.

## 5. 자체 검사

- [ ] `explore-brief.axes`의 모든 축이 스펙의 `axes`에 있고, 각각 `default`가 있는가
- [ ] 확정된 축 조합보다 그레인이 같거나 세밀한가 (실측했는가, 눈대중이 아닌가)
- [ ] **모든 패널 제목이 "이것만 봐도 무엇을 보여주는지 알 수 있나"를 통과하는가**
      (자체검사 ①). "요약"·"현황"처럼 무엇의 요약인지 없는 제목은 반려
- [ ] 패널마다 반응하는 축(`axes_used`)이 명시돼 있는가
- [ ] `action_title`·`key_takeaway`·`weight: primary`를 억지로 채우려 하지 않았는가
      — 이 필드들은 탐색형 스펙에 **존재하지 않는다**
- [ ] KPI 패널이 최상단에 있는가
- [ ] 금칙 차트가 없는가 (`chart-rules.md`)
- [ ] 기타 드릴다운마다 상위 N을 정한 근거가 있고, 필터에 반응하는가
- [ ] 위계가 있는 분류를 한 목록에 flat하게 펼치지 않았는가 (`hierarchy`)
- [ ] 비교가 있는 화면에 비교군이 있는가, 첫 비교가 원래 단위(금액·부수)인가
- [ ] 패널 위에 줄글이 없는가 — 사용법·기준은 `guide`·`notes`로 빠져 있는가
- [ ] `sections`를 썼다면 모든 패널에 `section`이 있는가
- [ ] 본문·라벨의 축약어·사내 용어가 모두 `glossary`에 있고, 쉬운 말이 먼저인가
- [ ] 한 문장으로 안 되는 계산이 `calcs`로 빠져 있는가
- [ ] `out_of_scope`가 `explore-brief`와 일치하는가 — 그레인이 못 받치는 조합이 화면에서
      "볼 수 없음"으로 표시되는가 (추정치로 채워지지 않았는가)
- [ ] 파일 크기가 관리 가능한 수준인가 (`explore-model.md` §5)

체크리스트가 실패로 늘어나면 이 장에 항목을 계속 추가하지 않는다. **①번 질문
("이것만 봐도 알 수 있나")으로 되돌아가 왜 실패했는지를 다시 판단한다.**

## 6. 하지 않는 것

- `action_title`·`key_takeaway.ask`·`weight`를 채우려 하지 않는다 — 없는 개념이다
- 저자가 미리 어떤 값을 강조할지 정하지 않는다. 강조는 화면이 조합을 보고 계산한다
- 드릴다운 목록을 렌더 시점에 고정하지 않는다 — 필터가 바뀌면 같이 바뀌어야 한다
- 그레인이 못 받치는 조합을 추정으로 채우지 않는다
- 결론(so_what)을 쓰려 하지 않는다. 탐색형은 결론을 내미는 산출물이 아니다
