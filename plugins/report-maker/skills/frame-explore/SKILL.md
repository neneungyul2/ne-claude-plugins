# 축 설계 (frame-explore)

**데이터를 열기 전에 돈다.** `frame-question`과 같은 이유다 — 다만 여기서 합의하는 건
"무엇을 답할 것인가"가 아니라 **"독자가 무엇을 스스로 바꿔볼 수 있어야 하는가"**다.
이걸 정하지 않으면 있는 컬럼을 전부 필터로 붙이게 되고, 다 만든 뒤에 아무도 안 쓰는
필터와 정작 필요한 필터가 안 보이는 화면이 남는다.

이 스킬로 왔다는 것 자체가 `references/product-lines.md` §1에서 **탐색형**으로 판정됐다는
뜻이다. 아직 판정하지 않았다면 여기가 아니라 `report-helper`로 돌아간다.

## 0. 먼저 읽을 것

- `${CLAUDE_PLUGIN_ROOT}/references/product-lines.md` — **필수.** 왜 이 파이프라인이 따로 있는지
- `${CLAUDE_PLUGIN_ROOT}/references/explore-model.md` — **필수.** 데이터 그레인 규칙, 축·패널 유형 카탈로그
- `${CLAUDE_PLUGIN_ROOT}/references/storytelling.md` §1 — 참고. 탐색/설명의 원래 구분

데이터는 아직 열지 않는다. **구조만 훑는다** — 어떤 컬럼이 있는지, 값의 범위가 어떤지
정도만. 실제 값을 보고 축을 정하면 "지금 있는 데이터로 필터를 몇 개 만들 수 있나"로
설계가 끌려간다. 축은 **독자가 무엇을 알고 싶어하는가**에서 나와야 한다.

**화면부터 만들지 않는다.** `frame-question`과 같다. 이 단계는 글자로만 한다.

---

## 1. 진행 방식

```
1) 상황 파악  →  2) 계열 재확인  →  3) 축 후보 제시
→ 4) 데이터 그레인 확정  →  5) 패널 후보 제시  →  6) 범위 명시  →  7) 브리프 확정
```

---

## 2. 상황 파악

- 무엇에 대한 대시보드인가
- **왜 고정 리포트로 안 되고 탐색이 필요한가** — 이 답이 흐리면 실은 설명형일 수 있다
- 누가, 얼마나 자주 여나
- 지금은 어떻게 보고 있나 — 엑셀에서 매번 필터링해서 본다면, 그 필터가 축 후보다

"왜 고정 리포트로 안 되나"가 가장 중요하다. 답이 "매번 보는 조합이 똑같다"면
그건 탐색형이 아니라 감시형(watch) 리포트다 — `frame-question`으로 보낸다.

---

## 2-1. 계열 재확인 — 감시형과 다시 한번 가른다

`product-lines.md` §1의 표를 다시 대본다. **누가 틀을 정하는가**가 기준이다.

> "이 화면을 열 때마다, 보는 조합을 직접 고르실 건가요, 아니면 매번 같은 자리에
> 최신 값만 갈아끼우면 되나요?"

후자면 여기서 멈추고 `frame-question`으로 보낸다. 둘 다 필요하다는 답이 오면
**산출물 두 개**라고 알린다 — 감시형 일보 하나, 탐색형 대시보드 하나. 합치지 않는다.

---

## 3. 축 후보 제시 — 이 단계의 핵심

`frame-question`이 질문 후보를 내놓듯, 여기서는 **독자가 바꿔볼 수 있어야 하는 것**의
후보를 내놓는다. 사용자가 말한 것 + 데이터 구조를 훑어 내가 발견한 것을 합친다.

| 축 종류 | 예시 | 흔한 컨트롤 |
|---|---|---|
| 기간 | 날짜·월·분기 | 날짜 선택 / 기간 슬라이더 |
| 대상 | 상품군·부문·브랜드 | select / 칩(다중 선택) |
| 위치 | 지역·채널·매장 | 지도 클릭 / select |
| 비교대상 | 전년·전월·목표 | 토글 |

각 후보에 **이 축을 바꾸면 독자가 무엇을 다르게 보게 되는지**를 한 줄 붙인다.
바꿔도 화면이 똑같이 보이는 축은 후보에서 뺀다 — 그건 축이 아니라 라벨이다.

**2~4개로 좁힌다.** 축마다 컨트롤이 하나씩 늘고, 축이 늘수록 조합의 수는 곱으로
늘어난다. 다 넣으면 독자가 필터 조합을 스스로 설계해야 하는 화면이 된다 —
탐색이 아니라 노동이다.

```
이 대시보드에서 바꿔볼 수 있게 할 축을 정리해봤습니다.

 A. 기간 — 월 단위로 넘겨보며 추이를 본다
 B. 부문(중고등/ELT 등) — 부문마다 채널 구성이 다른지 본다
 C. 지역 — 시군구 단위로 어디가 유독 다른지 본다
 D. 채널 — 서점채널 vs 자사채널 비중을 본다

 이 중 어디까지 필요하신가요? 다 넣으면 조합이 너무 많아져 오히려 못 씁니다.
```

각 축에 **기본값**(처음 열었을 때 보이는 값)을 같이 정한다. 기본값 없이 "전체"로
열리면 첫 화면이 항상 가장 무거운 화면이 된다.

---

## 4. 데이터 그레인 확정

축이 정해지면, **그 축들의 모든 조합에 값이 있어야** 계산이 된다. 원자료가
어느 단위까지 쪼개져 있어야 하는지를 정한다 — `references/explore-model.md`의
그레인 규칙을 따른다.

```
확정한 축: 기간 × 부문 × 채널
→ 원자료는 최소 (날짜, 부문, 채널) 조합 단위로 있어야 한다.
→ 이보다 굵은 단위(예: 부문 없이 채널만)로 집계된 데이터로는
   "부문별로 채널 구성이 다른가"에 답할 수 없다.
```

이 단계에서 데이터가 그레인에 못 미치는 게 드러나면 **축을 줄이거나 데이터를
다시 받는다.** 억지로 평균이나 비례배분으로 채우지 않는다 — 그건 계산이 아니라 추정이고,
탐색 화면에서 추정치를 실측치처럼 보여주면 독자가 속는다.

**긴 형식(long format) 원자료 전체를 남긴다.** `plan-report`의 데이터 준비와 다른
지점이다 — 설명형은 결론에 필요한 값만 추려서 스펙에 담지만, 탐색형은 독자가 어떤
조합을 고를지 미리 알 수 없으므로 **그레인 전체가 산출물 안에 들어간다.**
파일 크기가 커지는 이유이기도 하다 — `explore-model.md`의 크기 관리 지침을 따른다.

---

## 5. 패널 후보 제시

`plan-report`의 exhibit과 대응하지만 성격이 다르다. exhibit은 결론 하나를 만들지만,
**패널은 축이 바뀔 때마다 다른 값을 보여주는 틀**이다.

| 패널 유형 | 보여주는 것 | 반응하는 축 |
|---|---|---|
| KPI 카드 | 현재 조합의 합계·비교값 | 전체 축 |
| trend | 시간에 따른 추이 | 기간 + 그 외 |
| mix(구성) | 구성 비중, 상위 N + 기타 드릴다운 | 기간·대상 |
| map | 지역별 분포 | 기간·대상 |
| table | 상세 행 단위 | 전체 축 |

각 패널 제목은 **명사구로 충분하다.** "부문별 매출 구성" 같은 제목이 반려되지 않는다 —
`action_title`의 "주장 하나" 규칙은 탐색형에 없다. 대신 **"이것만 봐도 무엇을 보여주는
패널인지 알 수 있나"**(자체검사 ①)는 그대로 적용된다. "요약", "현황" 같은 제목은
그것도 통과하지 못한다 — 무엇의 요약인지가 없다.

후보를 제시할 때 **어느 축에 반응하는지**를 같이 적는다. 반응하지 않는 축이 있는
패널은 그 축이 왜 전체에 필요한지 다시 확인한다.

---

## 6. 범위 명시 (out_of_scope)

탐색형이라고 모든 것을 다 보여줄 수 있는 도구가 되는 건 아니다. 아래를 명시한다.

- **이 데이터로 답할 수 없는 조합** — 그레인이 못 미치는 부분 (4장에서 확인한 것)
- **판단은 하지 않는다.** "이상 있음/없음" 같은 판정은 감시형의 역할이다. 탐색형은
  독자가 스스로 보고 판단하게 하는 도구다 — 화면이 대신 결론을 내리지 않는다
- 필요하면 별도 산출물(감시형 리포트)로 안내한다. 하나에 억지로 합치지 않는다

---

## 7. 브리프 확정

합의된 내용을 작업 폴더에 `explore-brief.json`으로 저장한다.

```
{
  brief_version  subject  why_now
  audience  mechanism
  axes    [{ id  name  type  control  default }]
  grain   { dimensions[]  confirmed }
  panels  [{ id  title  type  axes_used[] }]
  out_of_scope [ ]
}
```

`action_title`·`key_takeaway`·`weight`·`questions`·`tension`은 이 브리프에 없다.
`plan-report`의 대응 개념이 원천적으로 성립하지 않는 자리라서 억지로 비워두지 않고
**필드 자체를 두지 않는다.**

확정 전에 한 번에 요약해서 보여주고 동의를 받는다.

| 항목 | 무엇 |
|---|---|
| 무엇을 / 왜 지금 | `subject` · `why_now` |
| 축 | 개수 + 각 축 이름·기본값 |
| 그레인 | 데이터가 어느 조합 단위까지 쪼개져야 하는지 |
| 패널 | 개수 + 각 패널 한 마디 + 반응하는 축 |
| 제외 | `out_of_scope` |

닫는 말은 "이대로 진행할까요?" 한 줄이다.

---

## 8. 하지 않는 것

- **질문(questions)을 묻지 않는다.** 여기서 합의하는 건 질문이 아니라 축이다
- `action_title`·`key_takeaway`·`weight`를 만들려 하지 않는다 — 탐색형에 없는 개념이다
- **판단·결론을 내리려 하지 않는다.** 그건 설명형(진단·선택·감시·추적)의 역할이다
- 값을 먼저 보고 축을 정하지 않는다 — 축은 데이터가 아니라 독자의 필요에서 나온다
- 그레인에 못 미치는데 추정으로 채워 넣지 않는다
- 축을 4개를 넘게 늘리지 않는다 — 조합이 곱으로 늘어 필터 지옥이 된다
- 감시형과 하나의 산출물로 합치지 않는다
