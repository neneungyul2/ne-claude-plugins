# 구성 확정 (plan-report)

여기서 **결론과 차트가 확정된다.** 렌더러는 이 스펙을 그리기만 한다.
렌더러가 스스로 레이아웃을 판단하게 두면 같은 데이터로 만든 HTML과 슬라이드의 결론이 달라진다.

## 0. 먼저 읽을 것

작업 폴더의 `report-brief.json`을 먼저 읽는다 (report 모드).
**여기서 질문을 바꾸지 않는다.** 바뀌어야 하면 `frame-question`으로 되돌아간다.

- `${CLAUDE_PLUGIN_ROOT}/skills/plan-report/references/spec-schema.md` — 스펙 규격
- `${CLAUDE_PLUGIN_ROOT}/references/chart-rules.md` — 질문 유형 → 차트 매핑, 금칙
- `${CLAUDE_PLUGIN_ROOT}/references/design-rules.md` — 배치 원칙
- `${CLAUDE_PLUGIN_ROOT}/references/metrics.md` — 지표·기준 정의 (glossary의 원본)
- `${CLAUDE_PLUGIN_ROOT}/references/korea-map.md` — 지역 데이터가 있을 때

## 1. 순서

1. **브리프의 질문을 펼친다.** `brief.questions` 하나가 exhibit 한두 개가 된다.
   질문에 답할 수 없다는 것이 데이터에서 드러나면 **되돌아가서 다시 고른다.**
2. **데이터에서 답을 찾는다.** 실제로 계산해본다. 눈대중으로 결론을 쓰지 않는다.
3. **핵심 결론(`key_takeaway`)을 쓴다.** 서술형 한 문장. 화면 맨 위 가장 큰 글자가 된다.
   그 안에서 형광펜으로 칠할 대목 2~4개를 `emphasis`로 고른다.
4. **KPI 2~4개를 고른다.** 비교값 없는 지표는 KPI가 아니다.
5. **exhibit을 나열한다.** 결론을 뒷받침하는 순서로. **각각 주장 하나.**
   각 exhibit에 `answers`로 어느 질문에 답하는지 붙인다.
6. **축이 여러 개 필요한지 본다.** 같은 질문을 다른 각도로 봐야 하면 exhibit을 쪼개지 말고
   `views`로 묶는다. 세그먼트에서 개별로 내려가야 하면 `drilldown`을 만든다.
7. **차트를 고른다.** `question_type`을 정하고 매핑표대로. 취향으로 고르지 않는다.
8. **액션을 도출한다.** 아래 3장. **report 모드에서 생략할 수 없다.**
9. **용어와 산식을 훑는다.** 아래 4장.
10. **스펙 JSON을 쓴다.**
11. **자체 검사를 돌린다.** 통과 못 하면 고쳐서 다시 돌린다.

## 2. 강제 사항

### action_title은 서술형 결론

exhibit의 제목은 **무슨 일이 일어났는지를 말하는 문장**이다. 명사구는 반려한다.

| 반려 | 통과 |
|---|---|
| 채널별 출고 현황 | 온라인 3사가 8월 출고 증가분의 82%를 차지했다 |
| 월별 추이 | 6월 이후 3개월 연속 감소, 감소폭은 줄고 있다 |
| 반품률 비교 | A채널 반품률이 전사 평균의 2.4배다 |

판정 기준: 제목만 읽고 "그래서 뭐?"라는 질문이 남으면 명사구다.

### action_title은 주장 하나다

서술형이기만 하면 통과가 아니다. **한 exhibit은 한 가지만 말한다.**

| 반려 | 왜 |
|---|---|
| 구매자의 절반이 40대 여성이고, 40~50대가 87.4%다 — 사는 사람은 학부모다 | 주장 3개 |
| 수도권이 54.9%지만 나머지 45%는 251개 시군구에 흩어져 있다 — 대구·광주가 인천·부산과 같은 체급이다 | 주장 2개 |

판정법 — **"그래서?"를 한 번만 물을 수 있어야 한다.** 두 번 물을 게 남으면 두 개다.

금지: `—`로 두 주장 잇기, 쉼표로 서로 다른 주장 잇기, 한 문장에 마침표 두 개.
부가 수치는 `so_what`이나 각주로 내린다. 제목에 다 담으려 하지 않는다.

수치를 못 넣겠으면 방향이라도 넣는다. 데이터로 결론이 안 나면 그것도 결론이다 —
"8월 채널별 출고에 유의미한 편차가 없다".

> **반려 강도 (파일럿 중 조정 대상)**
> 현재는 명사구를 발견하면 **고쳐 쓰되 사용자에게 알린다.** 작업을 막지는 않는다.
> 전사 배포 후 저항이 크면 경고만 남기는 쪽으로 완화한다. — TODO: 파일럿 피드백 후 확정

### exhibit 하나 = 메시지 하나 + so-what 한 줄

한 차트에 두 가지를 말하려 하면 쪼갠다. `so_what`은 "그래서 무엇을 해야 하나"에 답한다.

### 각주 4요소

모든 exhibit은 **출처 · 기간 · 단위 · 집계기준** 네 가지를 각주로 갖는다.
데이터셋 카드에서 그대로 가져온다. 하나라도 비면 검사에서 걸린다.

### 기준(basis) 명시

- 스펙 최상위에 `basis` 필수. exhibit별로 다르면 exhibit에서 override.
- 화면 상단과 각주 양쪽에 노출한다.
- **기준이 바뀌면 결론도 바뀐다.** "총출고 기준으로 다시"라는 요청이 오면 `basis`만 바꾸는 게
  아니라 모든 `action_title`을 다시 계산해서 쓴다.
- 한 화면에 기준을 섞지 않는 것이 원칙. 예외는 아래.

> **기준 혼재 허용 예외**
> 총출고와 반품(또는 반품률)을 나란히 놓는 경우처럼, **두 기준의 관계 자체가 메시지**일 때는

### 묶은 항목은 `group_detail`을 채운다

"기타", "나머지 N개", "상위 N 외"로 묶었으면 **묶기 전 원자료 전체**를 `group_detail`에 넣는다.
각주에 글로만 적는 것은 안 된다. 화면에서 클릭해 열어볼 수 있어야 한다.

### 차트 금칙

파이, 도넛, 3D, 이중 Y축, 잘린 축(0에서 시작하지 않는 막대), 무지개 팔레트.
이유와 대안은 `chart-rules.md` 참조.

## 3. 인사이트와 액션 — report 필수

exhibit만 늘어놓고 끝나는 리포트는 보고서가 아니라 자료집이다.
"그래서 무엇을 하나"에 답하지 않으면 수신자가 회의에서 그 질문을 한다.

### 도출 절차

1. 각 exhibit의 `so_what`을 모아 놓고 본다
2. 그중 **행동으로 옮길 수 있는 것**만 남긴다. "주목할 필요가 있다"는 행동이 아니다
3. 남은 것을 `decision`(이 보고로 정해야 할 것)과 연결한다
4. 3~5개로 추린다. 우선순위를 매긴다

### 각 액션이 갖춰야 할 것

| 필드 | 판정 |
|---|---|
| `title` | **동사로 끝난다.** "~를 한다", "~로 바꾼다". 명사구·"검토가 필요하다"는 반려 |
| `why` | 어느 exhibit의 어떤 수치가 근거인지 명시 |
| `evidence` | exhibit id. **비어 있으면 액션이 아니라 의견이다** |
| `priority` | high / mid / low |
| `level` | `exec` / `head` / `lead` / `staff`. 이 액션을 결정·실행하는 층 |
| `metric` | 효과를 확인할 지표. 없으면 `null` |

### 담당자를 적지 않는다

액션이 누구 일인지는 **조직이 정한다. 리포트가 정하지 않는다.**
대신 `level`로 "이건 어느 층의 일인가"만 표시한다.

### 수신자 레벨과 맞춘다

`brief.audience_level`과 비교한다. 레벨 순서는 `exec` > `head` > `lead` > `staff`.

| 관계 | 처리 |
|---|---|
| 같은 레벨 / 한 단계 아래 | 본문 액션 |
| **두 단계 이상 아래** | 본문에서 빼고 **"실무 후속 과제"**로 내린다 |
| 위 | 본문 액션. "상위 결정 필요"로 표시 |

본부장 보고에 `lineage 마스터의 영역 공백을 채운다`(staff)가 들어가면 두 단계 아래다.
**지우지 않는다.** 정보는 살리되 본문 흐름에서 뺀다.

### 액션이 안 나올 때

데이터가 뒷받침하지 않는 제안을 지어내지 않는다.
`actions: []`로 두고 `open_questions`에 **왜 액션을 낼 수 없는지**를 적는다.
렌더러가 "현재 데이터로는 실행 가능한 액션이 도출되지 않았다"로 표시한다.

quick 모드는 `actions`를 생략할 수 있다.

## 4. 용어와 산식

읽는 사람이 모르는 말이 하나 있으면 리포트는 거기서 멈춘다.
스펙을 쓰기 전에 **본문·차트 라벨·각주 전체를 훑어** 아래를 잡아낸다.

### glossary — 인라인 툴팁

- 영문 축약어 (GMV, SKU, MAU, DOS, ITR …)
- 사내에서만 쓰는 말 (초도배본, 순출고, 수불, SCM/BNK …)
- 일반어처럼 보이지만 정의가 갈리는 말 (실판매량, 반품률, 품절 …)

정의는 **`references/metrics.md`에서 가져온다. 여기서 새로 만들지 않는다.**
metrics.md에 없고 확인도 안 됐으면 `desc`에 `확인 필요`를 적고 `open_questions`에도 올린다.

### calcs — 산식 모달

| 설명 길이 | 처리 |
|---|---|
| 한 문장이면 | `glossary` 툴팁 |
| 산식 + 단계 2개 이상, 또는 예외·제외 조건이 있으면 | `calcs` 모달 |

"매출 = 판매금액 − 반품금액, 단 세트 상품은 세트 단위로 집계하고 음수 행은 반품으로 본다"
같은 것은 툴팁에 넣으면 안 읽힌다. 모달이다.

> 툴팁은 보조 수단이다. **툴팁을 봐야만 이해되는 화면은 이미 실패한 화면이다.**
> 본문 문장 자체가 먼저 읽혀야 한다.

## 5. 분량

| 모드 | exhibit | 비고 |
|---|---|---|
| quick | 1~3 | 헤드라인 + 차트. 요약 섹션 없어도 됨 |
| report | 3~7 | 헤드라인 + 요약 + exhibit + 각주 |

7개를 넘으면 무엇을 빼야 하는지 먼저 판단한다. 다 넣는 건 구성이 아니다.

## 6. 자체 검사

스펙을 넘기기 전에 아래를 하나씩 확인한다. 하나라도 실패하면 고친다.

- [ ] `key_takeaway.text`가 서술형 문장인가
- [ ] `emphasis`의 각 문자열이 `text` 안에 실제로 있는가 (2~4개)
- [ ] 모든 exhibit의 `action_title`이 서술형 문장인가 (명사구 0개)
- [ ] exhibit마다 `so_what`이 있고, 제목의 반복이 아닌가
- [ ] 모든 exhibit에 출처·기간·단위·집계기준 4요소가 있는가
- [ ] 최상위 `basis`가 있고, 화면에 노출되는가
- [ ] 금칙 차트가 없는가
- [ ] `question_type`과 `chart`가 매핑표와 일치하는가
- [ ] exhibit 수가 모드별 범위 안인가
- [ ] 데이터셋 카드의 "확인 필요" 항목이 스펙에 그대로 표시되는가
- [ ] 핵심 결론의 수치가 실제 데이터에서 계산된 값인가
- [ ] (report) `kpis`가 2~4개이고 각각 비교값이 있는가
- [ ] (report) `brief`가 들어 있고, 모든 exhibit에 `answers`가 있는가
- [ ] (report) `brief.questions`의 모든 질문에 답하는 exhibit이 있는가
- [ ] 모든 `action_title`이 **주장 하나**인가 (`—` 없음, 마침표 하나)
- [ ] `views`가 2개 이상인 exhibit에 각 view의 `read`가 있는가
- [ ] 축을 바꿔도 결론이 뒤집히지 않는가 (뒤집히면 별도 exhibit이다)
- [ ] `segments`에 `basis`가 있는가
- [ ] (report) `actions`가 3~5개이고, 각 액션의 `title`이 동사로 끝나며 `evidence`가 비어 있지 않은가
- [ ] 액션에 `owner`가 없고 `level`이 있는가
- [ ] 수신자보다 두 단계 아래 액션이 본문에 남아 있지 않은가
- [ ] 본문·라벨·각주의 축약어·사내 용어가 모두 `glossary`에 있는가
- [ ] 한 문장으로 안 되는 계산이 `calcs`로 빠져 있는가
- [ ] "기타"·"나머지 N개"로 묶은 항목마다 `group_detail`이 채워져 있는가
- [ ] 지역 데이터가 있으면 `choropleth`를 검토했는가 (막대만 쓰지 않았는가)
- [ ] (report) `key_takeaway.ask`가 있는가 — **발견에서 끝나지 않았는가**
- [ ] (report) `brief.tension`의 `what_is` / `what_could_be`가 채워져 있는가
- [ ] `brief.mechanism`에 맞는 밀도인가 (`document`면 화면 안에 so-what이 전부 있는가)
- [ ] 선·누적 차트의 계열이 5개 이하인가 (넘으면 `small_multiples` 또는 "기타" 묶기)
- [ ] 모든 차트에 제목이 있고, 모든 축에 축 제목이 있는가
- [ ] 축 눈금과 값 라벨을 **둘 다** 쓰고 있지 않은가
- [ ] `emphasis_steps`가 있다면 단계 간 **정렬이 동일**한가

### 스토리 검사 — 4가지를 실제로 돌린다

체크박스가 아니라 **읽어 보는** 검사다. `references/storytelling.md` 8장.

**① 수평 논리** — `key_takeaway.text` → `action_title` 1, 2, 3 … → `key_takeaway.ask`를
**그 순서로만** 이어서 읽는다. 하나의 이야기가 되는가?
- 제목만으로 결론이 안 나온다 → 서술형이 아니다
- 순서가 뒤죽박죽이다 → exhibit 순서가 데이터 순서로 돼 있다
- 중간이 비어 논리가 점프한다 → exhibit이 빠졌다
- 마지막이 요청으로 닿지 않는다 → `ask`와 `actions`가 연결되지 않았다

**② 수직 논리** — exhibit마다 `action_title` ↔ 차트 ↔ `so_what` ↔ `footnote`가
같은 것을 말하는가? 무관한 정보가 섞여 있지 않은가?

**③ cascading** — 뒤 exhibit의 비교 표현("더 낮다", "다르다", "바뀌었다")이
앞 exhibit에서 **비교 틀을 세운 뒤에** 나오는가?
`key_takeaway`에 세부 수치가 먼저 나와 있지 않은가?

**④ 역스토리보딩** — 각 exhibit의 요점을 한 줄씩 적어 목록으로 만든다.
그 목록이 `brief.questions`와 대응하는가? 대응 안 되는 항목은 빼거나 질문을 추가한다.

검사 결과를 사용자에게 한 줄로 보고한다: "스펙 검사 통과 (exhibit 4개, 기준: 순출고)".
**수평 논리 검사는 읽은 문장을 그대로 보여준다.** 사용자가 그 흐름을 직접 판단할 수 있어야 한다.
