# 구성 확정 (plan-report)

여기서 **결론과 차트가 확정된다.** 렌더러는 이 스펙을 그리기만 한다.
렌더러가 스스로 레이아웃을 판단하게 두면 같은 데이터로 만든 HTML과 슬라이드의 결론이 달라진다.

## 0. 먼저 읽을 것

- `${CLAUDE_PLUGIN_ROOT}/skills/plan-report/references/spec-schema.md` — 스펙 규격
- `${CLAUDE_PLUGIN_ROOT}/references/chart-rules.md` — 질문 유형 → 차트 매핑, 금칙
- `${CLAUDE_PLUGIN_ROOT}/references/design-rules.md` — 배치 원칙
- `${CLAUDE_PLUGIN_ROOT}/references/metrics.md` — 지표·기준 정의

## 1. 순서

1. **핵심 질문을 적는다.** 수신자가 이 화면을 보고 답을 얻어야 하는 질문. 한 문장.
2. **데이터에서 답을 찾는다.** 실제로 계산해본다. 눈대중으로 결론을 쓰지 않는다.
3. **헤드라인을 쓴다.** 서술형 결론 한 문장. 이게 화면 맨 위에 온다.
4. **exhibit을 나열한다.** 헤드라인을 뒷받침하는 순서로. 각각 메시지 하나.
5. **차트를 고른다.** `question_type`을 정하고 매핑표대로 고른다. 취향으로 고르지 않는다.
6. **스펙 JSON을 쓴다.**
7. **자체 검사를 돌린다.** 통과 못 하면 고쳐서 다시 돌린다.

## 2. 강제 사항

### action_title은 서술형 결론

exhibit의 제목은 **무슨 일이 일어났는지를 말하는 문장**이다. 명사구는 반려한다.

| 반려 | 통과 |
|---|---|
| 채널별 출고 현황 | 온라인 3사가 8월 출고 증가분의 82%를 차지했다 |
| 월별 추이 | 6월 이후 3개월 연속 감소, 감소폭은 줄고 있다 |
| 반품률 비교 | A채널 반품률이 전사 평균의 2.4배다 |

판정 기준: 제목만 읽고 "그래서 뭐?"라는 질문이 남으면 명사구다.

수치를 못 넣겠으면 방향이라도 넣는다. 데이터로 결론이 안 나면 그것도 결론이다 —
"8월 채널별 출고에 유의미한 편차가 없다".

> **반려 강도 (파일럿 중 조정 대상)**
> 현재는 명사구를 발견하면 **고쳐 쓰되 사용자에게 알린다.** 작업을 막지는 않는다.
> 전사 배포 후 저항이 크면 경고만 남기는 쪽으로 완화한다. — TODO: 파일럿 피드백 후 확정

### exhibit 하나 = 메시지 하나 + so-what 한 줄

한 차트에 두 가지를 말하려 하면 쪼갠다. `so_what`은 "그래서 무엇을 해야 하나"에 답한다.

### 각주 4요소

모든 exhibit은 **출처 · 기간 · 단위 · 집계기준** 네 가지를 각주로 갖는다.
데이터셋 카드에서 그대로 가져온다. 하나라도 비면 검사에서 걸린다.

### 기준(basis) 명시

- 스펙 최상위에 `basis` 필수. exhibit별로 다르면 exhibit에서 override.
- 화면 상단과 각주 양쪽에 노출한다.
- **기준이 바뀌면 결론도 바뀐다.** "총출고 기준으로 다시"라는 요청이 오면 `basis`만 바꾸는 게
  아니라 모든 `action_title`을 다시 계산해서 쓴다.
- 한 화면에 기준을 섞지 않는 것이 원칙. 예외는 아래.

> **기준 혼재 허용 예외**
> 총출고와 반품(또는 반품률)을 나란히 놓는 경우처럼, **두 기준의 관계 자체가 메시지**일 때는
> 허용한다. 이때 각 계열 라벨에 기준을 붙이고, 합계를 내지 않는다.

### 차트 금칙

파이, 도넛, 3D, 이중 Y축, 잘린 축(0에서 시작하지 않는 막대), 무지개 팔레트.
이유와 대안은 `chart-rules.md` 참조.

## 3. 분량

| 모드 | exhibit | 비고 |
|---|---|---|
| quick | 1~3 | 헤드라인 + 차트. 요약 섹션 없어도 됨 |
| report | 3~7 | 헤드라인 + 요약 + exhibit + 각주 |

7개를 넘으면 무엇을 빼야 하는지 먼저 판단한다. 다 넣는 건 구성이 아니다.

## 4. 자체 검사

스펙을 넘기기 전에 아래를 하나씩 확인한다. 하나라도 실패하면 고친다.

- [ ] `headline`이 서술형 문장인가
- [ ] 모든 exhibit의 `action_title`이 서술형 문장인가 (명사구 0개)
- [ ] exhibit마다 `so_what`이 있고, 제목의 반복이 아닌가
- [ ] 모든 exhibit에 출처·기간·단위·집계기준 4요소가 있는가
- [ ] 최상위 `basis`가 있고, 화면에 노출되는가
- [ ] 금칙 차트가 없는가
- [ ] `question_type`과 `chart`가 매핑표와 일치하는가
- [ ] exhibit 수가 모드별 범위 안인가
- [ ] 데이터셋 카드의 "확인 필요" 항목이 스펙에 그대로 표시되는가
- [ ] 헤드라인의 수치가 실제 데이터에서 계산된 값인가

검사 결과를 사용자에게 한 줄로 보고한다: "스펙 검사 통과 (exhibit 4개, 기준: 순출고)".

## 5. 다음 단계

스펙이 확정되면 포맷에 맞는 렌더러로 넘어간다.

- HTML → `${CLAUDE_PLUGIN_ROOT}/skills/build-html/SKILL.md`
- 문서·슬라이드 → `${CLAUDE_PLUGIN_ROOT}/skills/build-doc/SKILL.md`

스펙 JSON은 작업 폴더에 `report-spec.json`으로 저장한다. 수정 요청이 오면 스펙을 고치고
다시 렌더링한다. 렌더 결과물을 직접 고치지 않는다.
