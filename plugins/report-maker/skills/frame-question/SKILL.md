# 질문 설계 (frame-question)

**데이터를 열기 전에 돈다.** 이 단계가 없으면 "무엇을 답할 것인가"가 합의되지 않은 채
있는 데이터로 만들 수 있는 것을 만들게 되고, 다 만든 뒤에 방향이 틀렸다는 걸 알게 된다.

report 모드에서는 건너뛸 수 없다. quick 모드는 생략하고 `load-data`로 바로 간다.

## 0. 먼저 읽을 것

- `${CLAUDE_PLUGIN_ROOT}/references/report-types.md` — **필수.** 유형이 형태를 정한다
- `${CLAUDE_PLUGIN_ROOT}/references/storytelling.md` — **필수.** 무엇을 어떤 순서로 말할지의 규칙
- `${CLAUDE_PLUGIN_ROOT}/references/metrics.md` — 지표 정의. 질문이 지표를 건드리면 필요하다

데이터는 아직 열지 않는다. 파일이 첨부돼 있어도 **구조만 훑고 값은 보지 않는다.**
값을 먼저 보면 "이 데이터로 뭘 할 수 있나"로 질문이 끌려간다.

**화면부터 만들지 않는다.** 만들기 시작하면 만든 것에 애착이 생겨, 틀렸다는 걸 알아도 못 버린다.
이 단계는 글자로만 한다.

---

## 1. 진행 방식 — 대화로 한다

체크리스트를 던져 채우게 하지 않는다. **후보를 먼저 내놓고 고르게 한다.**
사용자가 생각하지 못한 질문을 발견하는 것이 이 단계의 가치다.

한 번에 다 묻지 말고 아래 순서로 짧게 주고받는다.

```
1) 상황 파악   →  2) 유형 판정      →  3) 질문 후보 제시
→ 4) 수신자·전달 방식 →  5) 가정 명시 →  6) 분석 축 정의
→ 7) 3분 스토리·긴장·순서  →  8) 브리프 확정
```

---

## 2. 상황 파악

사용자가 처음 한 말에서 아래를 뽑는다. 없는 것만 묻는다.

- 무엇에 대한 리포트인가 (채널·제품·기간·조직)
- 왜 지금 만드나 — **이 리포트가 없으면 무슨 일이 생기나**
- 누가 보나
- 이미 알고 있는 것 / 의심하고 있는 것

"왜 지금"이 가장 중요하다. 정기 보고면 정기 보고라고 답하는 것도 답이다.
답이 "그냥 궁금해서"면 quick 모드가 맞다.

---

## 2-1. 유형 판정 — 묻지 말고 읽어낸다

**"진단·선택·감시·추적 중 무엇인가요"라고 묻지 않는다.** 우리 분류를 사용자가 배울 이유가
없고, 넷 중 고르라고 하면 대부분 애매해한다. 사용자가 **이미 한 말**에 답이 들어 있다.

### ① 신호를 읽는다

| 이런 말이 나오면 | 유형 |
|---|---|
| "왜 이런지 모르겠다" · "이게 뭔지 파악해야" · "어떤 특성인지" · "원인이" | **진단** |
| "A랑 B 중에" · "뭘 골라야" · "할지 말지" · "우선순위를" · "승인받아야" | **선택** |
| "매일" · "매주" · "정기" · "이상 있으면" · "문제 생기면 알아야" · "모니터링" | **감시** |
| "언제 뒤집히나" · "목표 대비" · "따라잡히나" · "진도" · "얼마나 남았나" | **추적** |

**"왜 지금 만드나"에 답이 가장 많이 들어 있다.** 2장에서 이미 물은 것이다. 다시 묻지 않는다.

### ② 추정하고, 근거와 형태를 같이 보여준다

유형 이름을 말해도 되지만 **중요한 건 이름이 아니라 형태**다. 글자 와이어프레임으로 보여준다.

```
"○○ 때문에 만드신다고 하셔서, 이런 모양으로 잡았습니다.

 ┌────────────────────────┐
 │ 판단 한 줄 + 무엇을 정할지  │
 ├────────────────────────┤
 │ ■ 가장 큰 자리 — 판단 근거  │
 ├────────────────────────┤
 │ □ 다른 설명은 아닌가        │
 │ □ 이 데이터로 못 답한 것     │
 └────────────────────────┘

 한 번 읽고 판단하는 문서입니다. 갱신하지 않습니다.
 다르게 보셔야 하면 말씀해 주세요."
```

**HTML을 그려서 보여주지 않는다.** 화면을 만들면 사용자는 구조가 아니라 색과 폰트에
반응하고, 만든 쪽은 만든 것에 애착이 생겨 틀렸어도 못 버린다. 이 단계는 글자로만 한다.

### ③ 신호가 없거나 섞였을 때만 묻는다

그때도 유형 이름을 묻지 않는다. **가르는 질문 하나**면 된다.

> "이 화면, 다음 달에도 같은 걸 또 여시나요?"

- **아니오** → "고르실 선택지가 이미 있나요, 아니면 뭐가 문제인지부터 밝혀야 하나요?"
  → 선택지 있음 = **선택** / 없음 = **진단**
- **예** → "뭘 기준으로 '이상하다'고 판단하시나요?"
  → 정해진 수치·평소 범위 = **감시** / 목표·계획·상대방 진도 = **추적**

두 번이면 끝난다. 세 번째 질문이 필요하면 그건 산출물이 둘이라는 신호다.

### ④ 섞인 요청은 쪼갠다

"진단하고 나서 계속 지켜보고 싶다"는 **산출물 두 개**다. 하나에 담으면 둘 다 안 된다 —
진단은 결론이 고정돼야 하고 감시는 매번 달라져야 한다.

> "두 가지가 섞여 있습니다. 지금 필요한 건 원인을 밝히는 쪽인가요,
>  아니면 매주 확인할 화면인가요? 먼저 하나를 만들고 나머지는 이어서 하겠습니다."

### ⑤ 유형이 바꾸는 것

`report-types.md` §3의 표를 따른다. 유형에 따라 **필수 요소가 달라진다.**
감시형에 `tension`을 억지로 만들거나, 정상인데 액션을 만들어 넣지 않는다.

## 3. 질문 후보 제시 — 이 단계의 핵심

**6~8개를 내놓는다.** 사용자가 말한 것 2~3개 + 내가 발견한 것 4~5개.

후보를 만들 때 아래 축으로 훑는다. 전부 채우려 하지 말고, 이 주제에서 말이 되는 것만.

| 축 | 질문 형태 |
|---|---|
| 규모 | 얼마나 큰가, 전체에서 얼마를 차지하나 |
| 변화 | 늘었나 줄었나, 언제부터, 얼마나 |
| 구성 | 무엇이 그걸 만드나, 어디에 몰려 있나 |
| 편차 | 어디가 유독 다른가, 왜 다른가 |
| 효율 | 투입 대비 산출이 어디가 좋은가 |
| 기준 | 이 숫자를 다른 것과 비교하려면 무엇을 맞춰야 하나 |
| 한계 | 이 데이터로 답할 수 없는 것은 무엇인가 |

제시할 때 각 후보에 **이 질문에 답하면 무엇을 할 수 있는지**를 한 줄로 붙인다.
답해도 아무것도 안 바뀌는 질문은 후보에서 뺀다.

```
이 주제로 답할 수 있는 질문을 정리해봤습니다. 3~5개를 고르시면 그것만 다룹니다.

 A. 누가 사는가 — 상품명·상세페이지를 누구 언어로 쓸지가 갈린다
 B. 무엇이 팔리는가 — 신간을 어디에 붙여 올릴지가 갈린다
 C. 어디서 팔리는가 — 지역 타깃 기획의 단위가 갈린다
 D. 품목당 효율이 어디가 높은가 — 결품 관리 우선순위가 갈린다
 E. 이 채널 숫자를 사내 출고와 비교하려면 무엇을 맞춰야 하나 — 채널 간 비교가 가능해진다
 F. 반복 구매가 일어나는가 — 시리즈 연계 기획의 근거가 된다
 G. 이 데이터로 답할 수 없는 것은 무엇인가 — 다음 데이터 요청 목록이 된다

세 개까지가 적당합니다. 다 넣으면 다 흐려집니다.
```

**3~5개로 좁힌다.** exhibit이 아니라 질문 개수다. 질문 하나가 exhibit 한두 개가 된다.

## 4. 수신자 레벨 확정 — 액션의 필터가 된다

수신자를 묻기만 하고 쓰지 않으면 의미가 없다. **레벨을 확정하고 액션을 여기에 맞춘다.**

| 레벨 | 누구 | 이 사람이 결정하는 것 | 이 사람에게 안 맞는 액션 |
|---|---|---|---|
| `exec` | 대표·임원 | 자원 배분, 사업 방향 | 실행 방법, 담당 배정 |
| `head` | 본부장 | 조직 간 우선순위, 예산 | 개별 상품 조치, 데이터 정비 |
| `lead` | 팀장·파트장 | 팀 실행 계획, 담당 배정 | 쿼리·마스터 수정 같은 작업 단위 |
| `staff` | 파트원 | 개별 작업 | 조직 방향 제안 |

확인 질문은 한 줄이면 된다.

> "본부장 보고로 잡을까요, 팀 내부 실행용으로 잡을까요? 액션의 수준이 달라집니다."

수신자가 여럿이면 **가장 높은 레벨에 맞추고**, 낮은 레벨 액션은 별도 블록으로 내린다.
지우지는 않는다 — 정보는 살리되 본문 흐름에서 뺀다.

**수신자는 한 사람으로 특정한다.** "이해관계자", "관련 부서"는 특정이 아니다.
여러 청중에게 동시에 맞추려 하면 **아무에게도 맞지 않는다.** 의사결정자를 찾는다.

### 무엇을 알거나 하게 할 것인가

수신자만 정하고 끝내지 않는다. **그 사람이 이 보고를 읽고 무엇을 하기를 원하는가.**

> **항상 원하는 것이 있어야 한다.** 간결히 말할 수 없으면 보고할 필요가 없는 것이다.

여기서 많이 주저한다 — "판단은 그분들 몫 아닌가". **그 전제는 틀렸다.**
데이터를 분석한 사람이 그 데이터를 가장 잘 안다. 관찰과 권고를 내놓는 것이 역할이다.
권고가 부적절한 상황이면 **다음 단계를 제안해 대화를 유도**한다.
데이터만 내밀면 "흥미롭네"로 끝나지만, 요청하면 수용 여부를 **결정해야** 한다.

발상용 동사: 결정한다 · 승인한다 · 우선순위를 바꾼다 · 중단한다 · 재검토한다 ·
자원을 배분한다 · 기준을 정한다 · 확인한다 · 위임한다 · 착수한다

### 수위(`stance`) — 레벨과 다른 축이다

위 문단은 "판단은 그분들 몫"이라는 **주저**에 대한 답이다. 주저가 아니라
**요구**일 때가 있다. "대표 보고인데 데이터만. 의견은 빼라" 는 흔한 지시이고,
대개 이유가 있다 — 판단의 자리가 이 보고가 아니라 그 다음 회의이거나,
읽는 사람이 이미 판단을 갖고 있다.

이때 레벨은 `exec`인데 요청·액션은 넣지 말아야 한다. **레벨 하나로는 표현이 안 된다.**
브리프에 `stance`를 따로 적는다.

| `stance` | 무엇을 내놓나 | `key_takeaway.ask` · `actions` |
|---|---|---|
| `judgment` (기본) | 사실 + 판단 + 요청 | 필수 |
| `data_only` | 사실과 그 구조까지. 판단·제안 없음 | **해당 없음.** 없다고 감점하지 않는다 |

- 사용자가 "데이터만", "의견은 빼고", "판단은 내가 한다"고 하면 `data_only`다.
  **한 번 확인하고 그대로 간다.** 매 단계에서 다시 권고를 밀어 넣지 않는다
- `data_only`에서도 `action_title`은 남는다. "무엇이 보이는가"는 판단이 아니라
  차트를 읽는 방법이다. 빼는 것은 **"그래서 무엇을 하라"** 쪽이다
- `data_only`라고 해서 사실을 흐리지 않는다. 숫자와 그 구조는 오히려 더 촘촘해야 한다

## 4-1. 전달 방식과 톤

```
라이브 발표 ←──────────────────→ 배포 문서
발표자가 통제                  독자가 통제
디테일 적게                    디테일 많이
```

| `mechanism` | 언제 | 밀도 |
|---|---|---|
| `presentation` | 회의에서 직접 설명한다 | 화면당 정보를 줄인다. 강조 단계를 슬라이드로 펼친다 |
| `document` | 파일로 돌린다 (**HTML 산출물의 기본값**) | "그래서 무엇인가"가 화면 안에 글자로 전부 있어야 한다 |

**둘을 겸하려 하면 발표도 문서도 아닌 것이 된다.** 하나를 고른다.
둘 다 필요하면 배포용을 먼저 만들고, 발표용은 `emphasis_steps`로 펼쳐 `build-doc`에서 뽑는다.

`tone`도 한 줄로 정한다 — `serious`(문제 제기·자원 요청) / `neutral`(정기 보고) /
`celebratory`(성과 공유). 톤이 색과 문장의 강도를 정한다.

## 5. 가정 명시

무엇을 참으로 두고 시작하는지 적는다. 나중에 결론이 흔들리면 여기가 원인이다.

적어야 할 것

- **집계 기준** — 어느 기준으로 볼 것인가. 같은 이름의 지표라도 기준이 다르면 다른 숫자다
  (총출고/순출고, 외부 플랫폼 기준/당사 공급 기준 …)
- **비교 기준** — 무엇과 비교하나. 전월? 전년? 목표? 없으면 "비교 대상 없음"도 가정이다
- **대표성** — 이 데이터가 전체를 대표한다고 볼 수 있나. 한 채널 데이터를 전사로 읽지 않는가
- **인과** — 상관을 인과로 읽을 계획이 있는가. 있으면 무엇으로 검증할 것인가
- **데이터 한계** — 알고 있는 결측·미매칭

확인은 **가정을 나열하고 반박을 받는** 형태로 한다. 다섯 항목을 각각 한 줄로,
"~를 전제로 진행합니다 / 다르면 알려주세요"로 닫는다.
줄마다 **기준과 그 기준에서 하면 안 되는 것**을 같이 적는다 —
"A 기준으로 본다"만 적으면 나중에 B와 합산된다.

확인되지 않은 가정은 `확인 필요`로 두고 **`open_questions`로 넘긴다.**

## 6. 분석 축 정의 — 데이터에 없는 그룹은 여기서 만든다

**데이터 컬럼에는 없지만 판단에 필요한 묶음**이 있다. 이걸 정의하지 않으면 원본 단위로만
보게 되고, 그 단위에서는 답이 안 나온다.

정의할 때 반드시 함께 적는다.

| 항목 | 내용 |
|---|---|
| 이름 | 그룹 이름 |
| 소속 | 어떤 값들이 들어가나 |
| **분류 근거** | 무엇을 기준으로 나눴나. **이게 없으면 임의 분류다** |
| 확정 여부 | 사내 합의된 기준인가, 이번에 제안하는 것인가 |

### 분류 근거가 결과에서 나오면 순환논증이다

**가장 흔한 실패다.** 결과 변수로 그룹을 나눈 뒤, 그 그룹이 결과에서 다르다고 보고한다.

| 함정 | 어떻게 생기나 |
|---|---|
| 동어반복 | "지표 X가 높은 집단"으로 묶고 "이 집단은 X가 높다"고 결론낸다. 아무것도 밝히지 않았다 |
| 선택 편향 | 평균에서 벗어난 상위/하위만 묶으면, 다음 기간에는 평균으로 되돌아간다 |
| 교란 | 그룹 이름이 붙는 순간 이름에 담긴 통념이 설명으로 슬쩍 들어온다 |

**규칙 — 분류 근거는 결과 변수와 독립이어야 한다.**
외부에 이미 존재하는 기준(사내 합의 분류, 공개된 구분, 계약 형태 등)으로 나눈다.
그런 기준이 없으면 **그룹에 이름을 붙이지 않는다.** 관측된 사실을 그대로 서술한다.

확인은 이런 형태로 받는다 — 그룹 이름, 각 그룹의 분류 근거 한 줄, "기준을 다르게
잡으시면 그대로 따릅니다", 그리고 **이번 리포트 안에서만 쓰는 정의이고 각주에
표시된다**는 고지.

- **이번 리포트 안에서만 쓰는 정의다.** 사내 표준으로 만들지 않는다
- 분류 근거를 각주에 반드시 표시한다
- 사용자가 직접 목록을 주면 그대로 쓰되, 근거를 한 줄 받아 적는다
- 근거를 못 받으면 `분류 근거: 담당자 판단`이라고 적는다. 비워두지 않는다

계층이 있으면 함께 정한다(`상위 그룹 → 개별 단위`).
**상위에서 패턴을 보고, 클릭해서 개별로 내려가는 구조**가 된다.

## 6-1. 3분 스토리 · 긴장 · 서사 순서

질문과 축이 정해졌으면, **말로 해 본다.**

### 3분 스토리
> "3분만 주어진다면 무엇을 말하시겠습니까? 슬라이드 없이요."

문단 하나로 적는다. **이게 안 써지면 아직 무엇을 말할지 정해지지 않은 것이다.**
질문으로 되돌아간다. 이걸 해 두면 30분 슬롯이 5분으로 줄어도 대응된다.

### 긴장 — 현재 있는 것 vs 있을 수 있는 것
모든 것이 괜찮고 앞으로도 괜찮을 이야기는 **행동을 부르지 않는다.**

```
what_is        : 지금 어떤 상태이고, 무엇이 문제인가
what_could_be  : 어떤 상태가 되어야 하는가
```

"우리는 문제가 없는데요"라고 답이 오면 다시 묻는다 —
*"그럼 이 보고를 읽고 아무것도 안 바뀌어도 괜찮은가요?"*

긴장은 **독자의 문제**로 틀 지어야 그들이 해법에 이해관계를 갖는다. 우리 문제가 아니다.

### 서사 순서

| | 언제 | 배치 |
|---|---|---|
| `lead_with_ending` | 이미 신뢰가 있다. 독자가 "그래서?"만 원한다 | 결론·요청 → 근거 → 상세 |
| `chronological` | 신뢰를 쌓아야 한다. 독자가 과정을 보고 싶어한다 | 문제 → 데이터 → 분석 → 판정 → 권고 |

HTML 산출물의 기본은 `lead_with_ending`이다. 평소와 다른 순서를 쓸 거면
**그렇게 한다고 문서 앞에서 밝힌다.**

## 7. 브리프 확정

합의된 내용을 작업 폴더에 `report-brief.json`으로 저장한다.

```
{
  brief_version  subject  why_now  report_type  audience  audience_level  stance
  decision  mechanism  tone  narrative_order
  three_minute_story
  tension { what_is  what_could_be }
  questions   [{ id  text  why }]
  assumptions [{ text  confirmed }]
  segments    [{ name  groups[]  basis  confirmed  drill_to }]
  out_of_scope [ ]
}
```

`report_type`은 `diagnostic` | `choice` | `watch` | `track`.
이 값이 `plan-report`와 렌더러에서 **무엇이 필수인지**를 바꾼다 (`references/report-types.md` §3).

`stance`는 `judgment`(기본) | `data_only`. 위 §4를 따른다.
`data_only`면 `decision`은 "판단은 이 보고 밖에서 한다"로 적고,
`key_takeaway.ask`와 `actions`는 **해당 없음**으로 둔다.

**질문을 몇 개 둘지는 이 조각이 정하지 않는다.** `decision`을 내리는 데 꼭 필요한 만큼이다.
`segments`는 데이터에 없는 그룹을 쓸 때만 넣는다 — 쓰지 않으면 키째 뺀다.
`why`는 질문마다 반드시 채운다. **"왜 이걸 묻나"에 답을 못 하면 그 질문은 뺀다.**

확정 전에 **한 번에 요약해서 보여주고 동의를 받는다.** 요약에 들어갈 항목:

| 항목 | 무엇 |
|---|---|
| 무엇을 / 왜 지금 | `subject` · `why_now` |
| 형태 | `report_type` — 이름이 아니라 **와이어프레임으로** 다시 한 번 |
| 누구에게 | `audience`(레벨) · `mechanism` · `narrative_order` |
| 요청 | `decision` — 이 보고로 무엇을 정하는가 |
| 긴장 | `tension`을 "지금 → 되어야 할 것" 한 줄로 |
| 답할 질문 | 개수 + 각 질문 한 마디 |
| 가정 | `assumptions`를 쉼표로 이어 한 줄 |
| 분석 축 | `segments`가 있을 때만 |
| 제외 | `out_of_scope` |

닫는 말은 "이대로 진행할까요?" 한 줄이다. **동의를 받기 전에 다음 단계로 넘어가지 않는다.**

## 7-1. 의뢰받은 보고라면

다른 사람(팀장·본부장·고객)의 요청으로 만드는 경우, 맥락이 의뢰자 머릿속에만 있다.
아래를 물어서 꺼낸다.

- 어떤 배경 정보가 필수인가
- 의사결정자는 누구이고 무엇을 이미 알고 있나
- **그 사람이 가진 편향은 무엇인가** — 이 결론을 지지할까, 반대할까
- 주장을 강화할 데이터로 무엇이 있나
- **리스크는 어디에 있나** — 무엇이 우리 주장을 약화시키나
- **한 문장만 쓸 수 있다면 무엇을 말하겠나**

마지막 두 개가 가장 많은 것을 끌어낸다.

## 8. 하지 않는 것

- **데이터를 먼저 열지 않는다.** 값을 보면 질문이 데이터에 끌려간다
- **화면부터 만들지 않는다.** 만든 것에 애착이 생겨 틀려도 못 버린다
- 질문을 3~5개 넘게 남기지 않는다. 다 넣으면 다 흐려진다
- 답해도 아무것도 안 바뀌는 질문을 남기지 않는다
- 수신자를 "이해관계자"로 두지 않는다. **한 사람으로 특정한다**
- 수신자 레벨을 "모두"로 두지 않는다. 그건 아무에게도 안 맞춘 것이다
- **요청 없이 넘기지 않는다.** 무엇을 알거나 하기를 원하는지 말할 수 없으면 보고할 필요가 없다
- 분류 근거 없이 그룹을 만들지 않는다
- 가정을 사용자 확인 없이 `confirmed: true`로 적지 않는다
- 유리한 데이터만 쓰기로 하지 않는다. 한 명만 구멍을 찾아도 주장 전체가 버려진다
