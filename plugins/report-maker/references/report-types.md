# 산출물 종류 (report-types)

**report-helper가 가장 먼저 읽는 문서다.** 무엇을 만들지는 이 문서의 질문 하나와 조건 셋으로 정해진다.

---

## 0. 왜 종류를 나누나

형태가 하나뿐이면 모든 보고가 같은 모양으로 나온다. 그건 규칙이 아니라 **관성**이다.

형태를 정하는 첫 질문은 하나다 — **결론을 누가 내는가.**
이 답에 따라 맨 위에 무엇이 오는지, 어디서 끝나는지, 무엇이 꼭 있어야 하는지가 정해진다.
주제(채널·품목·매출)는 형태를 정하지 않는다. 같은 매출 데이터로 다섯 종류를 다 만들 수 있다.

**종류는 직급과 묶지 않는다.** 결정형이 늘 대표이사용이고 점검형이 늘 팀원용인 것이 아니다.

---

## 1. 다섯 종류

| 결론을 내는 쪽 | 종류 | 독자가 다 읽고 하는 일 | 맨 위 | 끝나는 곳 | 없으면 실패하는 것 |
|---|---|---|---|---|---|
| 저자 | `decide` **결정형** | 승인하거나 반려한다 | 권고와 요청 | 실행 일정 | 탈락시킨 안과 그 이유 |
| 저자 | `diagnose` **진단형** | 원인에 대한 생각을 고친다 | 핵심 사실 한 줄 | 그래서 달라지는 것 | 다른 설명을 깨려는 검증 |
| 정해둔 기준 | `check` **점검형** | 괜찮은지 확인한다 | 기준을 넘었는지 | 이탈 항목 담당 · 다음 점검일 | 기준(임계값 또는 계획선) |
| 독자 | `survey` **조망형** | 전체 그림을 머릿속에 그린다 | 범위와 전체 규모 | 눈여겨볼 곳 (판단 아님) | 범위 정의, 단계마다 전체 대비 위치 |
| 독자 | `explore` **탐색형** | 궁금한 걸 직접 찾아본다 | 읽는 법 | 없음 | 독자가 바꿀 수 있는 축 |

- **저자가 결론을 내는 두 종류**는 판단을 내놓는다. 그래서 근거와 반론 처리가 있어야 한다
- **점검형**은 판단을 정해둔 기준에 맡긴다. 저자의 해석보다 **기준선을 분명히 보여주는 것**이 중요하다.
  기준이 임계값이면 지표 행, 계획선이면 시간축이다. 둘 다 점검형이다
- **조망형과 탐색형**은 결론이 없다. 차이는 보는 순서를 **저자가 정하느냐(조망)**, **독자가 정하느냐(탐색)**다

**한 산출물은 한 종류다.** "원인을 밝히고 나서 매달 지켜보고 싶다"는 산출물이 둘이다.
진단형을 먼저 내고, 점검형은 따로 만든다. 하나에 섞으면 둘 다 안 된다.

### 파이프라인

```
결정·진단·점검·조망:  report-helper → frame-question → load-data → plan-report → build-html/build-doc → verify-report
탐색:               report-helper → frame-explore  → load-data → plan-explore → build-explore      → verify-report
```

탐색형이 아닌 네 종류를 묶어 부를 때는 **보고형**이라 한다 (스펙 `spec-schema.md`, 부품 `parts.html`).
탐색형은 축(독자가 바꾸는 것)을 합의하고 원자료 전체를 싣는다. 스펙도 따로다
(`skills/plan-explore/references/explore-spec-schema.md`). 결론 문장·`action_title`·`weight`가 없다.

## 2. 종류와 따로 고르는 조건 셋

종류만으로는 형태가 다 정해지지 않는다. 아래 셋은 **어느 종류에나 붙는 조건**이다.

### ① 독자가 배경을 아는가 — `reader_context: known | new`

배경을 모르는 독자에게 결론부터 주면 그 결론이 전체의 어느 부분인지 모른다. 모름이면 앞부분을 바꾼다.

| 종류 | `known` (앎) | `new` (모름) |
|---|---|---|
| 결정형·진단형 | 답부터 바로 | **맨 위에 질문** → 전체 그림(숲 → 나무 → 가지) → 답 |
| 점검형 | 기준 이탈 여부만 | 지표마다 뜻을 한 줄 함께 표시 |
| 조망형 | 차이 없음 | 차이 없음 — 그 자체가 전체 그림이다 |
| 탐색형 | 읽는 법 한 줄 | 처음 볼 순서 안내 |

**전체 그림**은 단계마다 전체 대비 위치를 숫자로 적는다 — "시장 209.9만 부 → 그중 수능 기본 87.9만 부(42%)
→ 그 안의 온라인 37.6만 부(18%)". 위치가 없으면 나무를 볼 때 숲이 사라진다.

**애매하면 `new`로 만든다.** 배경을 아는 독자는 그림을 건너뛰면 되지만,
배경을 모르는 독자는 결론만 보고는 돌아갈 길이 없다.

### ② 한 번 읽는가, 반복해서 여는가 — `repeat: once | recurring`

| | `once` | `recurring` |
|---|---|---|
| 결론 | 그 시점에 고정된다 | 열 때마다 달라진다 |
| 구성 | 이번 질문에 맞춘다 | **고정한다.** 매번 같은 자리에서 같은 걸 찾아야 한다 |
| 데이터 시점 | 각주에 한 번 | **화면 상단에 항상** |
| "특이사항 없음" | 실패다 | 정상 출력이다 |
| 제목 | 서술형 결론 | 명사구 허용 (결론이 매번 바뀌므로) |

점검형·탐색형은 거의 늘 `recurring`, 나머지는 대개 `once`다.

### ③ 배치 — `layout: one | side | menu`

| 배치 | 모양 | 기본 |
|---|---|---|
| `one` 한 페이지 | 위에서 아래로 한 번에 | 결정형·진단형·점검형 |
| `side` 사이드바 | 왼쪽 목차가 따라오고 지금 읽는 단락이 표시된다 | 조망형 |
| `menu` 메뉴 | 위쪽 메뉴에서 단락을 골라 하나씩 본다 | — |

단락이 많아 한 페이지가 길면 `side`, 단락마다 따로 읽히는 게 나으면 `menu`를 고른다.
기본값일 뿐이고, 작성자가 산출물 화면에서 바꿀 수 있다 (편집 막대). 탐색형은 자체 섹션 목차를 쓴다.

## 3. 종류별 필수와 해당 없음

`—`는 해당 없음이고, 없다고 감점하지 않는다. **억지로 채우지 않는다.**

| 스펙 요소 | 결정 | 진단 | 점검 | 조망 |
|---|---|---|---|---|
| `key_takeaway.text` | 권고안 | 핵심 사실 (판단 문장) | 현재 상태 판정 (갱신마다 다시 씀) | 무엇을 보는가 (명사구 가능) |
| `key_takeaway.ask` | 필수 | 필수 | 이탈일 때만 | — |
| `brief.tension` · `three_minute_story` | 필수 | 필수 | — | — |
| `options` (선택지·탈락 이유) | **필수** | — | — | — |
| `actions` | 실행 일정 | 그래서 달라지는 것 | 이탈 항목 담당만. **정상이면 0개** | — (대신 `look_at`) |
| `scope` (대상·기간·단위·제외) | — | — | — | **필수** |
| `weight: primary` | 선택지 표 | 근거 exhibit 하나 | 지표 행 | — (단계가 곧 구조) |
| exhibit 수 | 선택지 수에 따름 | 3~7 | **고정 슬롯** | 단계 수 (보통 3) |
| 임계값·기준선 | 판단 기준 | — | **필수** | — |
| `question_type` 주류 | `comparison` `ranking` | `deviation` `composition` | `single_value` `trend` | `composition` `composition_2d` |

### 종류가 바꾸는 것 — 특히 주의

**결정형은 탈락시킨 안을 지우지 않는다.** "왜 나머지가 아닌가"가 없으면 독자는 권고를 검증할 수 없고,
검증할 수 없는 권고는 승인되지 않는다. 판단 기준은 **선택지를 보기 전에** 정한다.

**진단형은 가설을 깨려고 시도한 흔적이 있어야 한다.** 뒷받침만 모으면 진단이 아니다.
"다른 설명은 맞지 않는다"를 표로 둔다.

**점검형은 `actions`가 비어 있는 것이 정답일 수 있다.** "이상 없음"을 명시적으로 쓰고 끝낸다.
구성도 매번 같아야 한다. 이번 달에 흥미로운 게 생겼다고 섹션을 추가하지 않는다 — 그건 별도의 진단형이다.

**조망형은 판단하지 않는다.** 문장은 "~해야 한다"가 아니라 "~가 보인다"로 쓴다.
끝은 권고가 아니라 **눈여겨볼 곳**이다. 단계마다 경로(전체 › 부분 › 칸)와 전체 대비 비중을 보인다.

## 4. 종류별 뼈대

**레이아웃이 아니라 부품 목록이다.** 개수와 순서는 스펙이 정한다. 부품은 `template/parts.html`.

### 결정형 (`decide`)

```
[배경 모름이면] 결정할 질문 + 기한 → 전체 그림
권고 + 요청
선택지 × 판단 기준 표                  ← weight: primary
택하지 않는 이유 (안마다)
실행 일정
```

### 진단형 (`diagnose`)

```
[배경 모름이면] 풀 질문 → 전체 그림
핵심 사실 한 줄 + 요청
① 가장 큰 자리 — 사실의 근거            ← weight: primary
② 다른 설명은 맞지 않는다
③ 이 데이터로 답 못 한 것
그래서 달라지는 것
```

### 점검형 (`check`)

```
데이터 시점 (가장 위, 항상)
지표 행 + 기준 대비 (임계값)           ← weight: primary
또는 시간축 + 계획선 + 현재 위치 → "이 속도면 어떻게 되는가"
이탈 항목만 펼침 (없으면 "이상 없음") · 정상 항목은 접는다
이탈 항목 담당 · 다음 점검일
```

임계값은 `references/watch-thresholds.md`를 따른다. 기준선이 없으면 점검이 아니라 그냥 추이다.

### 조망형 (`survey`)

```
범위 (대상·기간·단위·제외) + 전체 규모
숲 — 전체가 어떻게 나뉘나        (경로: 전체)
나무 — 그중 가장 큰 부분         (경로: 전체 › 부분 · 전체의 00%)
가지 — 그 안에서 눈에 띄는 칸     (경로: 전체 › 부분 › 칸 · 전체의 00%)
눈여겨볼 곳
```

## 5. 로직은 사칙연산으로 설명할 수 있어야 한다

모든 종류에 적용한다. 보고서에 들어가는 계산은 **읽는 사람이 계산기로 따라 할 수 있어야** 한다.

- **첫 화면은 원래 단위로 보여준다.** 부수, 금액, 점유율(%). 지수·비율은 그 아래에 둔다
- **계산 방법 창(`calcs`)에는 실제 숫자로 쓴 계산을 한두 줄 넣는다** (`worked`).
  예: "5.36만 부 ÷ 99.4만 부 = 5.39%"
- **계수가 꼭 필요하면 이름이 아니라 뜻으로 부른다.** "계절지수 1.3"이 아니라 "1~2월은 평소 달보다 1.3배 팔린다"
- **복잡한 산식과 예외를 늘리지 않는다.** 예외가 필요해지면 예외를 붙이기 전에 기준 자체를
  단순하게 바꿀 수 있는지 먼저 본다. 예외를 남겨야 하면 화면에 그 예외를 적는다
- 한두 줄로 설명할 수 없는 계산이면 계산이 너무 복잡한 것이다. **설명을 늘리지 말고 계산을 줄인다**

## 6. 설명은 필요할 때 펼쳐 읽게 한다

| 무엇 | 어디에 |
|---|---|
| 제목, 결론 문장, 숫자, 차트, 출처 한 줄 | 화면에 늘 보인다 |
| 용어 뜻 | 점선 밑줄 용어 → 툴팁 (`glossary`). 두 문장 이내 |
| 계산 방법, 가정 | 제목·숫자 옆 ⓘ → 창 (`calcs`). 실제 숫자로 쓴 계산 포함 |

## 7. 작성자가 화면에서 고친다

산출물(HTML)에는 편집 막대가 있다. 작성자는 글을 고치고, 단락 순서를 바꾸고, 단락을 숨기고,
배치를 바꿔 저장한다. 원본은 그대로 두고 고친 것만 `rm-edits`에 적는다.
결론·구성 자체를 바꾸는 수정은 여전히 스펙으로 돌아간다 (`commands/report.md` 수정 3층).

## 8. 종류를 정하는 방법

**사용자에게 다섯 종류 중 고르라고 묻지 않는다.** 우리 분류를 사용자가 배울 이유가 없다.
사용자가 이미 한 말에서 읽어내고, 추정한 근거와 글자 와이어프레임으로 확인받는다.
방법은 `skills/frame-question/SKILL.md`(탐색형은 `skills/frame-explore/SKILL.md`)에 있다.

| 이런 말이 나오면 | 종류 |
|---|---|
| "A랑 B 중에" · "할지 말지" · "승인받아야" · "어떻게 대응할지" | 결정형 |
| "왜 이런지" · "원인이" · "뭐가 문제인지" · "어떤 특성인지" | 진단형 |
| "매일·매주·정기" · "이상 있으면" · "목표 대비" · "진도" · "따라잡히나" | 점검형 |
| "한눈에" · "전체 그림" · "시장 구조" · "현황 정리" · "판단은 빼고" · "데이터만" | 조망형 |
| "필터로" · "날짜·기간을 바꿔가며" · "직접 파볼 수 있게" · "대시보드로 계속" | 탐색형 |

신호가 없거나 섞였을 때만 **가르는 질문 하나**를 던진다.

> "이 자료가 답을 드리는 건가요, 정해둔 기준으로 판정하는 건가요, 아니면 읽는 분이 직접 보시는 건가요?"

- 답을 준다 → "고르실 선택지가 이미 있나요?" → 있음 = **결정** / 없음 = **진단**
- 기준이 판정한다 → **점검**
- 읽는 분이 본다 → "보는 순서를 정해 드릴까요, 직접 골라 보시게 할까요?" → 정해 준다 = **조망** / 직접 = **탐색**

두 번이면 끝난다. 세 번째 질문이 필요하면 산출물이 둘이라는 신호다.

### 점검형과 탐색형이 헷갈릴 때

둘 다 다시 연다. 가르는 기준은 **누가 틀을 정하는가**다.
점검형은 저자가 구성을 고정하고 기준이 판정한다. 탐색형은 독자가 그때그때 고르고 판정이 없다.
"영업일보를 매일 갱신"은 점검형, "영업일보를 날짜 골라서 볼 수 있게"는 탐색형이다.
둘 다 원하면 산출물이 둘이다.

### 옛 이름 (v0.11 이전)

| 옛것 | 지금 |
|---|---|
| `diagnostic` 진단 | `diagnose` 진단형 |
| `choice` 선택 | `decide` 결정형 |
| `watch` 감시, `track` 추적 | `check` 점검형 |
| 탐색형 제품군 | `explore` 탐색형 |
| `stance: data_only` | 없앴다. 판단 없이 보여주려면 조망형 |
