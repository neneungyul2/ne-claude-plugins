# 산출물 유형 (report-types)

## 0. 왜 유형을 나누나

형태가 하나뿐이면 모든 보고가 같은 모양으로 나온다. 그건 규칙이 아니라 **관성**이다.

형태를 정하는 근본 변수는 주제(채널·품목·매출)가 아니다. **독자가 무엇을 모르는가**다.
같은 매출 데이터로도, 독자가 "왜 이런지"를 모르면 진단이고 "지금 괜찮은지"를 모르면 감시다.
화면은 완전히 달라진다.

판단은 이 사슬을 따라간다.

```
관찰 → 해석 → 판단 → 선택지 → 결정 → 실행
```

산출물은 **독자의 앎이 끊긴 지점에서 시작해, 독자의 권한이 시작되는 지점에서 멈춘다.**
어디서 시작해 어디서 멈추는지가 곧 형태다.

---

## 1. 네 유형

"모른다"의 네 가지 종류다.

| 독자가 모르는 것 | 유형 | 주인공 | 결론의 모양 | 없으면 실패하는 것 |
|---|---|---|---|---|
| 무슨 일이 일어나고 있나 | `diagnostic` **진단** | 근거 exhibit 하나 | "실은 X다" | 가설과 그것을 깨려는 검증 |
| 어느 쪽이 나은가 | `choice` **선택** | 옵션 × 판단기준 표 | "X를 하자. Y가 아닌 이유는" | 탈락시킨 안과 그 이유 |
| 지금 괜찮은가 | `watch` **감시** | 지표 행과 임계값 | "이상 없음" 또는 "여기가 벗어났다" | 임계값. 없으면 매번 사람이 판정한다 |
| 계획대로 가고 있나 | `track` **추적** | 시간축과 기준선 | "이 속도면 X에 도달/미달" | 기준선과 남은 시간 |

다섯 번째가 떠오르면 대개 이 중 하나의 **시제나 선택지 수만 다른 것**이다 —
성과 보고는 과거형 진단, 예산 요청은 선택지가 둘인 선택.

**유형에 억지로 끼우지 않는다.** 정말 안 맞으면 새로 만들고, 같은 것이 반복해서
나오면 그때 이 표에 추가한다. 없는 유형을 위해 미리 자리를 비워두지 않는다.

**한 산출물은 한 유형이다.** "진단하고 나서 계속 추적하고 싶다"는 산출물이 둘이라는 뜻이다.
진단 리포트를 먼저 내고, 추적 대시보드는 별도로 만든다. 하나에 섞으면 둘 다 안 된다.

---

## 2. 더 큰 갈래 — 한 번 읽는 것과 다시 여는 것

네 유형은 둘씩 묶인다. 이 갈래가 유형 차이보다 크다.

| | 진단 · 선택 | 감시 · 추적 |
|---|---|---|
| 읽는 횟수 | **한 번** | **반복해서 연다** |
| 결론 | 그 시점에 고정된다 | 열 때마다 달라진다 |
| 갱신 | 없다. 그때의 판단 기록이다 | **갱신이 본질이다** |
| "특이사항 없음" | 실패다 | **정상 출력이다** |
| 전달 | 파일 | 링크·아티팩트 (다시 열 수 있어야) |
| 데이터 시점 | 각주에 한 번 | **화면 상단에 항상** |
| 제목 | 서술형 결론 | 명사구 허용 (결론이 매번 바뀌므로) |

감시·추적 산출물에 **"언제 데이터인가"가 안 보이면 그건 고장난 것이다.**
다시 여는 화면에서 가장 먼저 확인해야 할 것은 값이 아니라 신선도다.

---

## 3. 유형별 필수와 해당 없음

기존 규칙 중 여럿은 **진단형을 전제로 쓰여 있었다.** 유형별로 갈라 적는다.
`—`는 해당 없음이고, 없다고 감점하지 않는다.

| 스펙 요소 | 진단 | 선택 | 감시 | 추적 |
|---|---|---|---|---|
| `key_takeaway.text` | 필수 (판단 문장) | 필수 (추천안) | **현재 상태 판정** (갱신마다 다시 씀) | 필수 (도달 전망) |
| `key_takeaway.ask` | 필수 | 필수 | **이상일 때만** | 이탈 시 필수 |
| `brief.tension` | 필수 | 필수 | — | 필수 (계획 대비 격차) |
| `three_minute_story` | 필수 | 필수 | — | — |
| `actions` | 3~5개 필수 | 추천 1 + 대안 | **정상이면 0개가 정답** | 이탈 항목만 |
| `weight: primary` | exhibit 하나 | **옵션 표가 primary** | **KPI 행이 primary** | 시간축 차트 하나 |
| 히어로 요약 목록 | action_title 순서대로 | 옵션별 한 줄 | **이탈 항목만** (정상이면 없음) | 기준선 대비 한 줄 |
| exhibit 수 | 3~7 | 옵션 수에 따름 | **고정 슬롯** (매번 같아야 한다) | 1~3 |
| `narrative_order` | `lead_with_ending` | `lead_with_ending` | `lead_with_ending` | `chronological` 기본 |
| 임계값 정의 | — | 판단기준 가중치 | **필수** | 기준선이 대신한다 |
| `question_type` 주류 | `deviation` `composition` | `comparison` `ranking` | `single_value` `deviation` | `trend` `change_2point` |

### `stance`가 유형 위에 걸린다

위 표는 `stance: judgment`(기본)일 때다. 브리프가 `stance: data_only`면
**유형과 무관하게** 아래가 해당 없음으로 내려간다.

| 요소 | `data_only`에서 |
|---|---|
| `key_takeaway.ask` | 해당 없음 |
| `actions` | 해당 없음 |
| `key_takeaway.text` | **남는다.** 단 판단이 아니라 **무엇이 보이는가**로 쓴다 |
| `action_title` | **남는다.** 차트를 읽는 방법이지 제안이 아니다 |

"자사는 이 시장에 제품이 없다", "대응이 필요하다" 같은 문장은 `data_only`에서
빠지는 쪽이다. 읽는 사람이 이미 아는 사실을 결론 자리에 놓지 않는다.

---

### 유형이 바꾸는 것 — 특히 주의

**감시형은 `actions`가 비어 있는 것이 정답일 수 있다.** "특이사항 없음"을 명시적으로 쓰고
끝낸다. 억지로 액션을 만들면 다음부터 아무도 그 칸을 안 읽는다.

**감시형은 exhibit 구성이 매번 같아야 한다.** 이번 달에 흥미로운 것이 생겼다고 섹션을
추가하면, 독자가 매번 화면을 새로 익혀야 한다. 흥미로운 것이 생겼으면 그건 **별도의
진단 리포트**다.

**선택형은 탈락시킨 안을 지우지 않는다.** "왜 Y가 아닌가"가 없으면 독자는 추천을 검증할
수 없고, 검증할 수 없는 추천은 승인되지 않는다.

**추적형은 결론부터 가지 않아도 된다.** 어디서 출발해 지금 어디인지가 이야기 자체다.
다만 "이 속도면 어떻게 되는가"는 화면 안에 있어야 한다.

## 4. 유형별 뼈대

**레이아웃이 아니라 부품 목록이다.** 개수와 순서는 스펙이 정한다.

### 진단 (`diagnostic`)

```
판단 한 줄 + 요청
① 가장 큰 자리 — 판단의 근거          ← weight: primary
② 반례 차단 — "다른 설명은 아닌가"
③ 한계 — 이 데이터로 답 못 한 것
인사이트 → 액션
```

가설을 세우고 **그것을 깨려고 시도한 흔적**이 있어야 한다. 뒷받침만 모으면 그건 진단이 아니다.

### 선택 (`choice`)

```
추천안 + 요청
옵션 × 판단기준 표                    ← weight: primary
왜 나머지가 아닌가
뒤집히는 조건 — 무엇이 달라지면 답이 바뀌나
```

판단기준은 **옵션을 보기 전에** 정의한다. 나중에 정하면 원하는 답에 맞춰진다.

### 감시 (`watch`)

```
데이터 시점 (가장 위, 항상)
지표 행 + 임계값 대비                 ← weight: primary
이탈 항목만 펼침 (없으면 "이상 없음")
정상 항목은 접어둔다
```

고정 슬롯. 매번 같은 자리에 같은 지표가 있어야 눈이 익는다.

### 추적 (`track`)

```
데이터 시점 (가장 위, 항상)
시간축 + 기준선 + 현재 위치            ← weight: primary
이벤트 마커 — 무엇이 언제 있었나
이 속도면 어떻게 되는가
```

기준선이 없으면 추적이 아니라 그냥 추이다.

---

## 5. 유형을 정하는 방법

**사용자에게 네 유형 중 고르라고 묻지 않는다.** 우리 분류를 사용자가 배울 이유가 없다.
사용자가 이미 한 말에서 읽어내고, 추정한 근거와 함께 확인받는다.
방법은 `skills/frame-question/SKILL.md`에 있다.
