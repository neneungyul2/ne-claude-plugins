# 예시 — 이 폴더는 비어 있다

**의도적으로 비웠다.** `quick-minimal.json`이 있었을 때, "스키마 확인용" 라벨을 붙여도
exhibit 개수·순서·차트 종류·문구를 그대로 베끼는 습관이 생겼다 — 완결된 예시는
아무리 "복사하지 말라"고 적어도 결국 형태를 고정시킨다. `spec-schema.md` 변경 이력
2.5를 참고.

## 스키마가 어떤 모양인지 확인하려면

완결 예시가 아니라 **스키마 문서의 코드 조각**을 본다.

- `skills/plan-report/references/spec-schema.md` — 결정·진단·점검·조망형 스펙. §0이 코드 조각을 읽는 법을 설명한다
- `skills/plan-explore/references/explore-spec-schema.md` — 탐색형 스펙

각 필드 옆 값·중첩 구조만 보고, 값 자체나 개수·순서는 가져오지 않는다.

## 예시에서 뽑아냈던 좋은 패턴은 어디 있나

완결 예시 HTML이 실제로 보여주던 좋은 패턴 세 가지는 **글로 옮겨 `design-rules.md`에
있다.** HTML을 지운 뒤에도 원칙은 남는다.

| 패턴 | 어디 |
|---|---|
| 목차 — 지금 어디를 보고 있는지 항상 안다 | `design-rules.md` §13 |
| 결론이 맨 위 — 핵심 결론과 요청이 히어로에 먼저 온다 | `design-rules.md` §1 |
| 헤더 위계 — 번호와 제목이 층을 명확히 가른다 | `design-rules.md` §2, §6 |

## 렌더러가 스펙을 못 읽을 때

완결 예시로 대조하지 않는다. 스펙 JSON에서 렌더러가 실제로 멈춘 지점을 찾아
그 필드의 코드 조각을 스키마 문서에서 다시 읽는다. 여전히 안 잡히면 사용자에게
구체적인 오류(어느 필드, 어떤 값)를 보여주고 함께 확인한다.
