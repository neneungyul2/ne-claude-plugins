# 스토리 규칙 (storytelling)

보고서는 **데이터를 보여주는 것**이 아니라 **이야기를 하는 것**이다.
이 문서는 무엇을 어떤 순서로 말할지에 대한 규칙이다. 차트 규칙은 `chart-rules.md`,
디자인 규칙은 `design-rules.md`에 있다.

근거: Cole Nussbaumer Knaflic, *Storytelling with Data* (2015) 1·7·8·9장.
분석 전문은 프로젝트 문서 `storytelling-with-data_전문분석.md`.

---

## 1. 탐색과 설명은 다른 일이다

> 굴 100개를 열어 진주 두 개를 찾는 것이 **탐색(exploratory)**,
> 진주 두 개만 내미는 것이 **설명(explanatory)**이다.

가장 흔한 실패는 분석을 끝낸 뒤 "이만큼 일했다"를 증명하려고 굴 100개를 다 보여주는 것이다.
**독자에게 굴을 다시 열게 만들지 않는다.**

- 탐색 단계에서 만든 차트를 그대로 보고에 쓰지 않는다
- 탐색 단계에서는 **강조를 쓰지 않는다.** 하나를 강조하면 다른 것이 안 보이게 되므로
- 설명 단계에서는 **반드시 강조한다.** 독자가 스스로 결론을 내게 두지 않는다

---

## 2. Big Idea — 한 문장

보고서 전체가 하나의 문장으로 압축되어야 한다. 3요소:

1. **당신의 고유한 관점**을 담을 것 — 사실 나열이 아니라 판단
2. **무엇이 걸려 있는지**를 전달할 것 — 하지 않으면 무엇을 잃는가
3. **완전한 한 문장**일 것

```
[분석 근거]에 따르면 [판단]이므로, [요청]을 권고한다.
```

예:
> "시장 가격 추이 분석에 근거해, 경쟁력을 갖추려면 소매가 $150~$200 범위로 출시할 것을 권고한다."

**발견에서 멈추면 Big Idea가 아니다.** "가격이 하락했다"는 관찰이고,
"그러므로 이 범위로 출시하자"까지가 Big Idea다.

스펙에서는 `key_takeaway.text`(판단) + `key_takeaway.ask`(요청)로 나눠 담고,
화면에서는 **히어로 블록 안에 둘 다** 넣는다. 액션 표는 그것의 전개일 뿐이다.

## 3. 3분 스토리

3분만 주어진다면 무엇을 말할 것인가. **슬라이드 없이 말로** 할 수 있어야 한다.

- 이걸 할 수 있으면 30분 슬롯이 10분, 5분으로 줄어도 대응된다
- `frame-question` 단계에서 문단 하나로 적어 두고 `brief.three_minute_story`에 남긴다
- 이 문단이 안 써지면 **아직 무엇을 말할지 정해지지 않은 것이다.** 데이터로 돌아간다

---

## 4. 3막 구조 — 긴장이 없으면 이야기가 아니다

| 막 | 내용 | 보고서에서 |
|---|---|---|
| **1막 설정** | 주인공·세계를 세우고 **사건이 터진다** | 맥락 + 무엇이 달라졌나 |
| **2막 갈등** | 해결 시도. 상황이 악화된다 | 증거·검증·반증 |
| **3막 해결** | 절정 → 1막의 질문에 답한다 | 판정 + 행동 요청 |

**주인공은 독자다.** 우리가 아니다. 이야기는 독자의 문제여야 그들이 해법에 이해관계를 갖는다.

> **"우리는 문제가 없는데요"라고 생각된다면 다시 생각하라.**
> 모든 것이 장밋빛이고 앞으로도 그럴 이야기는 흥미롭지도, 행동을 부르지도 않는다.

긴장의 정의(Duarte): **현재 있는 것(what is)과 있을 수 있는 것(what could be) 사이의 갈등.**

`brief.tension`에 한 줄로 적는다.

```
what_is:       지금 우리가 이것을 어떻게 다루고 있나 (한 줄)
what_could_be: 데이터에 비추면 어떻게 다뤄야 하나 (한 줄)
```

두 줄이 **같은 것을 두 가지로 말하고 있어야** 긴장이 생긴다.
서로 다른 두 가지를 적었으면 그건 긴장이 아니라 항목 두 개다.

불릿으로 채운 슬라이드(관습적 수사)의 문제는, **설득하는 동안 독자가 머릿속에서
당신과 논쟁한다**는 것이다. 설득에 성공해도 지적 수준에 그친다.

## 5. 서사 순서 — 두 가지 중 고른다

| 순서 | 언제 | 형태 |
|---|---|---|
| **`chronological`** (시간순) | 신뢰를 쌓아야 할 때. 독자가 과정을 보고 싶어할 때 | 문제 → 데이터 → 분석 → 발견 → 권고 |
| **`lead_with_ending`** (결론부터) | 이미 신뢰가 있을 때. 독자가 "그래서?"만 원할 때 | 권고 → 근거 → 상세 |

결론부터 가면 독자가 **어떤 렌즈로 나머지를 볼지** 즉시 안다는 부가 효과가 있다.

평소와 다른 순서를 쓸 때는 **그렇게 한다고 먼저 알린다.**
> "오늘은 요청부터 말씀드리겠습니다. 근거는 그 뒤에 놓았습니다."

`brief.narrative_order`에 기록한다. 우리 HTML 산출물은 기본이 `lead_with_ending`이다
(히어로에 결론과 요청이 먼저 온다). 시간순이 필요하면 exhibit 배치를 바꾼다.

## 6. 반복 — Bing, Bang, Bongo

1. **Bing** — 무엇을 말할지 말한다 → **히어로의 섹션 헤더 목록**
2. **Bang** — 말한다 → **exhibit 본문**
3. **Bongo** — 말한 것을 요약한다 → **인사이트·액션 표**

만드는 사람에게는 중복으로 느껴지지만 **독자에게는 편안하다.** 세 번 만나면 남는다.

- 히어로의 요약 항목 = 각 exhibit의 `action_title`. **순서도 같아야 한다**
- 액션 표의 "발견" 열은 해당 exhibit의 결론을 다시 쓴 것이어야 한다
- **반복 가능한 한 문장**(repeatable sound bite)을 만든다. 독자가 다른 사람에게
  그대로 옮길 수 있는 문장이어야 한다

## 7. 위에서부터 좁혀 들어간다 (cascading)

앞 섹션이 틀을 세우지 않은 채 뒤 섹션의 세부 수치를 먼저 던지면, 독자 머릿속에
비교 대상이 없어 읽히지 않는다. **"다르다", "낮다", "바뀌었다"는 말은
무엇과 비교하는지가 먼저 서 있어야 성립한다.**

권장 골격:

```
① 규모     — 이것이 무엇이고 얼마나 큰가
② 대상     — 누가 관련되어 있는가
③ 전체 그림 — 대체로 어떠한가          ← 여기서 비교 틀이 선다
④ 차이     — 그중 무엇이 다른가        ← 이제 "다르다"가 읽힌다
⑤ 한계     — 이 판단이 서 있는 지반
```

**핵심 결론부에는 세부 수치를 넣지 않는다.** 각 섹션의 `action_title`만 나열한다.
세부는 해당 섹션에서 처음 만나게 한다.

## 8. 스토리가 전달됐는지 검사하는 4가지

`plan-report` 자체검사와 `build-html` 검수에서 반드시 돈다.

### ① 수평 논리 (horizontal logic)
**exhibit의 `action_title`만 순서대로 읽어서 전체 스토리가 되는가.**
서술형 제목("지역별 현황")이면 작동하지 않는다. **액션 타이틀**이어야 한다.

읽어 보고 아래에 걸리면 고친다:
- 제목만으로 결론이 안 나온다 → 제목이 서술형이다
- 순서가 뒤죽박죽이다 → exhibit 순서가 데이터 순서로 돼 있다
- 중간이 비어 논리가 점프한다 → exhibit이 빠졌다

### ② 수직 논리 (vertical logic)
**한 exhibit 안의 모든 정보가 서로를 보강하는가.**
제목 ↔ 차트 ↔ `so_what` ↔ 각주가 같은 것을 말하는가. 무관한 정보가 없는가.

### ③ 역스토리보딩 (reverse storyboarding)
완성본을 위에서 아래로 넘기며 **각 블록의 요점을 한 줄씩 적는다.**
그 목록이 `brief`에서 합의한 질문 목록과 같아야 한다. 다르면 구조를 고친다.

### ④ 제3자 시선 (fresh perspective)
맥락을 모르는 사람에게 보여주고 **소리 내어** 말하게 한다 —
어디를 먼저 보는지, 무엇이 중요하다고 읽히는지, 어디서 질문이 생기는지.
만든 사람은 자기 산출물을 독자의 눈으로 볼 수 없다.

## 9. 전달 매체가 밀도를 정한다

```
라이브 발표 ←──────────────────────────→ 배포 문서
발표자가 통제                        독자가 통제
디테일 적게                          디테일 많이
빈 화면에서 한 겹씩                  한 화면에 주석 전부
```

둘을 한 산출물로 겸하려 하면 **slideument**(발표도 문서도 아닌 것)가 된다.

**우리 HTML 산출물은 오른쪽 끝이다.** 발표자가 옆에 없다.
→ 각 exhibit의 "그래서 무엇인가"가 **화면 안에 글자로** 있어야 한다.
→ 주석·콜아웃을 아끼지 않는다. 대신 **강조는 10% 이하**를 지킨다.

발표용이 따로 필요하면 `build-doc`으로 슬라이드를 뽑고, 거기서는 반대로
한 장에 한 겹씩 쌓는다(`emphasis_steps`가 곧 슬라이드 장수가 된다).

## 10. 새 형식을 받아들이게 하는 법

보고 형식을 바꾸면 저항이 온다. 저항이 **변화 거부**인지 **설계 결함**인지부터 가른다.
이해관계 없는 제3자에게 보여주면 대개 갈린다.

받아들이게 하는 4가지:
1. **왜 달라지는지 말로 설명한다** — 새 방식으로 무엇을 새로 볼 수 있는가
2. **나란히 보여준다** (before–after)
3. **여러 안을 만들어 고르게 한다** — 처방하지 말고 의견을 구한다
4. **발언권 있는 한 사람을 먼저 설득한다**

## 11. 하지 않는 것

- 발견에서 끝내기 → 요청까지가 결론이다
- 청중을 "이해관계자"로 뭉뚱그리기 → **한 사람**으로 특정한다
- 데이터를 다 보여주고 독자가 알아서 결론 내게 두기
- 유리한 데이터만 보여주기 → 한 명만 구멍을 찾아도 주장 전체가 버려진다.
  반대 증거와 한계를 함께 적는다
- 지루함을 막으려고 형식을 바꾸기 → 주의를 잡는 것은 **스토리**다
- 만들기 전에 구조를 합의하지 않고 바로 화면부터 만들기 →
  만든 것에 애착이 생겨 틀려도 못 버린다. **`frame-question`을 건너뛰지 않는다**
