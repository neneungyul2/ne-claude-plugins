# 디자인 규칙 (design-rules)

quick·report, HTML·문서 어디에나 동일하게 적용한다.
구현 토큰과 컴포넌트는 `references/html-template.html`에 있다. **여기는 판단 기준이다.**

근거가 되는 원전은 `references/storytelling.md`에 정리해 두었다.

---

## 0. 먼저 — 한국어 줄바꿈

```css
body{ word-break:keep-all; overflow-wrap:anywhere; }
h1,h2,h3,p,li,td,th,text{ word-break:keep-all; overflow-wrap:anywhere; }
```

**이 두 줄이 없으면 한국어가 단어 중간에서 잘린다.** "상품이" → "상 / 품이".
브라우저 기본값(`break-word`)은 영어 기준이라 한국어에서는 어절을 무시한다.

- `keep-all` — 어절 단위로 끊는다
- `overflow-wrap:anywhere` — 긴 URL·영문이 박스를 넘는 것만 예외로 끊는다

SVG `<text>`에도 적용한다. 라벨이 길면 CSS가 아니라 **`<tspan>`으로 직접 줄을 나눈다.**

## 1. 배치 — 결론이 먼저다

```
헤더        제목 · 기준 배지 (스티키)
  ↓
히어로      핵심 결론 (화면에서 가장 큰 글자) + 섹션 헤더 목록 + 요청 1줄
  ↓
KPI         2~4개. 값 + 비교
  ↓
① exhibit   번호 배지 + action_title
② exhibit
  ↓
인사이트·액션   3~5개
  ↓
확인 필요 · 각주
```

- **핵심 결론보다 큰 요소를 만들지 않는다.** 로고·제목이 결론보다 크면 안 된다
- 결론 안에서 수치와 결론어는 형광펜(`emphasis`)으로 칠한다. 2~4개만. 다 칠하면 강조가 아니다
- **히어로 요약은 각 exhibit의 `action_title`을 순서대로 나열한다.** 요약을 따로 쓰지 않는다.
  이것이 수평 논리 검사이자 청중에게 주는 목차다 (`storytelling.md` 참조)
- **결론은 요청으로 끝난다.** 발견에서 멈추지 않는다. `key_takeaway.ask`가 히어로 안에 있어야 한다
- exhibit 순서는 결론을 뒷받침하는 순서다. 데이터 순서가 아니다
- 헤더 우측에는 **기준 배지**만 둔다 (`기준: 순출고 · 2026-08 · 단위 부`)

**위에서부터 좁혀 들어간다.** 앞 섹션이 틀을 세우지 않은 채 뒤 섹션의 세부 수치를 먼저 던지면
독자 머릿속에 비교 대상이 없어 읽히지 않는다. 규모 → 대상 → 전체 그림 → 차이 → 한계 순.

## 2. 카드와 여백

시안 기준이다.

| 요소 | 값 |
|---|---|
| 블록 테두리 | `1px solid var(--line2)` |
| 블록 라운드 | `14px` |
| 블록 패딩 | `22px 24px` |
| 블록 간격 | `14px` |
| 섹션 헤더 위 여백 | `30px` |
| 본문 폭 | `max-width:1120px` |

- exhibit은 **카드 하나**다. 구분선만으로 나열하지 않는다
- 섹션 헤더에는 번호 배지(22×22, 라운드 6px, 잉크 배경)를 붙인다. 목차·앵커와 번호가 같아야 한다
- 섹션 간격 > 요소 간격 > 요소 내부 간격. 이 순서가 뒤집히면 묶음이 잘못 읽힌다
- 모바일 폭에서도 좌우 여백 16px 이상

**여백은 발표의 pause와 같다.** 공간이 남는다는 이유로 데이터를 더 넣지 않는다.
정말 중요한 것 하나는 그 블록에 그것만 둔다.

## 3. 게슈탈트 — 무엇을 지워도 되는가

무엇이 clutter인지는 취향 문제가 아니다. 사람이 어떻게 보는지에서 나온다.

| 원칙 | 사람은 이렇게 본다 | 그래서 이렇게 한다 |
|---|---|---|
| **근접** | 가까이 있으면 한 묶음 | **범례를 없애고 데이터 옆에 라벨을 붙인다.** 표는 간격만으로 행/열을 나눈다 |
| **유사** | 색·모양이 같으면 한 묶음 | **라벨 색을 데이터 색과 같게** 한다. 문장의 강조색과 차트의 강조색을 맞춘다 |
| **둘러싸기** | 함께 둘러싸이면 한 묶음 | **옅은 배경 음영만으로 충분하다.** 실적/예측, 권고 범위 등을 테두리 없이 구분 |
| **닫힘** | 일부가 없어도 전체로 본다 | **차트 테두리·배경 박스는 지운다.** 지워도 그래프는 완결돼 보인다 |
| **연속** | 눈은 가장 매끄러운 경로를 만든다 | **y축 선을 지워도** 일정한 여백 덕에 막대가 정렬돼 보인다 |
| **연결** | 선으로 이어지면 한 묶음. **색·크기보다 강하다** | 선그래프·슬로프그래프가 작동하는 이유. 100% 누적 막대의 **동일 세그먼트 점선 연결**도 이것 |

지우기 전 자문: **"이걸 빼면 뭐가 달라지나? 안 달라진다? 빼라."**
귀엽다고, 만드느라 고생했다고 남기지 않는다.

## 4. 색

색은 **의미가 있을 때만** 쓴다.

| 용도 | 토큰 |
|---|---|
| 강조 1색 | `--blue` `#3182f6` (진한 쪽 `--blueDk`) |
| 계열 구분 | `--g1`~`--g5` 단색 계조. **색상환을 돌지 않는다** |
| 계열이 성격상 갈릴 때만 | `--violet` `--teal` `--amber` — 3개까지 |
| 증가 / 감소 | `--up` `#00b25b` / `--dn` `#f04452` |
| 주의 | `--warn` `#c47b00` + `--warnBg` |
| 배경 강조 | `--blueBg` `#e8f3ff` (히어로·액션 블록) |

- **한 화면에 강조색 1개.** 둘을 강조하면 강조가 아니다
- 기본색은 **검정이 아니라 회색**이다. 회색을 기준으로 두어야 강조색의 대비 폭이 커진다
- **그래프·섹션 제목은 진회색(`--sub`)**. 순수 검정은 강조용으로 아껴 둔다
- 증가가 나쁜 지표(반품률·재고일수)는 색을 반대로 쓴다. 자동으로 초록을 붙이지 않는다
- 무지개 팔레트, 기본 팔레트 그대로 쓰기 금지
- 색만으로 정보를 구분하지 않는다. 라벨·위치를 함께 쓴다
- 본문 텍스트 대비 4.5:1 이상

**색맹** — 남성 약 8%, 여성 0.5%가 적–녹 구분이 어렵다.
→ **빨강–초록 조합을 피한다.** 긍정/부정을 나눠야 하면 **파랑–주황**을 쓴다.
부득이 적–녹을 쓸 때는 굵기·부호(+/−)·채도 같은 **두 번째 신호를 반드시 함께** 준다.
현 팔레트의 `--blue`/`--amber` 조합은 이 이유로 선택된 것이다.

**색 의미는 문서 전체에서 고정한다.** 색이 바뀌면 독자는 "무언가 바뀌었다"고 읽는다.
**지루함을 막기 위해 색이나 차트 종류를 바꾸지 않는다.** 주의를 잡아 두는 것은 디자인이 아니라 스토리다.

**라이트 전용이다.** 보고 문서는 보는 사람마다 색이 달라지면 안 된다.
어두운 배경은 시선을 데이터가 아니라 배경으로 끌고, 읽기 어렵다.

## 5. 강조 — 상한과 서열

> **강조는 전체 디자인의 10%를 넘지 않는다.** (Lidwell, *Universal Principles of Design*)
> 강조 비율이 올라갈수록 강조 효과는 희석된다.

**매와 비둘기** — 비둘기 떼 속의 매는 찾기 쉽다. 새의 종류가 늘수록 매는 찾기 어려워진다.
서로 다르게 만드는 것이 많아질수록 **어떤 것도 돋보이지 않는다.**

강조 기법 서열:

| 기법 | 쓰임 |
|---|---|
| **볼드** | 기본. 노이즈를 가장 적게 더하면서 명확히 구분한다 |
| **색** | 아껴서, 보통 다른 기법과 함께 |
| **크기** | 상대 크기 = 상대 중요도. 같은 중요도면 같은 크기 |
| **대문자·짧은 어구** | 제목·라벨·키워드. 스캔이 쉽다 |
| 이탤릭 | 노이즈는 적으나 눈에 덜 띄고 가독성이 떨어진다 |
| 밑줄 | 노이즈를 더하고 가독성을 해친다. 거의 쓰지 않는다 |
| 다른 서체 | **쓰지 않는다.** 방해 없이 차이를 만들기 어렵다 |
| 반전·깜빡임 | 쓰지 않는다 |

**작업 순서: 먼저 전부 배경으로 민다.** 그래야 무엇을 앞으로 끌어낼지 명시적으로 결정하게 된다.
전부 회색으로 만든 뒤 → 데이터를 축보다 굵게 → 강조 대상만 색·마커·라벨.

**모든 텍스트는 같은 크기가 기본이다.** 다르게 한 것은 전부 의도된 결정이어야 한다.

## 6. 타이포그래피

| 역할 | 크기 / 굵기 |
|---|---|
| 핵심 결론 | 26px / 800 / `letter-spacing:-.03em` |
| 섹션 제목 | 16.5px / 700 |
| KPI 값 | 32px / 800 / tabular-nums |
| 본문 | 14px / 400 |
| 각주 | 11.5px / `--dim` |

- 폰트는 Pretendard → 시스템 기본 순으로 폴백. **웹폰트를 불러오지 않는다**
- 위계는 3단계까지. 그 이하는 색으로 구분한다
- 수치는 `font-variant-numeric: tabular-nums`. 자릿수가 흔들리면 비교가 안 된다
- 천단위 구분 기호. 단위는 축이나 각주에 한 번만
- 한 줄 길이 34em 이하

**"읽기 어려우면 하기도 어렵다."** (Song & Schwarz, 2008)
같은 내용도 까다로운 서체로 주면 사람들은 그 일이 **더 어렵다고 판단하고 시도하지 않는다.**
복잡해 보일수록 독자는 이해에 시간이 더 걸릴 거라 느끼고, 그 시간을 쓰지 않는다.

## 7. 정렬

- **중앙정렬을 쓰지 않는다.** 좌우 어디에도 깨끗한 선이 생기지 않아, 공들인 배치도 지저분해 보인다
- 제목·축 제목·범례는 **좌상단 정렬**. 독자가 데이터에 닿기 전에 읽는 법을 먼저 알게 한다
- y축 제목은 **최상단 눈금과 수직 정렬**, x축 제목은 **최좌측 눈금과 수평 정렬**
- 요소들이 세로·가로로 깨끗한 선을 이루게 배치한다
- **대각선 요소 금지.** 45도 회전 텍스트는 평균 **52% 느리게**, 90도는 **205% 느리게** 읽힌다
  (Wigdor & Balakrishnan, 2005). x축 라벨이 안 들어가면 기울이지 말고 **가로막대로 바꾼다**

독자는 **좌상단에서 시작해 z자**로 훑는다. 위쪽이 가장 비싼 자리다.
중요한 것을 찾으러 아래로 내려가게 만들지 않는다.

---

## 8. 텍스트 — 없으면 독자가 멈춘다

> **모든 차트에 제목이 필요하고, 모든 축에 축 제목이 필요하다.** 예외는 극히 드물다.

없으면 독자는 멈춰서 "내가 무엇을 보고 있지?"를 묻는다. 그 순간 인지 자원이 내용이 아니라
읽는 법을 알아내는 데 쓰인다.

- **두 사람이 같은 그림을 보고 같은 결론에 도달하리라 가정하지 않는다.**
  도달하기를 원하는 결론이 있으면 **말로 적는다**
- 제목 자리에 서술형("2026년 8월 실적")을 쓰지 않는다. **액션 타이틀**("8월 지출이 예산을 초과했다")
- 주석(annotation)으로 데이터의 미묘한 지점·외부 요인을 그래프 위에 직접 적는다
- 약어는 처음 쓸 때 풀어 쓴다. 전문 용어는 정의한다
- 짧은 단어, 적은 단어. 똑똑해 보이려다 독자를 바보로 만들지 않는다
- `$`·`%`·천단위 콤마는 숫자에서 빼지 않는다. 제목에만 적으면 독자가 기억해야 한다

## 9. 데이터-잉크 비율

숫자를 전달하지 않는 픽셀은 지운다.

지울 것 — 세로 격자선, 차트 테두리, 배경 박스, 그림자, 그라데이션(히어로 제외),
축 눈금 표시, **불필요한 소수점과 후행 0**, 항목 8개 이하일 때의 y축 눈금,
**목적 없는 데이터 마커**(선이 이미 보여주는 것을 다시 처리하게 만든다)

남길 것 — 축 제목과 단위, 값 라벨(항목 8개 이하면 막대 위에 직접), 기준선·목표선

- **후행 0은 정보가 없으면서 숫자를 복잡해 보이게 한다.** `300.00` → `300`
- **데이터 마커와 값 라벨은 아껴 쓸 때만 "여기 보세요" 신호가 된다.** 전부 붙이면 다시 잡동사니다.
  **주석이 가리키는 지점에만** 붙인다
- 격자선을 남길 거면 얇고 회색으로. 데이터와 시각적으로 경쟁시키지 않는다
- **범례는 clutter다.** 데이터에 직접 라벨을 붙이고 범례를 지운다.
  누적 막대는 **첫 막대의 각 세그먼트에 이름을 직접** 쓴다.
  범례가 꼭 필요하면 차트 위 좌상단에 두고, 계열 순서와 범례 순서를 맞춘다

---

## 10. 각주

모든 exhibit에 **출처 · 기간 · 단위 · 집계기준** 4요소. 본문보다 작게, 회색으로.

- 각주는 exhibit 바로 아래. 문서 끝으로 몰지 않는다
- 데이터 한계(누락·추정·제외 항목)를 각주에 쓴다. 숨기지 않는다
- 100% 누적을 쓸 때는 **각 범주의 절대 총량**을 각주에라도 함께 준다

---

## 11. 용어와 산식은 읽는 자리에서 풀어준다

읽는 사람이 모르는 말이 하나 있으면 리포트는 거기서 멈춘다.

| 상황 | 처리 |
|---|---|
| 축약어·사내 용어 | 첫 등장에 **점선 밑줄 + 호버 툴팁** |
| 한 문장으로 안 되는 계산 (산식 + 단계 2개 이상, 예외 조건 있음) | 옆에 **`i` 아이콘 → 모달** |
| 지표 정의가 사내에서 갈리는 것 | 툴팁에 **어느 기준인지** 함께 |

- 정의는 `references/metrics.md`에서 가져온다. 여기서 새로 만들지 않는다
- 확인되지 않은 정의는 `확인 필요`로 쓰고 `open_questions`에도 올린다
- 툴팁은 보조 수단이다. **툴팁을 봐야만 이해되는 화면은 이미 실패한 화면이다**

---

## 12. 묶은 항목은 열어볼 수 있어야 한다

"기타", "나머지 8개 지역", "상위 10 외"로 묶는 것은 화면을 읽히게 만드는 좋은 방법이다.
다만 **묶은 순간 그 안의 데이터가 사라진다.** 각주에 글로 나열하는 것으로는 부족하다.

- 묶은 항목에는 클릭 가능한 표시(`i` 아이콘 또는 클릭 행)를 둔다
- 클릭하면 **묶기 전 원자료 전체**를 모달로 보여준다. 여기서 또 줄이지 않는다
- 모달 상단에 합계와 전체 대비 비중을 적는다
- 스펙의 `group_detail`이 비어 있으면 렌더링하지 않고 되돌려 보낸다

## 13. 네비게이션

| 요소 | 언제 |
|---|---|
| 스티키 헤더 | 항상. 제목과 기준이 스크롤해도 보여야 한다 |
| 좌측 스티키 목차 | exhibit 3개 이상. 1420px 이상 화면에서만 표시 |
| 섹션 번호 배지 | 항상. 목차·앵커와 번호를 맞춘다 |
| 상단 탭 | exhibit 8개를 넘거나 성격이 갈릴 때만 |

- 목차 항목은 `nav_label`을 쓴다. `action_title`을 그대로 넣으면 목차가 아니라 문단이 된다
- 스크롤 위치에 따라 현재 섹션이 목차에서 강조돼야 한다
- 목차가 본문을 가리면 안 된다. 좁은 화면에서는 숨긴다

## 14. 인터랙션

인터랙션은 **마지막에** 붙인다. 없어도 성립하는 화면을 먼저 만든다.

- **툴팁** — 기본. 값·라벨·단위
- **모달** — 묶은 항목 전체, 계산 로직
- **강조 단계(`emphasis_steps`)** — 같은 차트, 같은 순서, 강조만 이동. 기본 상태가 곧 첫 단계
- **축 전환(`views`)** — 같은 질문을 다른 축으로. 강조 이동과 혼동하지 않는다
- **지도 ↔ 표 연동** — 지역 데이터에서는 기본
- 필터는 "이 화면을 보고 바로 이어서 나올 질문"에만. 걸면 현재 상태를 글자로 표시한다
- `localStorage`를 쓰지 않는다. 페이지 내 변수로만 상태를 유지한다

**우리 산출물은 배포 문서다.** 발표자가 옆에서 설명하는 슬라이드가 아니다.
따라서 각 화면의 "그래서 무엇인가"가 **화면 안에 글자로** 있어야 한다.
인터랙션은 그 위에 얹는 것이지, 그것을 대신하지 않는다.

## 15. 검수 — 눈으로 확인한다

만든 사람은 자기 화면을 객관적으로 볼 수 없다. 두 가지를 반드시 한다.

**① "눈이 먼저 가는 곳" 테스트**
화면을 띄우고 **눈을 감았다 뜬 뒤**, 시선이 처음 어디로 가는지 본다.
의도한 곳인가? 아니라면 강조가 잘못 걸린 것이다.

**② 제3자 시선**
맥락을 모르는 사람에게 보여주고 **소리 내어** 말하게 한다 —
어디를 먼저 보는지, 무엇이 중요하다고 읽히는지, 어디서 질문이 생기는지.

이 두 가지를 대신할 수 있는 검수는 없다. 렌더링하지 않고 코드만 보고 넘기지 않는다.

## 16. 하지 않는 것

- 제목에 "현황", "분석", "추이" 같은 명사구만 쓰기 → 서술형 결론으로
- 결론을 발견에서 끝내기 → **요청까지가 결론이다**
- exhibit만 늘어놓고 액션 없이 끝내기 → `actions` 3~5개는 report 필수
- **중앙정렬**
- **기울어진 텍스트**
- **지루함을 막으려고 색이나 차트 종류를 바꾸기**
- **같은 데이터를 다시 보여주면서 정렬을 바꾸기** → 인지 세금이다. 순서를 고정하고 강조만 옮긴다
- 데이터가 없는 구간을 0으로 그리기 → 끊어서 표시하고 각주에 명시
- 축을 잘라 차이를 부풀리기
- 한 화면에 서로 다른 집계 기준을 말없이 섞기
- 공간이 남는다고 데이터 더 넣기
- 애니메이션으로 주의를 끌기
- 다크모드 자동 전환
