# 산출물 계열 (product-lines)

**report-helper가 가장 먼저 읽는 문서다.** `report-types.md`(진단·선택·감시·추적)보다 앞선다 —
그 4유형은 전부 한 계열 안의 유형이고, 이 문서가 그 계열이 어디까지인지를 가른다.

---

## 0. 왜 나누나

`report-types.md`는 산출물을 "독자가 무엇을 모르는가"로 네 갈래로 나눈다. 이 질문은
전제가 하나 깔려 있다 — **모르는 것 하나를 밝혀서 전달한다.** 저자가 결론을 정하고,
독자는 그 결론을 받는다.

이 전제가 안 맞는 요청이 있다. "날짜·부문·지역을 바꿔가며 볼 수 있게", "필터 걸어서 보게",
"대시보드로 계속 열어보게" — 이런 요청은 **독자가 무엇을 볼지 그때그때 스스로 정한다.**
저자는 "무엇을 보여줄 수 있는 틀"만 만들고, "무엇을 지금 보는가"는 정하지 않는다.

`storytelling.md` §1의 구분을 그대로 가져온다 — 굴 100개를 열어 진주 2개를 찾는 것이
**탐색(exploratory)**, 진주 2개만 내미는 것이 **설명(explanatory)**이다.
지금까지의 report-maker는 전부 설명형이었다. 탐색형은 **독자에게 굴 상자를 통째로 건네고,
어떻게 여는지를 만들어 주는 일**이다.

둘을 하나의 파이프라인에 억지로 넣으면 안 된다. 감시형(watch)에 명사구 제목을 허용하려다
`action_title` 규칙이 흔들렸던 것과 같은 일이 훨씬 크게 반복된다 — 탐색형은 `key_takeaway`도,
`weight: primary`도, `action_title`도 원천적으로 성립하지 않는다. 스펙의 절반이
"해당 없음"이 되는 유형을 억지로 다섯 번째로 끼워넣지 않는다.

---

## 1. 판정 — 질문 하나로 가른다

유형 이름을 사용자에게 묻지 않는 것과 같은 이유로, **계열 이름도 묻지 않는다.**
아래 질문 하나로 스스로 판정한다.

> **"이 화면을 다음에 열 때, 무엇을 볼지도 그때 정하나요, 아니면 지금 정한 게 계속 유지되나요?"**

| 답 | 계열 |
|---|---|
| 지금 정한 구성이 계속 유지된다. 데이터만 최신으로 갈아끼운다 | **설명형** |
| 열 때마다 날짜·부문·지역 같은 걸 독자가 스스로 고른다 | **탐색형** |

사용자의 말에서 신호를 먼저 찾는다. 아래가 나오면 되묻지 않고 판정한다.

| 이런 말이 나오면 | 계열 |
|---|---|
| "정리해줘", "보고해야 해", "일보 만들어줘", "이상 있으면 알아야" | 설명형 (유형은 `report-types.md`가 가른다) |
| "필터로 볼 수 있게", "날짜·기간을 바꿔가며", "대시보드로 계속 쓸", "직접 파볼 수 있게" | **탐색형** |

### 감시형과 헷갈리는 지점

둘 다 "다시 연다"는 공통점이 있어 헷갈린다. 가르는 기준은 **누가 틀을 정하는가**다.

| | 감시형 (설명형의 한 유형) | 탐색형 |
|---|---|---|
| 구성 | 저자가 고정한다. **매번 같아야 한다** | 독자가 그때그때 고른다 |
| 갱신되는 것 | 데이터 값만 | 데이터 + 독자가 보는 조합 |
| "이상 없음" | 정상 출력이다 | 개념 자체가 없다 — 판정을 내리는 화면이 아니다 |
| 임계값 | 있다. `watch-thresholds.md` | 없다. 판단은 독자가 한다 |

"영업일보를 매일 갱신"은 감시형이다. "영업일보를 날짜 골라서 볼 수 있게"는 탐색형이다.
둘 다 원하면 **산출물 두 개**다 — 감시형 일보(고정 슬롯, 임계값 판정) +
탐색형 대시보드(과거 아무 날짜나 탐색). 하나로 합치면 둘 다 안 된다.

## 2. 설명형 — 지금까지의 파이프라인

```
report-helper → frame-question → load-data → plan-report → build-html/build-doc → verify-report
```

`report-types.md`의 진단·선택·감시·추적 4유형이 이 안에서 갈린다. 전부 이대로 쓴다.

---

## 3. 탐색형 — 별도 파이프라인

```
report-helper → frame-explore → plan-explore → build-explore → verify-report(탐색형 분기)
```

| 스킬 | 설명형 대응 | 하는 일 |
|---|---|---|
| `frame-explore` | `frame-question` | **질문이 아니라 축(axis)을 합의한다** — 독자가 무엇을 바꿀 수 있어야 하는가 |
| (load-data 재사용) | `load-data` | 어댑터는 같다. 다만 **긴 형식(long format) 원자료 전체**를 남긴다 — 특정 결론에 맞춰 자르지 않는다 |
| `plan-explore` | `plan-report` | 축·패널·데이터 그레인을 확정한 탐색 스펙(JSON)을 만든다 |
| `build-explore` | `build-html` | 공용 계산 엔진(`template/explore-engine.js`) 위에 패널을 조립한다 |
| `verify-report` | (같음) | 결론 검사 대신 **모든 축 조합에서 화면이 안 깨지는가**를 검사한다 |

**`action_title`·`key_takeaway`·`weight`는 탐색형에 없다.** 대신 성립하는 것 —
패널 제목은 "이게 뭘 보여주는지" 하나만 알 수 있으면 되는 **명사구**이고,
"이것만 봐도 알 수 있나"(자체검사 두 질문 중 ①)는 탐색형에도 그대로 적용된다.
"제일 큰 얘기가 먼저 나오나"(②)는 탐색형에는 순서라는 개념이 없어 해당 없음이다.

자세한 절차는 각 스킬의 SKILL.md에 있다.

---

## 4. 하지 않는 것

- 탐색형을 `report_type`의 다섯 번째 값으로 추가하지 않는다. 계열이 다르다
- 탐색형 스펙에 `action_title`·`key_takeaway.ask`·`weight`를 억지로 채우지 않는다
- 감시형과 탐색형을 하나의 산출물로 합치지 않는다. 원하는 게 둘이면 산출물도 둘이다
- 설명형 산출물에 "필터 몇 개"를 넣어 탐색형처럼 보이게 하지 않는다 —
  `views`(축 전환)는 저자가 미리 정한 2~3개 각도를 토글하는 것이고, 탐색형의 필터는
  독자가 임의의 값을 고르는 것이다. 각도가 2~3개로 고정돼 있으면 `views`로 충분하다
