# print-quantity

도서 제작 수량을 근거 있게 정한다. **신간과 기간본을 둘 다 본다.**

제작 계획서에 적힌 부수가 적정한지, 기간본 재고가 언제 떨어지고 몇 부를 다시 찍어야 하는지
판단해야 할 때 쓴다. 감이나 전례 대신 **신간은 경쟁서 시장에서 역산하고, 기간본은 자사 실적과
재고에서 소진 시점을 잡는다. 계수는 언제나 자사 실적에서 뽑는다.**

## 설치

```
/plugin install print-quantity@ne-claude-plugins
```

## 쓰는 법

```
/print-qty    처음 수능 SYNC 2종 제작 계획 검토       ← 신간·기간본 자동 판별
/launch-qty   신간 제작 수량만
/reprint-qty  필히 통하는 2종 재제작 수량
/launch-qty-market  고등 영어 서술형 시장 규모만
```

제작 계획서(pptx·xlsx)를 첨부하면 먼저 읽고 필요한 것만 되묻는다.

## 두 갈래

**신간인지 기간본인지가 워크플로를 통째로 가른다.**

| | 신간 | 기간본 |
|---|---|---|
| 자사 실적 | 없다 | **있다. 1차 근거다** |
| 방향 | 경쟁서 시장에서 역산 (top-down) | 자사 출고에서 투영 (bottom-up) |
| 정하는 것 | 첫해 얼마나 팔릴까 → 초판 부수 | **언제 떨어지고, 언제까지 버틸 만큼 찍을까** |
| 시장 조회 | 시장 규모를 잡으려고 | **추세가 꺾인 원인을 가리려고** |
| 상한 | 없다 | **개정·폐간 예정일** |

개정판이라도 **내용이 바뀌어 새 품목코드로 나가면 신간**, **쇄만 다시 찍으면 기간본**이다.

## 5단계

1·2·5단계는 공통이고 3·4단계가 갈린다.

```
              신간                        기간본
1)  define-segment          세그먼트·권별 위계 확정        ← 데이터를 열기 전
2)  size-market             경쟁서 전수 조회 → 목차 검증   ← 사용자 확인
        ↓                            ↓
3)  derive-coefficients     project-demand     추세·계절지수·가용재고
4)  estimate-demand         size-reprint       소진 시점 → 수량   ← 사용자 확인
        ↓                            ↓
5)  build-qty-report        HTML 렌더링 + 수치 정합 검사
```

시장 규모만 필요하면 `/launch-qty-market`으로 2단계까지만 돈다.

## 산출 구조

### 신간

```
경쟁서 추정 판매량
  ÷ K_EST   추정 → YES24 실판매
  × K_YEAR  조회 기간 → 연간
  × K_SHIP  YES24 실판매 → 총출고
                                    = SAM
  × 목표 점유율                      = SOM
  × K_FIRST(0.75)  안정기 → 첫해      = 첫해 수요
  × ONLINE / (1−ONLINE)              = 온라인 / 총판

초도 배본 > 총판 수요 → 초도 배본 + 온라인 × K_PRINT
초도 배본 ≤ 총판 수요 → 첫해 수요 × K_PRINT
```

### 기간본

```
가용재고       = Σ 재고수량 (정품 창고만. 폐기·반품·수리본·수출·세트 제외)
월별 수요 D(m) = 기준 연간 수요 × g^(경과연차) × s(m)
소진 예상월    = 누적 D(m)가 가용재고를 넘어서는 달
발주 마감일    = 소진 예상월 − 리드타임 L

수요 기준 수량 = Σ D(T ~ T+L+C) + 안전재고 − 가용재고
잔여 수명 상한 = Σ D(T ~ E) × r − 가용재고          E = 개정·폐간 예정

제작 수량 = min(수요 기준 수량, 잔여 수명 상한) → 로트 반올림
```

계수는 **카테고리마다, 품목마다 다시 뽑는다.** 같은 시리즈 안에서도 종별로 노후화율이 다르다.
실측 대조표는 `references/benchmarks.md`에 있다.

## 데이터

Metabase MCP로 조회한다. 사내망 전용이며, 접근이 안 되면 붙여넣기·엑셀로 우회한다.

| 용도 | 소스 |
|---|---|
| 경쟁서 추정 판매량 · 도서 분류 | DB1 `mart.yes24_sales_daily`, `raw.yes24_item_meta` |
| 서점 실판매 | DB3 `mart.actual_sales_daily` |
| SAP 출고 · 거래처 | DB4 `raw.sap_sales`, `raw.sap_item_isbn` |
| **재고 (기간본)** | DB4 `raw.sap_inventory_wh` |
| **제작 이력 (기간본)** | DB4 `mart.sap_inventory_daily`의 `생산입고수량` |
| 쿠팡 입고 | DB9 `raw.stocked_items` |

채널 정의는 하나로 고정한다 — 온라인 4사는 실판매, 쿠팡은 2025년 이전 SAP·2026년 이후 입고 확정,
총판은 SAP 순출고 중 온라인 5사 거래처 코드를 제외한 나머지. `LOCAL` 채널은 쓰지 않는다.

**기간본은 창고를 가려야 한다.** `raw.sap_inventory_wh`에는 폐기·반품·수리본·수출 창고가
섞여 있고, 그대로 더하면 소진 시점이 한참 뒤로 밀린다. **SAP에 생산 발주 잔량 테이블은 없다.**
제작 진행 중 물량은 제작팀에서 확정값으로 받는다.

## 보고서

단일 HTML. 배경 논의를 모르는 사람이 결론만 보고도 이해할 수 있게 만든다.

**신간** — 목표 점유율 슬라이더, 경쟁서 범위 토글, 계산 흐름, 용어 툴팁, 계수 모달

**기간본** — 커버 기간 슬라이더, **소진 타임라인**(잔량 곡선 + 월별 수요 + 발주 마감 점선),
개정 상한 토글, 창고 분류, 제작 이력. 결론에 **수량과 함께 날짜**가 들어간다.
발주 마감일이 이미 지났으면 색을 바꿔 경고한다.

전달 전에 검사를 돌린다.

```
python3 scripts/check_qty_report.py <보고서.html>
```

스크립트가 데이터 블록을 보고 신간·기간본을 스스로 가른다.
초기 표시값과 스크립트 산출값이 어긋나는지 잡아준다. **가장 많이 틀리는 곳이다.**

## 자주 틀리는 것

### 공통

| 증상 | 원인 |
|---|---|
| 새로고침하면 숫자가 바뀐다 | 초기 표시값과 스크립트 산출값이 다르다. 검사 스크립트로 잡는다 |
| 경계값에서 천 단위가 어긋난다 | 파이썬 `round`는 0.5를 짝수로 내린다. Node로 검산한다 |
| 분류를 고쳤는데 본문 서술이 안 맞는다 | 검사 스크립트가 뽑아주는 퍼센트 목록을 하나씩 대조한다 |

### 신간

| 증상 | 원인 |
|---|---|
| 총판 수요가 과대하게 나온다 | 반품이 포함된 구간으로 `ONLINE`을 다시 뽑는다 |
| 두 도서의 산식이 비대칭이라고 지적받는다 | `K_PRINT`는 항상 양쪽에 같이 적용한다 |

### 기간본

| 증상 | 원인 |
|---|---|
| 소진 시점이 터무니없이 멀다 | 폐기·반품 창고 재고를 합쳤다 |
| 수요가 실제보다 적다 | 세트 품목코드 판매분이 빠졌다 |
| 성수기 직전에 품절났다 | 연평균으로 수요를 깔았다. 계절지수를 안 썼다 |
| 계절성이 1년치밖에 안 나온다 | 개정으로 품목코드가 바뀌었다. 구품목코드를 이어 붙인다 |
| 재고가 계속 남는다 | 개정 예정일을 확인하지 않고 커버 기간으로만 찍었다 |
| 추세가 꺾인 이유를 설명 못 한다 | 2단계 시장 조회를 건너뛰었다 |
